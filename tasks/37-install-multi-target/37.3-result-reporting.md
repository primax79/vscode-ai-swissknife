# 37.3 — Rendicontazione degli esiti per target

Un task, un commit. Dipende da 37.2.

**Read first:** `plan.md`, la gestione degli esiti in `availableView.ts` (`switch (outcome.status)` per `applied` / `refused` / `rolled-back` / `manual-recovery-required`), gli esiti per target di `37.1`.

## Nota dalla verifica di 37.1

`applyInstallMatrix` (src/engine/installMatrix.ts sul branch `kilo/fbac7d820930`) restituisce lo stato `refused` sia per un rifiuto effettivo sia per un target saltato perché già esistente (conflitto senza `overwrite`) o non supportato. Derivare i conteggi "skipped (existing)" e "unsupported" da `outcome.target.prepared` (`supported`, `plan.conflict`), non dal solo `status`.

## Cosa fare

Sostituire i messaggi di esito dei singoli flussi con un unico reporter: una sola notifica che riepiloga i conteggi `applied / skipped (existing) / unsupported / failed`; in caso di qualsiasi errore, offrire "Show details" aprendo un canale di output che elenca target, stato e motivo. `manual-recovery-required` per qualsiasi target rimane un errore modale che elenca i percorsi (comportamento attuale, `:657-662`). Aggiornare Installed una sola volta alla fine, non una volta per target.

## Verification

`ui.test.ts`: esiti misti (applied, refused, rolled-back) producono un unico messaggio di riepilogo e una sola chiamata di refresh; `manual-recovery-required` continua a mostrare la modale con i percorsi. `npm test` verde, `npm run build` pulito.
