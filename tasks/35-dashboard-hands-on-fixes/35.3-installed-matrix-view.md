# 35.3 — Installed matrix view (replaces the flat table)

**Depends on:** nothing beyond current `main` (independent of 35.1/35.2,
but dispatch after they land per `plan.md`'s file-overlap caution).

## Why

Combined user feedback after hands-on testing: the flat unified table
(`getInstalledSectionHtml`, `src/ui/dashboard.ts:842-...`) is visually
poor, has no column sorting, and — the real functional gap — gives no way
to compare the same artifact across assistants at a glance. A user asked
directly: **"obviously the status per tool for the same skill can
differ, so each artifact needs a sub-row per tool"** — i.e. this is not a
simple pivot-to-badges matrix, it's a grouped/expandable list: one parent
row per artifact identity, one real sub-row per assistant that has it,
each sub-row carrying its own actual drift status and actions.

**Explicit product decision (asked directly, not assumed): this view
REPLACES the flat table as the Installed section's primary view — it is
not an added toggle.** Clicking a row still opens the existing detail
panel mechanism (`selectRow`/`requestDetail`/`itemDetail`,
`src/ui/dashboard.ts`) — no functionality removed, only reorganized.

## Data model

- **Managed installations** (the comparison target): group all
  `ManagedInstallation[]` by artifact identity, reusing the exact same
  provenance-first / name+kind-fallback strategy already implemented and
  tested in `findRelatedInstallations` (`src/engine/crossFrameworkLookup.ts`)
  — same-`sourceId`+`artifactId` when both are present, else same
  `name`+`kind`. **Also group by `scope`** (a project-scope and a
  global-scope installation of the "same" artifact are different rows —
  confirmed by the user's own sort request including `scope` as a column,
  meaning it stays a per-row dimension, not folded into the matrix).
  Do not write a new ad-hoc grouping function if `findRelatedInstallations`
  can be reused/adapted directly — check whether adapting its signature
  (e.g. exporting a `groupByIdentity(all: ManagedInstallation[]):
  Map<string, ManagedInstallation[]>` helper alongside it in the same
  file) is cleaner than reimplementing the matching logic in
  `dashboard.ts`.
- **Columns = assistants.** Use `ALL_ADAPTERS` (`src/adapters/registry.ts`),
  **not** `getEnabledAdapters()` — this is an informational comparison
  view, not a target picker, and the `getEnabledAdapters()` rule
  (`tasks/CONTEXT.md`, search "Any `showQuickPick` that lets the user pick
  a TARGET assistant") explicitly does not apply here; a disabled
  assistant's existing installations are still real and worth comparing
  against.
- **Observed (unmanaged) items are out of this matrix.** They're
  inherently single-location discoveries with no natural
  cross-environment comparison. Keep them as a separate, simpler list
  section below the matrix (reuse today's existing observed-row rendering
  — kind/name/status badge/Promote button — from
  `getInstalledSectionHtml`'s current unmanaged-row logic, just not
  interleaved with managed rows in one table anymore).

## Rendering

- One parent row per (identity, scope) group: kind pill, name, scope
  pill, and a compact row of small per-assistant status indicators (reuse
  the existing `assistant-icon`/pill visual language, colored by that
  assistant's status — success/info/warning/error, same badge classes
  already defined in the `<style>` block) so the comparison is visible
  **before** expanding — this is the actual "compare environments at a
  glance" value the user asked for.
- Expanding a parent row (click, matching the existing `toggleFolder`-style
  collapsible pattern already used in the catalog view from Initiative
  33.2 — reuse that exact interaction pattern, don't invent a new one)
  reveals one sub-row per assistant that has this artifact: full status
  badge/text (matching today's per-row badge text, e.g. "● Managed · up
  to date"), and per-sub-row action buttons:
  - **Diff vs. original** — when available (same `diffAvailable` logic
    the detail panel already computes) — wire directly, don't require
    opening the detail panel first.
  - **Preview** — new for installed items (previously only available for
    not-yet-installed catalog artifacts via Initiative 33.3). For an
    installed item, "preview" means opening its main file the same way
    the sidebar's own tree item does today (`vscode.open` command on the
    artifact's path, or `SKILL.md` for a skill directory — check
    `src/ui/installedView.ts`'s existing `item.command = { command:
    'vscode.open', ... }` wiring for the exact path-resolution logic
    already implemented there and reuse it, don't reimplement).
  - **Update to latest** — when this specific assistant's status is
    `update-available`/`modified-and-update-available` — reuse
    Initiative 34.2's existing `updateItem` message/identity-key pattern
    exactly.
  - Clicking anywhere else on the sub-row (not a button) opens the
    existing detail panel for that specific installation (same
    `selectRow`/`requestDetail` flow already wired for table rows today —
    the sub-row's identity key is exactly `getIdentityKey(inst)`, reuse
    directly).
- **Column sorting**: clickable column headers for Kind, Name, Scope, and
  Status, applied to the **parent rows**. For Status, since a parent row
  can have different statuses across its sub-rows, sort by the "worst"
  status present in the group, using this severity order (worst first):
  `missing-on-disk` > `modified-and-update-available` >
  `update-available` > `modified-locally` > `up-to-date`. Persist the
  current sort in client-side JS state (no need to survive a panel
  reload).
- Filters (env/scope/membership/kind/search) from the existing toolbar
  keep working, now filtering parent rows (and their sub-rows) instead of
  flat table rows — re-verify each filter still does something sensible
  against the new grouped structure (e.g. "membership: unmanaged" now
  filters the separate observed-items list, not the matrix).

## Scope (implementation)

- `src/ui/dashboard.ts`: rewrite `getInstalledSectionHtml` (and its
  incremental-update counterpart in `update()`'s Phase A/postMessage
  path) to produce this grouped structure instead of the flat
  `<table>`. Keep using the established incremental `postMessage`
  pattern for refreshes (Initiative 32.3) — do not reintroduce full-page
  reloads.
- Add whatever new webview messages are needed for the new sub-row
  Preview action (if it doesn't map onto an existing message).

  confirm the parent row's at-a-glance indicators show both statuses
  correctly, expanding reveals two distinct sub-rows with correct
  per-assistant status/actions, and clicking Update on just the
  out-of-date sub-row only updates that one installation.
- Manual: sort by each of Kind/Name/Scope/Status, confirm parent-row

  Status sorting.
- Manual: Diff and Preview buttons work per sub-row without needing to
  open the detail panel first; the detail panel itself still opens

- Manual: unmanaged items still render (in their own section) with
  Promote still working.
