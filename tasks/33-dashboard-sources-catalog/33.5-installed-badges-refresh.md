# 33.5 — "Installed in" badges + catalog refresh

**Depends on:** 33.4 (merged).

## Why

The sidebar's catalog already shows which assistants an artifact is
installed in, via description/tooltip, not the label (per `src/ui/ui.test.ts`'s
own coverage: *"shows which assistants an artifact is installed in via
description and tooltip, not the label"*) — the Dashboard's catalog view
(33.2) has rendered rows with no such indicator yet. Separately, every
mutation from 33.1/33.4 needs the cross-provider/status-bar refresh
`specs/phase-9-spec.md` §4.1 requires, which hasn't been wired end-to-end
in any single task yet.

## Scope

- Extend `catalogData` (33.2) to include each artifact's installed-in
  state — `AvailableTreeDataProvider` already tracks this via
  `installedByArtifactKey` (built during `refreshCatalog`, per the Codex
  review's finding — re-confirm the exact field/accessor name by reading
  the class) — surface it in the payload rather than recomputing
  installed-state independently in the Dashboard.
- Dashboard UI: render a small badge/icon set per catalog artifact row
  (reusing the existing `assistant-icon`/pill visual language from
  `src/ui/dashboard.ts`'s CSS, per the spec's "keep existing style"
  constraint) showing which assistants already have it installed.
- Wire `refreshCatalog` (mirroring `aiSwissknife.refreshCatalog`,
  `src/extension.ts:409`) as a Dashboard action (e.g. a refresh button on
  the Sources & Catalog section), and confirm every 33.1/33.4 mutation
  path (`addSource`, `removeSource`, `importConfig`, `installArtifact`,
  `installFolder`, `installSourceGroup`) actually triggers
  `availableProvider.refreshCatalog()` (some do internally already,
  confirmed per-method during those tasks — this task is the final
  end-to-end check, not new logic for each) **and** the status-bar/
  sidebar-provider refresh from Initiative 32.1's callback.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Manual: install an artifact from the Dashboard's catalog view, confirm
  its "installed in" badge appears without needing a manual
  `refreshCatalog` — proves the cross-refresh actually fires.
- Manual: trigger `refreshCatalog` from the Dashboard after externally
  editing a source's content (e.g. touching a local-folder source's
  files) — confirm the catalog view picks up the change, matching what
  the sidebar's own `refreshCatalog` command does.
