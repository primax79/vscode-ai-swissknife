# 30.4 — Migrate `sourcesView.ts`'s icon switch

> Part of [Source-resolver registry](plan.md) · spec: [../specs/adapter-and-source-registries.md](../specs/adapter-and-source-registries.md) §4.3, §5

## Goal

The last standalone piece of `Source.type`-keyed branching: replace
`sourcesView.ts`'s own `getSourceTypeIcon` switch with a lookup into the
registry built by 30.3.

This task must produce one commit containing only its changes.

## Steps

1. In `src/ui/sourcesView.ts`, find `getSourceTypeIcon(type: Source['type'])`
   (currently a `switch` returning `new vscode.ThemeIcon('folder' |
   'repo' | 'extensions' | 'git-commit' | 'link')`, with a `default` case
   returning `new vscode.ThemeIcon('source-control')`).
2. Replace its body with:
   ```ts
   function getSourceTypeIcon(type: Source['type']): vscode.ThemeIcon {
     return new vscode.ThemeIcon(getSourceResolver(type).iconThemeId);
   }
   ```
   importing `getSourceResolver` from `../sources/registry`.
3. The original `default` case returned `'source-control'` for an
   unrecognized type — `getSourceResolver` instead **throws** for an
   unknown type (per 30.3's implementation). Since `Source['type']` is a
   closed union of the five known values, this is not a behavior
   regression in practice, but confirm no caller of `getSourceTypeIcon`
   can realistically receive a value outside that union (e.g. from
   deserializing an old/malformed `manifest.json`) before removing the
   fallback — if it can, keep a `try { ... } catch { return new
   vscode.ThemeIcon('source-control'); }` around the lookup instead of
   letting it throw, and say so in the commit message.

## Verification

- Run full test suite, typecheck, lint, build.
- `grep -n "getSourceTypeIcon" src/ui/sourcesView.ts` — confirm the
  function body is now a one-line delegation, and
  `grep -n "'folder'\|'repo'\|'extensions'\|'git-commit'\|'link'" src/ui/sourcesView.ts`
  returns no matches (the literal icon ids no longer live here, only in
  each resolver module's own `iconThemeId`).
- Manually in the Extension Development Host: confirm every registered
  source in the Sources view still shows the same icon per type as before
  this change (visually compare against a screenshot/memory of the
  pre-change tree, or re-add one of each type and check against the table
  in spec §4.3/task 30.1).
