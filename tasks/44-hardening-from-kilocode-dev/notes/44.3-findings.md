# 44.3 Phase 1 findings (verified 2026-10-08 with the real Kilo 7.4.5)

Method: isolated `HOME` (and empty `XDG_CONFIG_HOME`) per case, a temp project dir, `kilo mcp list`. The entry was either produced by **our own Kilo adapter** (`getAdapterWithHomeRoot('kilo-code', home).writeMcpServer`) or written by hand. Temp dirs removed afterwards; the owner's real config was never touched.

| # | Case | Result of `kilo mcp list` |
| --- | --- | --- |
| 1 | Adapter-written global `~/.config/kilo/mcp.json` (shape `{type:"stdio", command:"echo", args:[..], env:{..}}`) | **"No MCP servers configured"**: the install is a silent no-op |
| 2 | Adapter-written project `<project>/.kilo/mcp.json`, same entry | **"No MCP servers configured"**: same no-op |
| 3 | Our `stdio` shape placed in the **right** file (`~/.config/kilo/kilo.jsonc`, field `mcp`) | **`Error: Configuration is invalid ... Expected { "type": "local", ... } \| { "type": "remote", ... }, got {"type":"stdio",...}`** : this would break the whole Kilo config, not just the server |
| 4 | Correct shape `{"type":"local","command":["echo","hello"],"environment":{...}}` in global `~/.config/kilo/kilo.jsonc`, **with a `//` comment in the file** | Loaded and listed (`swk-test`, status failed only because `echo` is not an MCP server, which is expected) |
| 5 | Correct shape in project `<project>/.kilo/kilo.jsonc` | Loaded and listed |

## Conclusions

1. **F3 is confirmed and has two layers**: wrong file (Kilo ignores `mcp.json`) AND wrong entry shape (Kilo wants `type: "local"` with `command` as an **array** and `environment`, or `type: "remote"` with `url`/`headers`; `stdio`/`args`/`env` are rejected as invalid configuration).
2. **Fixing only the file path would be dangerous** (case 3: an invalid config makes Kilo refuse to start with it). Phase 2 must change file and shape together.
3. JSONC with comments is accepted by Kilo, so the writer must preserve comments (`jsonc-parser`).
4. Real shapes (source: `kilocode-dev/packages/core/src/v1/config/mcp.ts`): local = `{type:"local", command:[cmd,...args], cwd?, environment?, env? (alias), enabled?, timeout?}`; remote = see the `Remote` struct in the same file (fields to be read by the executor, not guessed).

## Phase 2 verification (2026-10-09, architect, real Kilo 7.4.5, adapter after the fix)

- Install of a stdio and an http server into a `kilo.jsonc` that already had comments, a `model`, an `mcp.existing` remote entry and trailing commas: `kilo mcp list` lists `existing`, `swk-new` and `swk-remote`; comments and other keys preserved. The opt-in smoke test (`AISK_REAL_KILO=1`) passes.
- Two limitations found: the untouched `existing` entry was reformatted and its trailing comment displaced (task 44.6); and the real `kilo mcp list` itself **adds `$schema` and a default `permission` block to the user's `kilo.jsonc`** (Kilo's own behaviour, not ours: tests that compare files byte for byte must not run Kilo in between).
- Build lesson: `jsonc-parser`'s UMD main could not be bundled by esbuild (`require('./impl/format')` left at runtime, which breaks activation); fixed with `mainFields: ['module','main']` and a build-time guard against unbundled relative requires.
