# 44.1 — Irrigidire la risoluzione delle sorgenti git

Un task, un commit. Igiene di sicurezza su un percorso di input non attendibile (piano F1). Non è una RCE dimostrata; non descriverla come tale nei messaggi di commit o nei commenti del codice.

**Read first:** `../CONTEXT.md`, `plan.md` (F1), `src/sources/gitProcess.ts`, `src/sources/gitCustom.ts:80-135` e gli altri utilizzatori di `runGit` (`gitSingleItem.ts`, `gitMarketplace.ts` e qualsiasi altro chiamante di `runGit(`: `grep -rn "runGit(" src`), `src/sources/sourceDefaults.ts` (`validateLocation`, 36.1), `src/domain/registry.ts` (`fromDesiredSource`), `src/sources/remoteUrl.ts` (il percorso di fetch HTTP).

## Cosa fare

1. **Validare al momento della risoluzione, non solo nel wizard.** In ogni resolver git, prima di qualsiasi `runGit`, invocare `validateLocation(type, source.url)`; in caso di errore sollevare un'eccezione con un messaggio chiaro (emerge come il gruppo diagnostico esistente). Lo stesso vale per i ref: `branch`, `tag`, `commit` devono essere non vuoti, non devono iniziare con `-`, non devono contenere spazi bianchi, caratteri di controllo o `..`; il commit deve inoltre soddisfare `/^[0-9a-f]{7,40}$/i`.
2. **Separatori `--`**: `git clone -- <url> <targetDir>`; `git checkout <ref> --`... dove il ref è una revisione (usare `git checkout --detach <ref> --` o `git checkout <ref> --` a seconda dei casi, mantenendo il comportamento attuale); `git reset --hard <ref>` non presenta ambiguità sulle opzioni una volta che il ref ha superato la validazione, ma usare comunque il valore validato.
3. **Id della directory di cache**: dopo la sanitizzazione, rifiutare gli id vuoti, `.` o `..` (e tutti quelli che finiscono per iniziare con `.`), sollevando un'eccezione; verificare inoltre che `path.resolve(targetDir)` inizi con `path.resolve(baseCacheDir) + path.sep`. Non eseguire mai `rm -rf` su una directory che non supera questa verifica.
4. **Allow-list dei protocolli**: in `runGit` impostare `GIT_ALLOW_PROTOCOL` a `file:git:http:https:ssh` (ciò di cui hanno bisogno le forme di URL validate; mantenere `file` solo se un resolver o un test clona repository locali: verificare, non fare supposizioni) sul processo avviato.
5. Non modificare il comportamento per le sorgenti valide: i test esistenti restano verdi senza modifiche.
