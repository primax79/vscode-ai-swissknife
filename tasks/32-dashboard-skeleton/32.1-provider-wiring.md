# 32.1 — Provider wiring

**Depends on:** nothing beyond current `main` (re-verify Phase 8/29 has
landed first — see `plan.md`).

## Why

`DashboardPanel`'s constructor and `render` (`src/ui/dashboard.ts:21,114`)
take only `InstalledTreeDataProvider`; both `extension.ts` call sites
(`:550,552`) pass only that. Every new section in Initiative 33/34 needs
`SourcesTreeDataProvider`/`AvailableTreeDataProvider` in scope, plus a way
to trigger the same status-bar/sidebar-provider refresh the sidebar's own
mutating commands already perform (`specs/phase-9-spec.md` §4.1).

## Scope

- `src/ui/dashboard.ts`: `DashboardPanel`'s private constructor and
  `static render` gain `sourcesProvider: SourcesTreeDataProvider`,
  `availableProvider: AvailableTreeDataProvider`, and a
  `refreshCallback: () => void` parameter (or a small interface bundling
  it — pick whichever reads cleaner once the constructor signature is in
  front of you). Store all three as private fields, matching the existing
  `_provider` field's pattern.
- `src/extension.ts`: both `DashboardPanel.render(...)` call sites
  (`:550,552`) pass `sourcesProvider`, `availableProvider`, and a callback
  wired to the same refresh logic `updateStatusBar()` and the tree
  providers' own `refresh()`/`refreshCatalog()` calls already use inside
  `activate()` (`:335` for `updateStatusBar`, re-grep for its exact call
  sites after mutating commands — likely alongside `installedProvider.refresh()`/
  `availableProvider.refreshCatalog()` in each command registration). Do
  not inline the refresh logic a second time inside `dashboard.ts` — pass
  the existing closure(s) in, or extract them to a small named function in
  `extension.ts` if they aren't already one, and pass that.
- No new webview messages or UI in this task — purely constructor/wiring.
  `DashboardPanel`'s actual behavior is unchanged; the new fields are
  unused until Initiative 33/34 (a private field with no reader yet is
  fine here, it's the necessary base for what follows).
