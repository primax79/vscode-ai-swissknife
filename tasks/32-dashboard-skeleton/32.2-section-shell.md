# 32.2 — Section navigation shell + New Artifact entry point

**Depends on:** 32.1 (merged).

## Why

The Dashboard needs room for four sections (Overview, Installed, Sources &
Catalog, Recommendations) without becoming an even-more-monolithic single
scroll. Kilo/Gemini's review specifically recommended building this shell
*before* Initiative 33/34's content lands, to avoid building large HTML
blocks against a placeholder layout and reshaping them later
(`specs/phase-9-spec.md` §3.3).

## Scope

- `src/ui/dashboard.ts`: add top-level section tabs reusing the existing
  `.tab-btn`/`.tab-btn.active` CSS classes already defined for the kind
  filter (`:527-540`) — four tabs: **Overview**, **Installed**, **Sources
  & Catalog**, **Recommendations**. Only **Installed** has real content in
  this task (today's unified table/filters/detail panel, ported in as-is —
  no behavior change, just moved under its own tab instead of being the
  entire page). **Overview**, **Sources & Catalog**, **Recommendations**
  render an empty/placeholder section container (a `<div>` with an id
  Initiative 33/34 will target) — do not build their content here.
- Split `getHtml()` (`:304-1049`) into per-section template functions
  (e.g. `getOverviewHtml()`, `getInstalledSectionHtml(...)`,
  `getSourcesCatalogHtml()`, `getRecommendationsHtml()`) called from one
  top-level assembly function — this is the "split into per-section
  template functions" risk mitigation from `specs/phase-9-spec.md` §6,
  done now while the Installed section is the only one with real content,
  so the pattern is established before three more sections' worth of HTML
  land on top of it.
- Add a `+ New Artifact` button in the Dashboard header
  (`src/ui/dashboard.ts:676-686`) sending a new `createArtifact` webview
  message; the extension-host handler calls the same `FormEditorPanel`
  create-mode flow `aiSwissknife.createArtifact` already uses
  (`src/extension.ts:456-493`) — reuse that flow's logic directly (extract
  it to a callable function if it's currently only inline in the command
  registration, rather than duplicating it inside `dashboard.ts`).
- Client-side JS: section-switching logic (show/hide section containers,
  mark the active tab) — plain DOM show/hide, no framework.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Manual: open the Dashboard, confirm all four tabs render, switching
  tabs shows/hides the right container, and the **Installed** tab's
  content and every existing action (filters, row selection, detail
  panel, Copy/Move/Edit/diff/Promote — everything from Initiative 26)
  behaves identically to before this task — this is a pure relocation,
  verified by clicking through the same flows Initiative 26/27's own
  manual verification covered.
- Manual: `+ New Artifact` opens `FormEditorPanel` in create mode
  identically to the sidebar's `Create Artifact` command.
