# 03.4 — Shared skill codec, path validation, and directory payload (hardening)

> Part of [Claude + Kilo adapters](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · hardening context: [../../SPEC.md](../../SPEC.md) §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) findings B2, B5, B6 · **revised after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decisions 1, 10, 11 — a context-blind reviewer found this file's first draft asked for a mandatory `files` field that the codec function it also specifies structurally cannot populate; two reviewers independently found a separate, more severe bug in how a later task uses the adapter path this file owns)

**Goal**: close three gaps a second review found in the already-merged
adapters (`src/adapters/claude.ts`, `src/adapters/kilo.ts`) and detector
(`src/sources/detect.ts`): frontmatter parsing is duplicated three times
with no real YAML guarantee, a skill's supporting files (scripts,
references, assets) are silently dropped on install, and untrusted
artifact names/paths aren't validated before being joined into a
filesystem path. Also adds the directory-path method the install engine
(initiative 06) needs and could not safely derive from what this task
originally shipped.

**Depends on**: task 02.3 landing first (this task extends
`CanonicalSkill`, which 02.3 doesn't touch, so it can also run in
parallel with 02.3 if delegated separately — but read 02.3's task file
first to avoid duplicating the `nativeFormat`/`ResolvedRevision` changes
it already makes).

Steps:

1. **Add a real YAML dependency.** Add `yaml` (the `eemeli/yaml` npm
   package) to `package.json`'s `dependencies`. This project commits to
   **semantic preservation, not byte-verbatim preservation** (SPEC.md §7,
   finding B6): parsing and re-serializing with a real YAML library
   preserves every *value* supported by the schema this project actually
   uses (multiline strings, lists, nested objects), but does not
   reproduce the original document's exact comments, quote style, or key
   order in every edge case — say this precisely in any code comment or
   doc you write, not "round-trips every value," which overclaims.
2. **Extract one shared codec module**, `src/adapters/skillCodec.ts`:

   ```ts
   import type { CanonicalSkill } from './types';

   export function parseSkillMarkdown(raw: string): CanonicalSkill;
   export function serializeSkillMarkdown(skill: CanonicalSkill): string;
   ```

   **`parseSkillMarkdown` parses only the `SKILL.md` text — frontmatter
   + body — and always returns `files: []`.** It has no directory to
   walk (its only input is a string), so it structurally cannot populate
   a multi-file payload; don't try to make it do so. Populating the real
   `files` array from a skill's other files is a **separate**
   responsibility layered on top, owned by whichever function has a
   directory to walk — `readSkill()` in `claude.ts`/`kilo.ts` (step 5
   below) and `resolveArtifactContent()` (02.3) both call
   `parseSkillMarkdown()` for the `SKILL.md` part, then separately walk
   the directory and assign the real `files` array onto the result
   before returning it. State this explicitly in code comments at both
   call sites so a future reader doesn't "fix" `parseSkillMarkdown` to
   take a directory path instead.

   Replace the three separate/duplicated frontmatter implementations
   currently in `src/adapters/claude.ts`, `src/adapters/kilo.ts`, and
   `src/sources/detect.ts` (its `extractSkillFrontmatter`/similar helper)
   with calls to this shared module. `detect.ts` only needs `name` (and
   maybe `description`) for the detection pass — it's fine for it to
   call `parseSkillMarkdown` and only read the fields it needs.
3. **Validate names and paths before they reach a destination join.** In
   `skillCodec.ts` or a new `src/adapters/validate.ts` (your choice, keep
   it discoverable), add:

   ```ts
   export function validateSkillName(name: string): void; // throws with a clear message on failure
   ```

   Reject: empty string, any path separator (`/` or `\`), `.` or `..` as
   the whole name, a name starting with `.`, NUL bytes, and anything
   that isn't letters/digits/hyphen/underscore. Call this from every
   adapter's `skillPath()`/`writeSkill()` (`claude.ts`, `kilo.ts`)
   **before** joining the name into a path.

   Also add:

   ```ts
   export function validateRelativeFilePath(root: string, candidate: string): string;
   ```

   **First, explicitly reject an absolute `candidate`** via
   `path.isAbsolute(candidate)` — do this check before calling
   `path.resolve`, as a first-pass filter, not only as a side effect of
   the resolve+compare below (round 001 review flagged this ordering as
   worth stating explicitly rather than leaving implicit). Then resolve
   `candidate` against `root` and throw if the resolved path is not
   equal to `root` or does not start with `root + path.sep` (a real
   contains-check, not a naive string-prefix comparison, which a sibling
   directory like `root-evil` would pass incorrectly). This is what
   task 04.3/06 will use for each file in a skill's directory payload,
   not just the skill's own name.
4. **Add `skillDir()` to the `Adapter` interface** (`src/adapters/
   types.ts`), returning the skill's **directory**, distinct from
   `skillPath()` which returns the `SKILL.md` **file** path inside it:

   ```ts
   skillDir(name: string, loc: LocationRef): string; // e.g. .../skills/<name>  (parent of skillPath's return value)
   ```

   Implement it in both `claude.ts` and `kilo.ts` as
   `path.dirname(this.skillPath(name, loc))` — **this is the single
   most important fix in this task**: all three engines in round 001's
   review independently found that a later task (`06.1`/`06.2`, the
   install engine) needs the skill's *directory* to do an atomic
   directory swap, but the only method that existed (`skillPath()`)
   returns the `SKILL.md` *file* path — renaming a directory onto that
   path would either create a directory literally named `SKILL.md`, or
   fail outright. `skillDir()` closes that gap at its source instead of
   letting the install engine derive it inconsistently in two different
   places.
5. **Extend `CanonicalSkill` with a directory payload.** In
   `src/adapters/types.ts`:

   ```ts
   export interface ArtifactFile {
     relativePath: string; // relative to the skill's own root directory, e.g. "scripts/run.sh"
     content: Buffer;
     mode?: number;
   }

   export interface CanonicalSkill {
     name: string;
     description: string;
     body: string;
     extraFields: Record<string, unknown>;
     files: ArtifactFile[]; // every file under the skill directory EXCEPT SKILL.md itself — see step 2 on who populates this
   }
   ```

   Update `claude.ts`'s and `kilo.ts`'s `readSkill`/`writeSkill` to
   actually walk the skill's directory: `readSkill` calls
   `parseSkillMarkdown()` on the `SKILL.md` contents, then separately
   walks every other file under `skillDir()`, validating each
   `relativePath` with `validateRelativeFilePath` (step 3) as it goes,
   and assigns the result onto `files` before returning. `writeSkill`
   creates every entry in `files` at its `relativePath` under
   `skillDir()` (also re-validated), restoring `mode` via `fs.chmod`
   when present, in addition to writing `SKILL.md` itself via
   `serializeSkillMarkdown()`. **Symlinks**: refuse to follow or write a
   symlink anywhere in a skill's directory tree (throw a clear error
   naming the offending path) — a full symlink policy is a follow-up,
   not silently supporting or silently ignoring one.
6. **Validate required frontmatter, don't silently fall back.**
   `parseSkillMarkdown` must throw a clear, specific error (not return a
   partially-populated `CanonicalSkill`) when `name` or `description` is
   missing, empty, or non-string, or when the frontmatter block itself
   is malformed YAML or not a mapping. This closes a gap round 001's
   Codex review found: the detector currently falls back to the
   directory basename when `name` is absent, silently turning a broken
   skill into a valid-looking catalog entry. Callers that want a
   best-effort name for a listing (like `detect.ts`) should catch this
   error themselves and handle it as a detection-time diagnostic — see
   task 04.3's invalid fixtures — not have the codec silently paper over
   it.
7. Update every existing test (`claude.test.ts`, `kilo.test.ts`,
   `detect.test.ts`, and any translator test that builds a
   `CanonicalSkill` literal) for the new `files: ArtifactFile[]` field —
   most can pass `files: []` where a multi-file payload isn't the point
   of that specific test. Add new tests specifically for this task:
   + Round-trip a skill with at least one supporting file (e.g. build a
     temp fixture with `SKILL.md` + `scripts/run.sh`) through
     `readSkill`/`writeSkill` and confirm the supporting file's content
     and (on POSIX) executable mode bit survive.
   + `skillDir()` returns the parent directory of `skillPath()` for the
     same `name`/`loc`, for both adapters, at both scopes — assert this
     directly, don't just eyeball it.
   + `validateSkillName` rejects each malicious case listed in step 3.
   + `validateRelativeFilePath` rejects an absolute path (explicitly,
     via the `path.isAbsolute` check) and a `../`-escaping relative path.
   + A symlink inside a skill directory causes `readSkill` to throw
     rather than silently follow it (construct a real symlink in a temp
     dir with `fs.symlink`).
   + `parseSkillMarkdown` throws a specific error for missing `name`,
     missing `description`, and malformed YAML frontmatter — one test
     per case.

**Verification**: `npm run typecheck && npm run lint && npm test` all
pass. One commit containing all changed/new files — nothing else. After
this commit, update `tasks/00-INDEX.md`.
