# 07.2 — Available view (browse + install command)

> Part of [Minimal UI](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md)

**Goal**: a tree view listing `Artifact`s resolved from all registered
`Source`s, with an "Install" action per artifact that runs the pipeline
from initiative 06 with a preview step.

**Grounding**: `src/sources/localFolder.ts`/`gitCustom.ts` (initiative 04)
for resolving a `Source` to `Package[]`/`Artifact[]`; `src/install/
plan.ts`/`apply.ts` (initiative 06) for the install pipeline;
`src/ui/sourcesView.ts` (task 07.1) for how the registry is read in the
UI layer — this task depends on both 06 and 07.1 having landed.

Steps:

1. Add to `package.json`'s `contributes.views["ai-swissknife"]`:
   `{ "id": "aiSwissknife.available", "name": "Available" }`, and to
   `contributes.commands`: `aiSwissknife.install` (title "Install",
   category "AI Swissknife").
2. Create `src/ui/availableView.ts`:
   - A `vscode.TreeDataProvider` with a two-level tree: top level = one
     node per registered `Source`; children = the `Artifact`s its
     resolver currently returns (call `resolveLocalFolder`/
     `resolveGitCustom` depending on `source.type` — for `type ===
     'git-custom'`, pass a cache dir under
     `path.join(os.homedir(), '.ai-toolkit', 'cache', 'sources')`, per
     SPEC.md's cache-dir convention already implied by task 04.2).
   - Resolving on every tree expand is fine for this Phase (no caching
     layer) — don't add a caching mechanism speculatively; note in your
     report if resolution feels slow enough to warrant one, but don't
     build it now.
   - Leaf tree items show `artifact.name` + `artifact.kind`, with
     `contextValue: 'artifact'` so the "Install" command can be scoped to
     appear only on artifact nodes (via `package.json`'s
     `contributes.menus["view/item/context"]` with `when:
     "viewItem == artifact"`).
3. Implement the `aiSwissknife.install` command:
   - Prompt `showQuickPick` for target assistant (`claude-code`/
     `kilo-code` — the only two adapters that exist per this Phase) and
     target scope (`global`/`project`, `project` disabled with no open
     workspace folder, same rule as task 07.1).
   - Call `planInstall` (initiative 06.1), then show the plan to the user
     — at minimum a `vscode.window.showInformationMessage` listing the
     target path, whether it's a conflict, and the diagnostic, with
     "Install"/"Cancel" actions (`showInformationMessage(msg, {modal:
     true}, 'Install', 'Cancel')` or similar) — this **is** the "preview"
     step from SPEC.md §2.4, it does not need a dedicated webview/panel
     for Phase 1.
   - Only on explicit user confirmation, call `applyInstall` (initiative
     06.2), then show a success/failure message reflecting `verified`.
4. Register the provider and command in `src/extension.ts`.
5. Same activation-verification caveat as task 07.1: state plainly
   whether you could launch a real Extension Development Host or only
   verified build/lint/typecheck.

**Verification**: `npm run lint && npm run typecheck && npm run build`
all exit 0. One commit containing the `package.json` change,
`src/ui/availableView.ts`, and the command wiring — nothing else.
