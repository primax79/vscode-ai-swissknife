# 07.2 — Available view (browse + install command) (revised)

> Part of [Minimal UI](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · revised per [../../SPEC.md](../../SPEC.md) §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) findings B1, I3, I4

**This supersedes an earlier version of this task file.** Corrections:
resolving on every tree expand (rather than an explicit refresh) fetches
over the network on every UI interaction; the preview step didn't show
the full plan (file list, diagnostics, resolved commit) the revised
`InstallPlan` (06.1) now actually has; and the install flow needs to
refresh the Installed view (07.3) afterward, which didn't exist as a
stated requirement before.

**Goal**: a tree view listing `Artifact`s resolved from all registered
`Source`s via an explicit "Refresh Catalog" action (not fetch-on-expand),
with a full-detail preview before install.

**Grounding**: `src/install/plan.ts`/`apply.ts` (06, revised) for the
pipeline; `src/sources/localFolder.ts`/`gitCustom.ts`'s
`resolveArtifactContent` (02.3) for fetching real content; `src/ui/
sourcesView.ts` (07.1) for the established registry-backed
`TreeDataProvider` pattern in this codebase.

Steps:

1. Add to `package.json`'s `contributes.views["ai-swissknife"]`:
   `{ "id": "aiSwissknife.available", "name": "Available" }`; to
   `contributes.commands`: `aiSwissknife.install` (title "Install") and
   `aiSwissknife.refreshCatalog` (title "Refresh Catalog" — this is the
   command that actually calls the resolvers' `resolveGitCustom`/
   `resolveLocalFolder`, distinct from 07.1's registry-only
   `reloadRegistry`).
2. Create `src/ui/availableView.ts`:
   - Resolve **once per explicit `refreshCatalog` invocation** (and once
     on initial view load), cache the result in the provider instance,
     and serve tree expansion from that cache — do not re-resolve on
     every expand. Show a `vscode.window.withProgress` indicator while
     `refreshCatalog` runs, since a `git-custom` source involves a real
     network fetch.
   - Two-level tree: top = one node per `Source`; children = the
     `Artifact`s its cached resolution currently holds. Leaf items:
     `artifact.name` + `artifact.kind`, `contextValue: 'artifact'`.
   - If a source's resolution failed (auth error, network error, invalid
     local path), show a single child node under it with the error
     message rather than silently showing no children — the second
     review specifically flagged silent-empty-catalog as a risk to
     avoid.
3. Implement `aiSwissknife.install`:
   - Only offer this command (via `when: "viewItem == artifact"` in
     `contributes.menus["view/item/context"]`) — no change needed beyond
     what's already planned, but confirm it's still wired that way.
   - Prompt for target assistant (`claude-code`/`kilo-code`) and target
     scope (reuse 07.1's multi-root-aware project-folder picker — don't
     duplicate that logic, factor it into a small shared helper both
     views import if it doesn't already live somewhere shared).
   - Call `planInstall` (06.1). If `plan.supported === false`, show why
     and stop (no further prompts).
   - **Show the full plan in the preview**, not just a path/diagnostic
     summary: every `PlannedFile` with its operation
     (create/replace) and, for `replace`, that it will overwrite
     existing content; the `overall` diagnostic and every
     non-`'lossless'` entry in `diagnostics`; `plan.sourceRevision`'s
     commit SHA if present. A single modal `showInformationMessage` with
     a multi-line body is acceptable for this Phase (no dedicated
     webview) — construct the message string with all of the above, not
     just a subset.
   - If `plan.conflict`, prompt for `conflictPolicy` (`showQuickPick`:
     "Overwrite"/"Skip") before calling `applyInstall` — the plan's
     `conflictPolicy` must not reach `apply` as `'undecided'`.
   - On `applyInstall`'s result: `'installed'` → success message +
     **fire a refresh on the Installed view (07.3)** so it doesn't show
     stale state (expose a small event emitter or a direct method call
     from `extension.ts`'s wiring — either is fine, state which you
     picked); `'refused'`/`'rolled-back'` → show the reason, don't treat
     either as a crash.
4. Same activation-verification discipline as prior tasks.

**Verification**: `npm run lint && npm run typecheck && npm run build`
all exit 0. One commit containing the `package.json` change,
`src/ui/availableView.ts`, and the command wiring — nothing else.
