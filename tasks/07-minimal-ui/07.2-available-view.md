# 07.2 — Available view (browse + install command) (revised again after multi-engine review round 001)

> Part of [Minimal UI](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · revised per [../../SPEC.md](../../SPEC.md) §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) findings B1, I3, I4 · **superseded once more after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decision 12). Depends on `06.1`/`06.2`'s revised `PreparedInstall`/`ApplyOutcome` shapes — read those files' current versions first, not any earlier one.

**This supersedes an earlier version of this task file.** Corrections:
resolving on every tree expand (rather than an explicit refresh) fetches
over the network on every UI interaction; the preview step didn't show
the full plan (file list, diagnostics, resolved commit) the revised
`InstallPlan` (06.1) now actually has; the install flow needs to
refresh the Installed view (07.3) afterward, which didn't exist as a
stated requirement before; and — per round 001's decision 12 — the
previous version's preview was a plain informational toast that didn't
actually gate progress: for a no-conflict install it showed the summary
and then applied unconditionally, with no way to back out once you'd
seen the plan. This version makes approval explicit for every install,
not just conflicting ones.

**Goal**: a tree view listing `Artifact`s resolved from all registered
`Source`s via an explicit "Refresh Catalog" action (not fetch-on-expand),
with a full-detail preview and an explicit Install/Cancel approval gate
before any write happens — never applying on the strength of a dismissed
toast.

**Grounding**: `src/install/plan.ts`'s `PreparedInstall`/`InstallPlan` and
`src/install/apply.ts`'s `applyInstall`/`ApplyOutcome`/`ConflictPolicy`
(06.1/06.2, revised) for the pipeline; `src/sources/localFolder.ts`/
`gitCustom.ts`'s `resolveArtifactContent` (02.3) for fetching real
content; `src/ui/sourcesView.ts` (07.1) for the established
registry-backed `TreeDataProvider` pattern in this codebase.

Steps:

1. Add to `package.json`'s `contributes.views["ai-swissknife"]`:
   `{ "id": "aiSwissknife.available", "name": "Available" }`; to
   `contributes.commands`: `aiSwissknife.install` (title "Install") and
   `aiSwissknife.refreshCatalog` (title "Refresh Catalog" — this is the
   command that actually calls the resolvers' `resolveGitCustom`/
   `resolveLocalFolder`, distinct from 07.1's registry-only
   `reloadRegistry`).
2. Create `src/ui/availableView.ts`:
   - Resolve **once per explicit `refreshCatalog` invocation** (and once
     on initial view load), cache the result in the provider instance,
     and serve tree expansion from that cache — do not re-resolve on
     every expand. Show a `vscode.window.withProgress` indicator while
     `refreshCatalog` runs, since a `git-custom` source involves a real
     network fetch.
   - Two-level tree: top = one node per `Source`; children = the
     `Artifact`s its cached resolution currently holds. Leaf items:
     `artifact.name` + `artifact.kind`, `contextValue: 'artifact'`.
   - If a source's resolution failed (auth error, network error, invalid
     local path), show a single child node under it with the error
     message rather than silently showing no children — the second
     review specifically flagged silent-empty-catalog as a risk to
     avoid.
3. Implement `aiSwissknife.install`:
   - Only offer this command (via `when: "viewItem == artifact"` in
     `contributes.menus["view/item/context"]`) — no change needed beyond
     what's already planned, but confirm it's still wired that way.
   - Prompt for target assistant (`claude-code`/`kilo-code`) and target
     scope (reuse 07.1's multi-root-aware project-folder picker — don't
     duplicate that logic, factor it into a small shared helper both
     views import if it doesn't already live somewhere shared).
   - Call `planInstall` (06.1), which now returns a `PreparedInstall`
     (`{plan, content, contentHash}`) — keep the whole object, don't
     unpack just `plan`; `applyInstall` (06.2) needs the exact same
     `PreparedInstall` back, not a re-derived one. If `plan.supported ===
     false`, show `plan.unsupportedReason` and stop (no further prompts).
   - **Show the full plan in the preview**, not just a path/diagnostic
     summary: every `PlannedFile` with its operation
     (create/replace) and, for `replace`, that it will overwrite
     existing content; the `overall` diagnostic and every
     non-`'lossless'` entry in `diagnostics`; `plan.sourceRevision`'s
     commit SHA if present. Construct one multi-line message string with
     all of the above, not just a subset.
   - **Explicit approval gate — per round 001's decision 12, this
     applies to every install, not only conflicting ones.** Show that
     message via `showInformationMessage(message, {modal: true},
     'Install', 'Cancel')` and only continue if the user picks
     `'Install'`. Any other outcome (`'Cancel'`, or the modal dismissed
     with Escape/click-outside, both of which resolve to `undefined`) —
     stop, touch nothing, no `applyInstall` call. This replaces the
     previous version's plain toast, which showed the plan but applied
     unconditionally afterward for the no-conflict case; there must now
     be no path from "preview shown" to "files written" that doesn't
     pass through this explicit choice.
   - If `plan.conflict`, after the Install/Cancel gate above, prompt for
     `conflictPolicy` (`showQuickPick`: "Overwrite"/"Skip") before
     calling `applyInstall` — the plan's `conflictPolicy` must not reach
     `apply` as `'undecided'`. When there's no conflict, `applyInstall`
     still needs a `conflictPolicy` argument per its `06.2` signature;
     pass `'overwrite'` (it's inert with no conflict — `apply`'s step
     2.1/2.2 only branch on it when `plan.conflict` is true) rather than
     inventing a third value.
   - Call `applyInstall(prepared, conflictPolicy, targetAdapter)` (06.2's
     signature — takes the whole `PreparedInstall`, not a separately
     supplied `content`). On the result: `'installed'` → success message
     - **fire a refresh on the Installed view (07.3)** so it doesn't show
     stale state (expose a small event emitter or a direct method call
     from `extension.ts`'s wiring — either is fine, state which you
     picked); `'refused'` → show the reason, don't treat it as a crash;
     `'rolled-back'` → show the reason, make clear in the message that
     the destination was restored to what it was before; `'manual-
     recovery-required'` → show the reason **and** `backupPath` if
     present prominently (this is the one outcome that means something
     genuinely needs the user's attention afterward — don't phrase it
     like the other non-fatal outcomes).
4. Same activation-verification discipline as prior tasks.

**Verification**: `npm run lint && npm run typecheck && npm run build`
all exit 0. One commit containing the `package.json` change,
`src/ui/availableView.ts`, and the command wiring — nothing else.
