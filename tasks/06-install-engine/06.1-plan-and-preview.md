# 06.1 — Plan + preview

> Part of [Install engine](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md)

**Goal**: given a resolved `Artifact` (from an initiative 04 resolver) and
an install target, compute an `InstallPlan` describing exactly what would
happen — no filesystem writes.

**Grounding**: SPEC.md §2.4 "plan" bullet, and the `Adapter`/translator
interfaces from initiatives 03/05 — read both before writing this file,
this task is pure orchestration of already-built pieces, not new format
logic.

Steps:

1. Create `src/install/plan.ts`:
   ```ts
   import type { Artifact, AssistantId, Scope, ConversionDiagnostic } from '../domain/types';
   import type { Adapter } from '../adapters/types';

   export interface InstallPlan {
     artifactId: string;
     targetAssistant: AssistantId;
     targetScope: Scope;
     targetProjectRoot?: string;
     targetPath: string;
     conflict: boolean; // a file/dir already exists at targetPath
     diagnostic: ConversionDiagnostic;
     notes: string[];
   }

   export async function planInstall(
     artifact: Artifact,
     artifactContent: unknown, // the CanonicalSkill/CanonicalRule already resolved by the caller — see step 2 for why this isn't resolved here
     sourceAssistant: AssistantId,
     targetAdapter: Adapter,
     targetScope: Scope,
     targetProjectRoot?: string,
   ): Promise<InstallPlan>;
   ```
2. Design note to follow, not to second-guess: `planInstall` takes
   `artifactContent` already resolved (a `CanonicalSkill` or
   `CanonicalRule`, per `artifact.kind`) rather than re-reading it from
   the source itself — resolvers (initiative 04) already produce the
   `Package`/`Artifact` metadata, but actually *reading* a specific
   artifact's file content is a separate step this task doesn't own
   (that content-fetch responsibility can stay with whichever resolver
   produced the `Artifact`, or move into this function later — for this
   task, accept it as a parameter and don't add a new file-reading
   code path here; note in your report if this seams awkward, but
   implement it as specified rather than redesigning the boundary
   unilaterally).
3. Implementation:
   - Compute `targetPath` via `targetAdapter.skillPath(...)` or
     `.rulePath(...)` depending on `artifact.kind` (only these two kinds
     exist in Phase 1, per every prior initiative's shared decisions —
     throw a clear error for any other `kind`, don't silently no-op).
   - `conflict`: check whether `targetPath` already exists (`fs.access`,
     catch `ENOENT` specifically to mean "no conflict", propagate any
     other error).
   - `diagnostic`/`notes`: call `translateSkill`/`translateRule`
     (initiative 05) with `sourceAssistant` and `targetAdapter.assistant`,
     take its `diagnostic`/`notes` as-is — this function doesn't compute
     its own diagnostic, it delegates to the translator.
4. Write `src/install/plan.test.ts`:
   - No conflict: a `CanonicalSkill` targeting a path that doesn't exist
     yet in a temp dir produces `conflict: false`.
   - Conflict: pre-create a file at the target path, confirm
     `conflict: true`, and confirm `planInstall` did **not** modify or
     delete that pre-existing file (read it back, assert unchanged) —
     this is the core "plan never writes" guarantee, test it directly,
     not just by absence of an obvious write call in the code.
   - `diagnostic` reflects whatever the translator returned for a given
     same-assistant vs cross-assistant call (reuse initiative 05's test
     fixtures rather than inventing new ones).

**Verification**: the test file passes, in particular the "plan doesn't
write" conflict-case assertion; `npm run lint && npm run typecheck &&
npm run build` all exit 0. One commit containing `src/install/plan.ts`
and `src/install/plan.test.ts` — nothing else.
