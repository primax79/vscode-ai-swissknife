# 06.1 — Plan + preview (revised again after multi-engine review round 001)

> Part of [Install engine](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · revised per [../../SPEC.md](../../SPEC.md) §7 · **superseded once more after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decisions 2, 4, 5, 7) — three independent engines reviewed the *previous* version of this file (itself already a rewrite) before any of it was implemented, and found it still didn't compose with the real adapter/domain code. This version folds in every one of their blocking findings against this file. **Do not delegate any earlier version of this task.**

**Goal**: given a resolved `Source`+`Package`+`Artifact`, compute a
complete, self-contained `PreparedInstall` — every file that would be
created/modified, conflicts, provenance, and diagnostics — with no
filesystem writes, and with enough information that `applyInstall`
(06.2) never has to re-derive or re-fetch anything.

**Grounding**: read `src/domain/types.ts` (`Source`, `ResolvedArtifact`,
`ResolvedRevision` from 02.3), `src/adapters/types.ts` (`Adapter.
skillDir()`, `CanonicalSkill` with `files: ArtifactFile[]`,
`FieldDiagnostic`/`TranslationResult` from 03.4/05.2), and
`resolveArtifactContent` in both `src/sources/localFolder.ts` and
`src/sources/gitCustom.ts` (02.3) before writing this file.

Steps:

1. Create `src/install/plan.ts`:

   ```ts
   import type { Source, Package, Artifact, AssistantId, Scope, ResolvedRevision } from '../domain/types';
   import type { Adapter, CanonicalSkill, FieldDiagnostic } from '../adapters/types';
   import type { ConversionDiagnostic } from '../domain/types';

   export type FileOperation = 'create' | 'replace';

   export interface PlannedFile {
     relativePath: string; // relative to the artifact's own root (e.g. "SKILL.md", "scripts/run.sh")
     operation: FileOperation;
     existingContentHash?: string; // set when operation === 'replace'
   }

   export interface InstallPlan {
     sourceId: string;
     packageId: string;
     artifactId: string;
     artifactKind: Artifact['kind'];
     artifactName: string;
     sourceRevision?: ResolvedRevision;
     targetAssistant: AssistantId;
     targetScope: Scope;
     targetProjectRoot?: string;
     targetDir: string; // the skill's directory on the target side — from Adapter.skillDir(), NEVER skillPath()
     files: PlannedFile[];
     conflict: boolean; // true if targetDir already exists in any form
     uncoveredExistingFiles: string[]; // relative paths that exist under targetDir today but aren't in `files` — non-empty means apply() must refuse an overwrite (see 06.2)
     diagnostics: FieldDiagnostic[];
     overall: ConversionDiagnostic;
     supported: boolean; // false if artifactKind has no adapter support yet, or a name/path failed validation
     unsupportedReason?: string;
   }

   export interface PreparedInstall {
     plan: InstallPlan;
     content: CanonicalSkill; // the exact translated content the plan's diagnostics were computed from — applyInstall receives this unchanged, never a separately-supplied value
     contentHash: string; // sha256 over the canonical content (name/description/body/extraFields/files, in a stable order)
   }

   export async function planInstall(
     source: Source,
     pkg: Package,
     artifact: Artifact,
     targetAdapter: Adapter,
     targetScope: Scope,
     targetProjectRoot?: string,
   ): Promise<PreparedInstall>;
   ```

   Note what changed from the previous version, and why (per round 001):
   `sourceAssistant` is gone — there was never a real source of truth for
   it (decision 4); `targetRootPath` is renamed `targetDir` and is now
   computed via `Adapter.skillDir()`, never `skillPath()` (decision 1,
   already fixed in 03.4 — this task just uses the corrected method);
   the function now takes `source: Source` so it can dispatch to the
   right resolver (decision 5); the return type is `PreparedInstall`,
   not a bare `InstallPlan`, so the content used to compute diagnostics
   is provably the same content `applyInstall` will write (decision 2);
   `InstallPlan` gained `sourceId`/`packageId`/`artifactName` so
   `applyInstall` can build a complete `ManagedInstallation` without
   needing anything re-passed in (decision 2); `uncoveredExistingFiles`
   is new, closing the "overwrite silently deletes files" data-loss path
   (decision 7).

2. Implementation:
   - Only `artifact.kind === 'skill'` is `supported: true` in this Phase
     — for any other kind, return a `PreparedInstall` whose `plan.
     supported` is `false` with `unsupportedReason` set, rather than
     throwing. (`content`/`contentHash` can be dummy/empty values in
     this case — document that callers must check `supported` before
     using them.)
   - **Dispatch to the right resolver via `source.type`**: call
     `resolveArtifactContent` from `src/sources/localFolder.ts` when
     `source.type === 'local-folder'`, or from `src/sources/
     gitCustom.ts` when `source.type === 'git-custom'` — throw a clear
     internal error for any other `source.type` (none are supported in
     Phase 1's resolvers yet, so reaching this means a caller passed an
     unsupported `Source`, which is a caller bug, not a normal
     `supported: false` case).
   - Call `translateSkill(content, targetAdapter.assistant)` (05.2's
     revised two-argument signature — no `fromAssistant`) to get
     `diagnostics`/`overall`. Store the exact `CanonicalSkill` this call
     was given as `PreparedInstall.content` — this is the value
     `applyInstall` will receive back unchanged.
   - Validate `content.name` via `validateSkillName` and each
     `content.files[].relativePath` via `validateRelativeFilePath`
     (both from 03.4) **before** building any `PlannedFile` — a
     validation failure produces `supported: false` with a diagnostic
     explaining why, not a thrown exception.
   - `targetDir = targetAdapter.skillDir(content.name, {scope:
     targetScope, projectRoot: targetProjectRoot})`.
   - `conflict`: does `targetDir` exist at all (`fs.access`, `ENOENT` ⇒
     no conflict, any other error propagates).
   - Build `files`: one `PlannedFile` for `SKILL.md` plus one per entry
     in `content.files`, each `relativePath` relative to `targetDir`.
     For each, check existence on disk under `targetDir`;
     `operation: 'replace'` + a real `existingContentHash` if present,
     `'create'` otherwise.
   - **Build `uncoveredExistingFiles`**: if `conflict` is true, list
     every file that actually exists under `targetDir` today (recursive
     walk) whose relative path is **not** one of `files`' relative
     paths. A non-empty result means `06.2` must refuse to overwrite
     (Phase 1 does not implement partial removal or a full tree diff —
     an uncovered file is a hard stop, not a warning).
   - Compute `contentHash` as `sha256` over a stable serialization of
     `content` (e.g. JSON-stringify with sorted keys, `files` sorted by
     `relativePath`, buffers hashed individually then combined — pick
     one concrete, deterministic scheme and document it in a code
     comment, since `06.2` and any later drift-detection code must be
     able to recompute the same hash from the same content).

3. Write `src/install/plan.test.ts`:
   - No conflict: `PreparedInstall.plan.conflict === false`, every file
     `'create'`, `uncoveredExistingFiles` empty.
   - Conflict, fully covered: pre-create the target dir with exactly the
     files the new payload will also write (different content),
     confirm `conflict: true`, `'replace'` with real hashes,
     `uncoveredExistingFiles` empty, and — the core "plan never
     writes" guarantee — the pre-existing files are byte-identical
     after `planInstall` returns.
   - Conflict, uncovered file: pre-create the target dir with an *extra*
     file the new payload doesn't mention (e.g. `user-notes.md`),
     confirm it appears in `uncoveredExistingFiles`.
   - Unsupported kind: an `Artifact` with `kind: 'agent'` produces
     `plan.supported === false`, doesn't throw.
   - A malicious `content.files[].relativePath` (e.g. `"../../evil"` or
     an absolute path) produces `plan.supported === false` with a
     diagnostic naming the rejected path — no `PlannedFile` with that
     path is ever built.
   - Resolver dispatch: a `Source` with `type: 'local-folder'` and one
     with `type: 'git-custom'` (using `gitCustom.test.ts`'s existing
     real-repo fixture) both produce a correct `PreparedInstall` via the
     same `planInstall` call, proving the dispatch in step 2 actually
     routes to the right resolver.
