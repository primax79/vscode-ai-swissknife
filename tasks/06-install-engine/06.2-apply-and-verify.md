# 06.2 — Transactional apply + verify (revised again after multi-engine review round 001)

> Part of [Install engine](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · revised per [../../SPEC.md](../../SPEC.md) §7 · **superseded once more after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decisions 2, 7, 8). Depends on `06.1`'s revised `PreparedInstall`/`InstallPlan` shape — read that file's current version first, not any earlier one.

**Goal**: given a `PreparedInstall` (06.1) the user has approved (with a
decided conflict policy), materialize it as an atomic, recoverable
operation, and record it accurately — never claiming `'rolled-back'`
when the destination wasn't actually restored, and never silently
deleting a file the plan didn't cover.

**Grounding**: `src/domain/registry.ts`'s `statePath`/`readState`/
`writeState` (02.3).

Steps:

1. Create `src/install/apply.ts`:

   ```ts
   import type { PreparedInstall } from './plan';
   import type { Adapter } from '../adapters/types';
   import type { ManagedInstallation } from '../domain/types';

   export type ConflictPolicy = 'overwrite' | 'skip';

   export type ApplyOutcome =
     | { status: 'installed'; installation: ManagedInstallation }
     | { status: 'rolled-back'; reason: string } // destination genuinely restored to its pre-apply state
     | { status: 'manual-recovery-required'; reason: string; backupPath?: string } // swap succeeded but a LATER step failed — destination is NOT what it was before, and not fully installed either
     | { status: 'refused'; reason: string }; // nothing was touched

   export async function applyInstall(
     prepared: PreparedInstall,
     conflictPolicy: ConflictPolicy,
     targetAdapter: Adapter,
   ): Promise<ApplyOutcome>;
   ```

   Note what changed from the previous version (per round 001): this
   takes the whole `PreparedInstall` from `06.1`, not a separately
   supplied `content: CanonicalSkill` — there is now exactly one place
   `content` comes from, closing the "plan and apply don't share a
   proven payload" gap (decision 2). `ApplyOutcome` gained
   `'manual-recovery-required'`, because the previous version's
   `'rolled-back'` was sometimes a lie (decision 8) — see step 2.7.
   `conflictPolicy` no longer includes `'merge'` (never implemented,
   don't half-implement it) or `'undecided'` as a value `apply` accepts
   — the caller must have already decided by the time it calls this
   function; that decision now happens in `07.2`, not here.

2. Implementation — the staged-transaction sequence, in order, each step
   guarded so a failure anywhere triggers cleanup and returns the
   *honest* outcome for that failure point, not a generic one:

   1. **Refuse up front** if `prepared.plan.supported === false`, or if
      `prepared.plan.conflict && prepared.plan.uncoveredExistingFiles.
      length > 0` regardless of `conflictPolicy` — **this is the
      data-loss fix from round 001 (decision 7)**: Phase 1 does not
      implement partial removal or a full tree diff, so an existing file
      the new payload doesn't cover must always block the overwrite,
      not just when the caller happens to pick `'skip'`. Return
      `{status: 'refused', reason}` — nothing touched.
   2. If `prepared.plan.conflict && conflictPolicy === 'skip'`: return
      `{status: 'refused', reason: 'skipped by conflict policy'}` —
      nothing touched.
   3. **Precondition re-check**: re-read the current state of
      `prepared.plan.targetDir` and compare against what the plan
      recorded (`PlannedFile.existingContentHash`, or "didn't exist").
      If it changed since `planInstall` ran, return `{status: 'refused',
      reason: 'target changed since preview'}`.
   4. **Stage**: write every `PlannedFile` (`SKILL.md` via
      `serializeSkillMarkdown`, plus `prepared.content.files`) into a
      sibling temporary directory next to `prepared.plan.targetDir`
      (e.g. `<parent>/.ai-swissknife-staging-<random>/`), validating
      each path again with `validateRelativeFilePath` (03.4) as defense
      in depth.
   5. **Verify the staged copy**: re-read every staged file back and
      confirm it matches what was written (hash comparison).
   6. If `prepared.plan.conflict` (and, by step 2.1, it's therefore
      fully covered — no uncovered files): move the existing
      `targetDir` to a backup path (e.g. append
      `.ai-swissknife-backup-<random>`) rather than deleting it yet.
   7. **Atomic swap**: `fs.rename()` the staged directory into
      `prepared.plan.targetDir`.
   8. **Verify the final location**: re-read via `targetAdapter.
      readSkill(...)` at the real path and confirm it matches
      `prepared.content` (compare `files` as a map keyed by
      `relativePath`, not by array order — array order from a directory
      walk isn't guaranteed to be stable). **On failure here**:
      - If a backup exists (step 6 ran): attempt to restore it by
        renaming the failed new directory aside and the backup back
        into place. If that restoration itself succeeds, return
        `{status: 'rolled-back', reason}` — this is the only case
        allowed to use that status. If the restoration itself fails,
        return `{status: 'manual-recovery-required', reason, backupPath}`
        — say exactly where the backup is.
      - If no backup exists (fresh install, no prior conflict): remove
        the newly-written `targetDir` entirely, then return
        `{status: 'rolled-back', reason}`.
   9. **Persist state**: compute `contentHash` (reuse `06.1`'s scheme —
      import the same hashing function rather than reimplementing it),
      build the `ManagedInstallation` record from `prepared.plan`
      directly (`sourceId`/`packageId`/`artifactId`/`artifactName`/
      `sourceRevision` are all already on `InstallPlan` per `06.1`'s
      revision — no additional parameters needed), `installedAt = new
      Date().toISOString()`, then read-modify-write the state file
      (`readState`/`writeState`, 02.3) for the correct scope, replacing
      any existing entry with the same `(assistant, scope, projectPath,
      kind, name)` key.
   10. **On state-write failure**: the swap already succeeded — the new
       content is genuinely live on disk, but the registry doesn't know
       about it, and (if this was an overwrite) the backup is still
       sitting there. **This is not a rollback — don't call it one.**
       Return `{status: 'manual-recovery-required', reason: 'installed
       content is live but the registry state write failed', backupPath}`
       (or `backupPath: undefined` if this was a fresh install with no
       backup). This is the exact case round 001 found mislabeled as
       `'rolled-back'` in the previous version of this task.
   11. Only after the state write succeeds (step 9), remove the backup
       from step 6 if one was made. If backup removal itself fails,
       the installation is still `{status: 'installed'}` — a leftover
       backup directory is a cleanup nuisance, not a correctness
       problem; note it in your report if you hit this case in testing.

3. Write `src/install/apply.test.ts` against temp directories and a temp
   state file (never real `~/.ai-swissknife/` or a real assistant config
   dir):
   - Happy path, no conflict: file exists at the expected path with
     expected content including a supporting file, `{status:
     'installed'}`, state file has exactly one matching
     `ManagedInstallation` with a non-empty `contentHash` and the
     correct `sourceId`/`packageId`/`sourceRevision` carried through
     from the plan.
   - Reinstall, `overwrite`, fully covered: apply twice with different
     (but fully-covering) content, confirm exactly one state entry
     (replaced, not duplicated) and the backup was cleaned up.
   - Uncovered existing file: confirm `applyInstall` returns `{status:
     'refused'}` **regardless of `conflictPolicy`** when
     `prepared.plan.uncoveredExistingFiles` is non-empty, and that the
     pre-existing files are untouched.
   - `conflictPolicy: 'skip'` on a real, fully-covered conflict: returns
     `{status: 'refused'}`, target directory's original content
     untouched.
   - Precondition failure: mutate the target on disk between
     `planInstall` and `applyInstall`, confirm `{status: 'refused'}`
     and nothing was staged/swapped.
   - Post-swap verification failure, **with** a prior backup: use a test
     double for `targetAdapter.readSkill` that returns mismatched
     content for just this one call; confirm the backup is restored,
     final on-disk state matches what was there before `apply` ran, and
     `{status: 'rolled-back'}` is returned.
   - Post-swap verification failure, **without** a prior backup (fresh
     install): same test-double approach; confirm the newly-written
     directory is removed entirely and `{status: 'rolled-back'}` is
     returned (not `'manual-recovery-required'` — there was nothing to
     half-recover, a clean removal is a full rollback).
   - State-write failure: use a test double/injected failure for the
     state-file write; confirm the on-disk content is left live (**not**
     rolled back), the function returns `{status:
     'manual-recovery-required'}` with a `reason` that says the content
     is live but unregistered, and (if this was an overwrite) the
     backup path is reported in the outcome.

**Verification**: the test file passes, especially the uncovered-file
refusal and the two distinct rollback/manual-recovery cases; `npm run
lint && npm run typecheck && npm run build && npm test` all exit 0. One
commit containing `src/install/apply.ts` and `src/install/apply.test.ts`
— nothing else. After this commit, update `tasks/00-INDEX.md`'s row for
initiative `06` to `✅ done`.
