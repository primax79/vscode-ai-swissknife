# 06.2 — Transactional apply + verify (revised)

> Part of [Install engine](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · revised per [../../SPEC.md](../../SPEC.md) §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) finding B4

**This supersedes an earlier version of this task file**, which called
the adapter's `writeSkill` directly (not atomic for a multi-file skill)
and could record a `ManagedInstallation` even when verification failed.

**Goal**: given an `InstallPlan` (06.1, revised) the user has approved
(with a decided `conflictPolicy`), materialize it as an atomic,
recoverable operation: stage the full artifact in a sibling temp
directory, verify the staged copy, atomically swap it into place, persist
state, and roll back cleanly on any failure at any step.

**Grounding**: `src/domain/registry.ts`'s `manifestPath`/`statePath`/
`readState`/`writeState` (from 02.3) — this task appends to the state
file, never the manifest (installations are machine-local, per 02.3's
split).

Steps:

1. Create `src/install/apply.ts`:

   ```ts
   import type { InstallPlan } from './plan';
   import type { Adapter, CanonicalSkill } from '../adapters/types';
   import type { ManagedInstallation } from '../domain/types';

   export type ApplyOutcome =
     | { status: 'installed'; installation: ManagedInstallation }
     | { status: 'rolled-back'; reason: string }
     | { status: 'refused'; reason: string }; // e.g. conflictPolicy undecided, or a precondition check failed

   export async function applyInstall(
     plan: InstallPlan,
     content: CanonicalSkill,
     targetAdapter: Adapter,
   ): Promise<ApplyOutcome>;
   ```

2. Implementation — the staged-transaction sequence, in order, each step
   guarded so a failure anywhere triggers cleanup of whatever the
   previous steps created and returns `{status: 'rolled-back', reason}`
   rather than throwing out of this function:
   1. **Refuse up front** if `plan.conflictPolicy === 'undecided'` while
      `plan.conflict` is true, or if `plan.supported === false` — return
      `{status: 'refused', reason}` immediately, no filesystem touched.
   2. **Precondition re-check**: re-read the current state of
      `plan.targetRootPath` and compare against what `plan` recorded at
      plan time (each `PlannedFile.existingContentHash`, or "didn't
      exist" for `create`). If it changed since `planInstall` ran (a
      time-of-check/time-of-use gap), return `{status: 'refused', reason:
      'target changed since preview'}` — do not proceed and do not
      silently overwrite an unexpected change.
   3. **Stage**: write every `PlannedFile` (SKILL.md + `content.files`)
      into a sibling temporary directory next to `plan.targetRootPath`
      (e.g. `<parent>/.ai-swissknife-staging-<random>/`), validating each
      path again with `validateRelativeFilePath` (03.4) as a defense in
      depth even though 06.1 already validated at plan time.
   4. **Verify the staged copy**: re-read every staged file back and
      confirm it matches what was written (hash comparison) — this is
      distinct from re-reading the *final* location, which happens after
      the swap in step 6.
   5. If `plan.conflict` and `plan.conflictPolicy === 'overwrite'`: move
      the existing `plan.targetRootPath` to a backup path (e.g. append
      `.ai-swissknife-backup-<random>`) rather than deleting it yet. If
      `conflictPolicy === 'skip'`: return `{status: 'refused', reason:
      'skipped by conflict policy'}` before any swap. `'merge'` is not
      implemented in this Phase — treat it the same as `'skip'` with a
      reason noting merge isn't supported yet, don't attempt a partial
      merge.
   6. **Atomic swap**: `fs.rename()` the staged directory into
      `plan.targetRootPath`. On most filesystems this is atomic for a
      directory rename within the same volume — if the staging dir and
      target aren't guaranteed to be on the same filesystem, note this
      as a known limitation in your report rather than silently assuming
      it.
   7. **Verify the final location**: re-read via
      `targetAdapter.readSkill(...)` at the real path and confirm it
      matches `content`. If this fails **after** the swap already
      happened, attempt to restore the backup from step 5 (if one was
      made) and return `{status: 'rolled-back', reason}` — do not return
      `{status: 'installed'}` and do not persist state in this case.
   8. **Persist state**: compute a `contentHash` over the canonical
      content, build the `ManagedInstallation` record (including
      `sourceId`/`packageId`/`artifactId` from `plan`/the resolved
      `Package`/`Artifact`, `plan.sourceRevision`, `installedAt`), and
      append/replace it in the state file (`readState`/`writeState` from
      02.3, read-modify-write keyed on `(assistant, scope, projectPath,
      kind, name)` — replace an existing entry for a reinstall, don't
      duplicate).
   9. Only **after** the state write succeeds, remove the backup from
      step 5 (if any). If the state write itself fails, leave the backup
      in place (the swap already succeeded, so the new content IS live;
      losing the backup here is a lesser issue than losing the pre-swap
      content would have been — note this ordering rationale in your
      report so a reviewer doesn't "fix" it backwards).
3. Write `src/install/apply.test.ts` against temp directories and a temp
   state file (never real `~/.ai-swissknife/` or a real assistant config
   dir):
   - Happy path (no conflict): file exists at the expected path with
     expected content including a supporting file from `content.files`,
     `status: 'installed'`, state file has exactly one matching
     `ManagedInstallation` with a non-empty `contentHash`.
   - Reinstall (conflict + `overwrite`): apply twice with different
     content, confirm exactly one state entry (updated, not duplicated),
     and the backup from the first apply was cleaned up.
   - `conflictPolicy: 'skip'` on a real conflict: returns `{status:
     'refused'}`, target directory's original content is untouched.
   - Precondition failure: after `planInstall` runs but before `apply`,
     mutate the target on disk, then call `applyInstall` with the
     now-stale plan — confirm `{status: 'refused'}` and nothing was
     staged/swapped.
   - Simulated post-swap verification failure: this is the hardest case
     to construct honestly — e.g. by making `targetAdapter.readSkill`
     throw or return mismatched content via a test double for just this
     one call — confirm the pre-existing backup is restored and the
     final state matches what was there **before** `apply` ran, and that
     `status: 'rolled-back'` is returned, not `'installed'`.

**Verification**: the test file passes, especially the precondition and
rollback cases; `npm run lint && npm run typecheck && npm run build` all
exit 0. One commit containing `src/install/apply.ts` and
`src/install/apply.test.ts` — nothing else. After this commit, update
`tasks/00-INDEX.md`'s row for initiative `06` to `✅ done`.
