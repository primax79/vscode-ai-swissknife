# 06.2 — Integrity-bound transactional apply and recovery

> Part of [Install engine](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · accepted review decisions: [round 001](../_reviews/001-hardening-gate-SUMMARY.md) and [round 002](../_reviews/002-hardening-gate-SUMMARY.md), especially decisions 2, 9, 10, 11, and 16. Requires 06.1.

## Goal

Apply exactly the payload that was previewed, only if the complete target tree is unchanged, using a staged directory swap with truthful recovery outcomes and state persistence only after verified success.

This task must produce one commit containing only its changes.

## Contract

```ts
export type ApplyOutcome =
  | { status: 'applied'; installation: ManagedInstallation; warnings?: string[] }
  | { status: 'refused'; reason: string }
  | { status: 'rolled-back'; reason: string }
  | { status: 'manual-recovery-required'; reason: string; paths: string[] };

export function applyInstall(prepared: PreparedInstall): Promise<ApplyOutcome>;
```

`rolled-back` means the pre-apply filesystem state was **proven** restored (including “target absent” for a fresh install). If restoration cannot be proven, return `manual-recovery-required`; never report an optimistic rollback.

## Steps

1. Before any filesystem mutation:

   - Refuse the unsupported `PreparedInstall` branch.
   - Recompute `canonicalSkillHash(prepared.content)` and compare it to `prepared.contentHash`. Refuse on mismatch; this catches mutation after preview.
   - `lstat` the target with the same rules as 06.1. Do not follow symlinks. Refuse any non-directory/unreadable target state.
   - Re-walk the **entire** current target directory and compare its exact normalized file set and every content hash with `prepared.plan.existingFiles`. Refuse if a file changed, disappeared, or appeared after preview, even if it is not one of the proposed paths.
   - Refuse (no mutation) if the explicit uncovered-files set from preview is non-empty. This is separate from the full-tree revalidation above.

   Every refusal here touches neither target, staging, backup, nor state.

2. Create sibling staging and backup paths with unique names in the target parent. Stage the complete translated payload: deterministic `SKILL.md`, then each `prepared.content.files` entry. Create parents, write bytes, and apply every defined file `mode` with `chmod`. Use the shared path-safety rules and do not follow symlinks.

3. Read the staged directory back through the shared codec. Verify canonical equality and `canonicalSkillHash === prepared.contentHash`. If staging/write/chmod/verification fails before the target is touched, remove staging and return `refused` only when cleanup is proven. If staging residue cannot be removed, return `manual-recovery-required` with its path.

4. Swap transactionally:

   - Existing install: rename target → backup, then staging → target.
   - Fresh install: rename staging → target; no fake backup exists.

   If moving target to backup fails, inspect the filesystem. Return `refused` only if target is proven unchanged and no backup/staging residue remains; otherwise return `manual-recovery-required` with every relevant path.

   If staging → target fails after backup exists, restore backup → target and verify the complete original snapshot. Require removing the orphaned staging directory and proving its absence before returning `rolled-back`; if that cleanup cannot be proven, return `manual-recovery-required` with the staging path instead.

5. Read and verify the final target against `prepared.content` and `prepared.contentHash` using canonical equality (a normalized relative-path map of {content, mode} compared independent of traversal/array order). On mismatch, attempt recovery: quarantine/remove the new target before restoring and verifying backup for an existing install, or remove the new target and prove absence for a fresh install. Report `rolled-back` only when proven; otherwise `manual-recovery-required` with the relevant paths.

6. Persist `ManagedInstallation` with source/package/artifact/assistant/scope/target metadata, `sourceRevision: prepared.plan.sourceRevision`, and **exactly** `contentHash: prepared.contentHash`. Do not recompute or replace the approved hash. Write state atomically via 02.3; read the existing scoped StateFile, replace only the record matching a stable key (at minimum assistant + scope/project root + target path), and preserve every other record. Never write a StateFile containing only the new installation. Never write the manifest.

   If state persistence fails, recover the filesystem to its prior state and verify it. Return `rolled-back` only on proof; otherwise manual recovery. A filesystem install without its state record is not `applied`.

7. Remove backup after final verification and successful state persistence. If backup cleanup alone fails, the installation remains `applied` because target and state are consistent; return an `applied` warning with the orphan backup path. Any cleanup failure that leaves the authoritative target/state ambiguous is `manual-recovery-required`.

## Failure matrix tests

Inject failures at each boundary and assert both outcome and disk/state:

- staging create/write/`chmod`/read-back;
- staging cleanup;
- target → backup rename;
- staging → target rename after backup;
- final verification;
- fresh-install target cleanup;
- state write;
- rollback restore and rollback verification;
- final backup cleanup.

## Verification

- Run the full test suite, typecheck, lint, and build.
- Mutate `prepared.content` after preview: apply returns `refused` before creating staging.
- Add an unrelated file after preview: full-tree revalidation refuses with no mutation.
- Verify executable mode survives staging and final swap.
- Test symlink/file/socket/unreadable target refusal without following or modifying it.
- For every injected failure, assert `refused`, `rolled-back`, or `manual-recovery-required` matches the proof rules above.
- A successful apply records `prepared.contentHash` and source revision, then leaves no staging/backup residue.
- Test state persistence: first install, installing a second distinct skill, reinstalling/updating the same target (no duplicate records, no unrelated-record loss).

## Non-goals

- No user prompt; task 07.2 owns approval.
- No merge strategy for conflicts; overwrite is an explicit UI policy.
- No cross-filesystem non-atomic fallback.
