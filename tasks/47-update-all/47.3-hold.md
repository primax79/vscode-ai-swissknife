# 47.3 — Hold an item out of Update all

One task, one commit. Depends on 47.1 (merged) and 47.2's summary dialog (extend it in the same PR if 47.2 is already merged, otherwise land the engine part first). Decided by the architect (AB-Q1, delegated by the owner, 2026-10-08).

**Read first:** `plan.md`, `src/engine/update.ts` (47.1), `src/domain/types.ts` (`ManagedInstallation`), `src/domain/registry.ts` (state schema/version and migration), `src/ui/installedView.ts` (context menu, `contextValue` strings), `src/ui/dashboard.ts` (rows and detail bar), `package.json` menus.

## Do

1. **State**: optional boolean `held` on `ManagedInstallation` (absent = false; no schema version bump needed if reads treat missing as false; if the state loader validates strictly, bump and migrate).
2. **Engine**: `planUpdateAll` puts held items in a new bucket `held` (never in `toUpdate`, even with `includeModified`); `setHeld(inst, boolean)` helper writing through the existing state write (under the 46.3 lock once merged).
3. **UI**: action "Hold" / "Release" (toggle) in the context menu of installed items (sidebar) and in the Dashboard detail bar and row overflow; a small pin icon on held rows (sidebar `description` suffix and Dashboard row marker, tooltip "Held: skipped by Update all"); the Update-all summary lists "N held" next to the skipped ones. Held items still update normally when the user updates that single item explicitly (the single Update action shows a one-line note: "This item is held").

## Verification

Engine tests: held outdated item never in `toUpdate` (also with `includeModified`), listed in `held`; toggle persists across a state reload; missing field behaves as not held. UI tests: context-menu entries per state, pin marker, summary text includes the held count, explicit single update still works. `npm test` green, `npm run build` clean.
