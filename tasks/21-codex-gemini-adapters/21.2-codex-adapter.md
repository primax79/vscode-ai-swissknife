# 21.2 — Codex CLI adapter

> Part of [Codex CLI & Gemini CLI adapters](plan.md) · spec: [../specs/phase-4-spec.md](../specs/phase-4-spec.md) §7

## Goal

Implement `src/adapters/codex.ts`: TOML parse/serialize for `agent` and
`mcp-server`, plain-markdown handling for `rule` (`AGENTS.md`, no
frontmatter), pass-through for `skill` (identical `SKILL.md` format, no
translation needed), and **read-only** handling for `command` (deprecated
upstream — for discovery/import only, never an install target).

This task must produce one commit containing only its changes.

## Grounding

- Field shapes per `SPEC.md` §1 Codex CLI column: `agent` is `.toml` in
  `agents/` with `name`/`description`/`developer_instructions`/model/
  reasoning/sandbox/mcp/skills — structurally different from every other
  assistant's frontmatter, not a renamed-fields case. `mcp-server` is
  `[mcp_servers.<id>]` in `config.toml` (stdio: command/args/env; http:
  url/bearer_token_env_var/auth). `rule` is `AGENTS.md` at root, plain
  markdown, no frontmatter. `command` is `prompts/*.md` with
  `$1..$9`/`$ARGUMENTS` placeholders, **deprecated** per `SPEC.md` §5.
- Adapter interface to implement: whatever shape `src/adapters/claude.ts`/
  `src/adapters/copilot.ts` already conform to (check for a shared
  `Adapter` interface from initiative 03.1, `src/adapters/types.ts` or a
  dedicated interface file, before inventing new method names).
- A TOML library is needed (none currently in `package.json` — check before
  adding; prefer a small, maintained one over hand-rolled parsing given
  Codex's non-trivial nested `[mcp_servers.<id>]` sections).

## Steps

1. Add TOML parse/serialize helpers (or a small dependency) and define the
   Codex-specific config shape needed for `agent`/`mcp-server`.
2. Implement `parseCodexAgentToml`/`serializeCodexAgentToml` mapping to/from
   `CanonicalAgent` — `sandbox`/`reasoning`/`developer_instructions` have no
   equivalent in `CanonicalAgent` today; store them in `extraFields` so a
   round-trip through another assistant doesn't silently drop them, and flag
   them in the translator (21.4) as the lossy fields they are.
3. Implement `parseCodexMcpToml`/`serializeCodexMcpToml` mapping to/from
   `CanonicalMcpServer`.
4. Implement `parseCodexRule`/`serializeCodexRule` (trivial passthrough,
   `AGENTS.md` maps directly to `CanonicalRule.content`).
5. Implement a Codex `command` **reader only** (for discovery/import), with
   no corresponding writer wired into the install engine — per the
   non-goal in `phase-4-spec.md` §2, Codex must never be offered as a
   `command` install target.
6. Add unit tests: TOML round-trip for `agent` and `mcp-server` (including
   the `extraFields` preservation of sandbox/reasoning), `AGENTS.md`
   passthrough, and a test confirming `command` is discoverable but not in
   the set of install-target kinds for `codex-cli`.

## Verification

- Run full test suite, lint, typecheck, build.
