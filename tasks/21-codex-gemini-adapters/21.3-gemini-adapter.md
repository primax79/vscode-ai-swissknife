# 21.3 — Gemini CLI adapter

> Part of [Codex CLI & Gemini CLI adapters](plan.md) · spec: [../specs/phase-4-spec.md](../specs/phase-4-spec.md) §7

## Goal

Implement `src/adapters/gemini.ts`: TOML `command` with the path→`:` name
mapping, hierarchical `rule` (`GEMINI.md`, global + project combine),
`mcp-server` via the `mcpServers` key in `settings.json`, pass-through
`skill` (identical `SKILL.md` format), and `agent` per **21.1**'s finding
(implement it if confirmed, or an explicit `unsupported` translator branch
if confirmed absent — do not guess independently of 21.1).

This task must produce one commit containing only its changes for the
non-`agent` parts; if 21.1 confirms a standalone `agent` format, its
implementation is a natural part of this same task (still one commit) —
if 21.1 finds no such format, skip it here and note that explicitly in the
commit rather than silently omitting it.

## Grounding

- Field shapes per `SPEC.md` §1 Gemini CLI column: `command` is a `.toml`
  file in `commands/`, name = path with `/`→`:` (e.g. `git/commit.toml` →
  `/git:commit`), `prompt`/`description` fields. `rule` is `GEMINI.md`,
  hierarchical (global + project combine — unlike Claude/Codex's
  single-file model, this adapter must merge both levels when reading, not
  just pick one). `mcp-server` is a `mcpServers` key in `settings.json`
  (global or project; **always wins over an mcp-server declared by an
  extension** — a precedence rule worth a comment where it's implemented,
  since it's non-obvious and easy to get backwards). `skill` is the same
  `SKILL.md` format, portable 1:1.
- Reuse the TOML helper introduced in 21.2 rather than adding a second TOML
  parsing path.

## Steps

1. Implement `parseGeminiCommandToml`/`serializeGeminiCommandToml` mapping
   to/from `CanonicalCommand`, including the path↔name `/`↔`:` conversion
   both directions.
2. Implement `parseGeminiRule`/`serializeGeminiRule` — reading combines
   global + project `GEMINI.md` (document how the two are combined, e.g.
   concatenation order, since "hierarchical" isn't further specified in
   `SPEC.md`); writing targets whichever scope the install/sync operation
   is actually targeting, not both at once.
3. Implement `parseGeminiMcpServer`/`writeGeminiMcpServer` against the
   `mcpServers` key in `settings.json`, preserving the rest of the file's
   content (this is a shared config file, same merge-care as the existing
   Claude/Kilo mcp-server adapters already exercise).
4. Per 21.1's finding: implement `agent` parse/serialize, or add a comment
   + translator-level `unsupported` branch (21.4) recording why it's absent.
5. Add unit tests: command name↔path mapping both directions, `GEMINI.md`
   hierarchical read combining a global + project fixture, `mcpServers`
   merge-write preserving unrelated `settings.json` keys.

## Verification

- Run full test suite, lint, typecheck, build.
