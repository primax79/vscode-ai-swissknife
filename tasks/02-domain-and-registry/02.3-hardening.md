# 02.3 — Persistence and resolved-artifact model (hardening)

> Part of [Domain types + registry store](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · hardening context: [../../SPEC.md](../../SPEC.md) §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) findings B1, B3, I2, I8, I13 · **revised after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decisions 3, 6, 9 — three independent engines reviewed this file's first draft before any of it was implemented; two found the same missing `ManagedInstallation` field, one found the registry split silently dropped desired installations)

**Goal**: close the data-model gaps a second review found before
initiative 06 (install engine) locks in a plan/apply contract on top of
them: artifacts need a way to fetch real content — bound to the exact
git revision they were listed at, not whatever's currently checked out
— the registry needs to stop mixing shareable and machine-local state
without dropping the shareable half of installation intent, and the
data directory needs its final name before any real user has data under
the old one.

**This is a revision of already-merged code** — `src/domain/types.ts` and
`src/domain/registry.ts` exist (initiatives 02.1/02.2). Read both in full
first. This task edits them; it does not replace them wholesale.

**Shares a file with task 04.3** (both edit `src/sources/gitCustom.ts`)
— land this task first; 04.3 depends on it now, not just on 02 generically.

Steps:

1. **Rename the data directory** `.ai-toolkit` → `.ai-swissknife`
   everywhere it appears in `src/domain/registry.ts` (`registryPath()`)
   and its tests, **and in `src/sources/gitCustom.ts`'s cache directory
   default** (`~/.ai-toolkit/cache/sources` → `~/.ai-swissknife/cache/
   sources`) — grep the whole `src/` tree for `ai-toolkit` first and fix
   every occurrence, not just the registry file (round 001 review found
   this scoped too narrowly the first time).
2. **Add `ResolvedRevision`** to `src/domain/types.ts`:

   ```ts
   export interface ResolvedRevision {
     requestedRef?: string; // what the Source asked for: a branch/tag name, or undefined for "default"
     commit: string; // the immutable resolved commit SHA
   }
   ```

   Change `Package.version` from `string | undefined` to
   `ResolvedRevision | undefined` — update every place that constructs a
   `Package` (`src/sources/localFolder.ts`, `src/sources/gitCustom.ts`)
   and every test that reads `.version`. For `local-folder` sources
   there's no git commit — leave `version` undefined there. For
   `git-custom`, run `git rev-parse HEAD` in the checkout after checkout
   and populate `commit` with the real SHA; `requestedRef` is whatever
   `source.commit`/`source.tag`/`source.branch` was (or undefined for
   "resolved the default branch").
3. **Also add `sourceRevision?: ResolvedRevision` to
   `ManagedInstallation`** in `src/domain/types.ts`, alongside the
   `Package.version` change above — two independent reviewers in round
   001 flagged that `06.2` (install engine, a later task) needs to
   persist the resolved revision into the installation record, but
   nothing added a field to receive it. Add it now while already
   touching this file, so `06.2` isn't blocked on a missing type.
4. **Add a content-resolution contract, bound to the exact resolved
   revision.** Add to `src/domain/types.ts`:

   ```ts
   export interface ResolvedArtifact<T = unknown> {
     artifact: Artifact;
     content: T; // a CanonicalSkill (or later CanonicalRule, etc.)
   }
   ```

   Then add one function per existing resolver:

   ```ts
   // src/sources/localFolder.ts
   export async function resolveArtifactContent(
     pkg: Package,
     artifact: Artifact,
   ): Promise<ResolvedArtifact>;

   // src/sources/gitCustom.ts
   export async function resolveArtifactContent(
     pkg: Package,
     artifact: Artifact,
     opts?: GitCustomResolveOptions, // same options shape resolveGitCustom takes — needed to find the right cache dir
   ): Promise<ResolvedArtifact>;
   ```

   For `localFolder.ts`: `findSkillDirs` already discovers the real
   absolute path of a skill directory, but `resolveLocalFolder` discards
   it when building the `Artifact`. Fix this at the source: retain the
   absolute path keyed by the `Artifact.id` you generate (an internal
   map maintained by the module, or a field threaded through — your
   choice), so `resolveArtifactContent` can look it up and actually read
   the file.
   For `gitCustom.ts`, **this is the part round 001 flagged as a real
   correctness bug, not just an ergonomics gap**: `resolveGitCustom`'s
   checkout is mutable — if the module just remembers "the last checkout
   path" and reads from it later, a second `resolveGitCustom` call
   (e.g. a catalog refresh) can move that same checkout to a different
   commit *between* when a `Package` was listed and when its content is
   read, silently serving the wrong revision while the `Package` still
   claims the old one. **`resolveArtifactContent` for `gitCustom.ts`
   must re-checkout the exact commit recorded in `pkg.version.commit`
   before reading any file** (`git checkout <commit>` again, even if
   something else has since moved the working tree elsewhere), not
   trust "whatever's currently checked out." This makes content
   resolution correct regardless of what else has touched the shared
   cache directory in the meantime, without needing a full
   immutable-per-commit-worktree architecture (that's a valid future
   improvement, not required for Phase 1's risk level — a single
   developer's own registered sources, not a high-concurrency scenario).
   Don't have callers reverse-engineer a path from `artifact.id`/
   `artifact.name` — `resolveArtifactContent` is the only place that
   knows how to turn an `Artifact` back into real content. (This
   function currently returns a `CanonicalSkill` with only `name`/
   `description`/`body`/`extraFields` — task 03.4 extends
   `CanonicalSkill` to include a full file payload; this task only
   needs the function to exist and return what `CanonicalSkill`
   currently has. Don't block on 03.4 landing first.)
5. **Use a neutral `nativeFormat` id.** Replace the literal string
   `'claude-skill'` (used in `src/sources/localFolder.ts` and
   `src/sources/gitCustom.ts` when constructing `Package`/`Artifact`)
   with `'skill-md'` — the `SKILL.md` format is portable across
   Claude/Codex/Gemini/Kilo (SPEC.md §1), calling it "claude-skill" when
   it isn't Claude-specific is misleading provenance.
6. **Split the registry file into shareable + local state — without
   dropping the shareable half of installation intent.** Change
   `src/domain/registry.ts`:
   - `registryPath` becomes two functions: `manifestPath(scope,
     projectRoot?)` → `.../<scope-dir>/manifest.json`, and `statePath(scope,
     projectRoot?)` → `.../<scope-dir>/state.json`.
   - Define a **shareable, portable** `DesiredInstallation` type,
     distinct from the machine-local `ManagedInstallation`:

     ```ts
     export interface DesiredInstallation {
       sourceId: string;
       packageId: string;
       artifactId: string;
       kind: ItemKind;
       name: string;
       targetAssistant: AssistantId;
       targetScope: Scope;
       requestedRef?: string; // mirrors ResolvedRevision.requestedRef — intent, not a resolved commit
     }
     ```

     No absolute paths, no timestamps, no content hashes — those are
     exactly the fields that made the original single-file registry
     unshareable, per the round 001 review. **`ManifestFile` gains an
     `installations: DesiredInstallation[]` field** alongside
     `sources: Source[]` — the first draft of this task removed
     installations from the shareable model entirely instead of
     separating the shareable half from the machine-local half; that
     was too aggressive a fix. `Source` itself keeps its existing shape
     for now (its `projectPath`/`localPath` fields being absolute in
     some cases is a known follow-up, not blocking for Phase 1 — note it
     in your report rather than solving it in this task).
   - `ManifestFile { schemaVersion: number; sources: Source[];
     installations: DesiredInstallation[] }` (shareable) and
     `StateFile { schemaVersion: number; installations:
     ManagedInstallation[] }` (machine-local, what's actually installed
     on *this* machine — including the `sourceRevision` field from step
     3).
   - `readManifest`/`writeManifest`/`readState`/`writeState` replace
     `readRegistry`/`writeRegistry`, same atomic-write behavior
     (temp-file + rename) as before.
   - On read, if `schemaVersion` is missing or doesn't match the current
     constant (define it as an exported `const CURRENT_SCHEMA_VERSION =
     1` in `registry.ts` — round 001 flagged that no task named an
     actual value), throw a clear error naming the file and both
     versions — don't silently coerce or ignore a version mismatch.
7. Update `src/domain/registry.test.ts` for the new split (manifest vs
   state, round-trip each independently including the new
   `installations` field on `ManifestFile`, and a schemaVersion-mismatch
   throw).
