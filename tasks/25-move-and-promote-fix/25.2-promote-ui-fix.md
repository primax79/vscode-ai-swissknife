# 25.2 — Promote UI: candidate-based visibility + disambiguation

> Part of [Move action + Promote disambiguation fix](plan.md) · spec: [../specs/phase-6-spec.md](../specs/phase-6-spec.md) §2, §3, §4.4

## Goal

`Promote` becomes: hidden with 0 candidates (the `'local-promotion'`
placeholder is removed entirely — this is an intentional capability
removal, confirmed with the user, not an oversight), direct with 1
candidate, and a `QuickPick` disambiguation with >1. Depends on 25.1
having landed (needs `ObservedArtifact.candidates`).

This task must produce one commit containing only its changes.

## Steps

1. Give `ObservedArtifactItem` (`src/ui/installedView.ts`) a `contextValue`
   reflecting the candidate-count bucket: `observedArtifactItem:none` (0
   candidates), `observedArtifactItem:one` (1), `observedArtifactItem:many`
   (>1) — replacing the current unconditional `observedArtifactItem`.
   Precedent for this pattern: `installedInstallation:recommended` at
   `src/ui/installedView.ts:173`.
2. In `package.json`, split the single `aiSwissknife.promoteItem`
   `view/item/context` entry (currently `when: view ==
   aiSwissknife.installed && viewItem == observedArtifactItem`, no further
   condition) into two `when` clauses matching `:one` and `:many` — `:none`
   gets no `Promote` entry at all.
3. Update `promoteItem` (`src/ui/installedView.ts:480-511`): if invoked on
   an item with exactly 1 candidate, promote directly using that
   candidate's `{sourceId, packageId, artifactId, sourceRevision}` (not
   deriving from the ambiguous `match` field). If invoked on an item with
   >1 candidates, show a `QuickPick` listing each candidate (label:
   `sourceId`, description: its `status` — `identical`/`different`); on
   selection, promote using the chosen candidate's fields.
4. Update `promoteObservedArtifact` (`src/engine/discovery.ts:340-360`-ish,
   confirm exact lines) to accept an explicit chosen candidate/provenance
   parameter instead of deriving `finalSourceId`/`finalPackageId`/
   `finalArtifactId`/`finalSourceRevision` from `observed.match`. Remove
   the `'local-promotion'` string fallback entirely — the function must
   never be called with zero candidates now that the UI prevents it, but
   make the removal explicit (e.g. require the candidate parameter, don't
   leave a silent fallback path in the function itself).
5. Apply the same `contextValue`-bucket split to the Dashboard's
   `promote`/`promoteAllIdentical` message handlers in `src/ui/dashboard.ts`
   where they call `promoteObservedArtifact` — the single-item `promote`
   message handler needs the same 0/1/many branching (webview-side, since
   there's no `contextValue` there — gate on `item.candidates.length` sent
   in the message payload instead).

## Verification

- Manual verification: an unmanaged item matching zero sources shows no
  `Promote` action anywhere (sidebar or Dashboard); one matching exactly
  one source promotes directly with correct provenance; one matching two
  sources opens a picker and promotes with the chosen source's provenance.
- Update/add tests covering the `contextValue` bucket assignment and
  `promoteObservedArtifact`'s new explicit-candidate signature.
- Run full test suite, lint, typecheck, build.
