# 21.3 — Adapter Gemini CLI

> Parte di [Adapter Codex CLI e Gemini CLI](plan.md) · spec: [../specs/phase-4-spec.md](../../specs/phase-4-spec.md) §7

## Goal

Implementare `src/adapters/gemini.ts`: `command` TOML con la mappatura del nome
percorso→`:`, `rule` gerarchica (`GEMINI.md`, combinazione di globale + progetto),
`mcp-server` tramite la chiave `mcpServers` in `settings.json`, `skill` pass-through
(formato `SKILL.md` identico) e `agent` secondo i risultati di **21.1**
(implementarlo se confermato, oppure aggiungere un ramo esplicito `unsupported` nel traduttore
se confermato assente — non tirare a indovinare indipendentemente da 21.1).

Questo task deve produrre un singolo commit contenente solo le proprie modifiche per le
parti non-`agent`; se 21.1 conferma un formato `agent` standalone, la sua
implementazione è parte naturale di questo stesso task (sempre un unico commit) —
se 21.1 non rileva tale formato, saltarlo qui e annotarlo esplicitamente nel
commit invece di ometterlo silenziosamente.

## Riferimenti nel codice

- Struttura dei campi secondo la colonna Gemini CLI di `SPEC.md` §1: `command` è un file `.toml`
  in `commands/`, nome = percorso con `/`→`:` (es. `git/commit.toml` →
  `/git:commit`), campi `prompt`/`description`. `rule` è `GEMINI.md`,
  gerarchica (globale + progetto si combinano — a differenza del modello a file singolo di
  Claude/Codex, questo adapter deve unire entrambi i livelli in lettura, non
  sceglierne uno solo). `mcp-server` è una chiave `mcpServers` in `settings.json`
  (globale o di progetto; **prevale sempre su un mcp-server dichiarato da un'estensione**
  — una regola di precedenza che merita un commento nel punto in cui viene implementata,
  poiché non è ovvia ed è facile invertirla). `skill` ha lo stesso
  formato `SKILL.md`, portabile 1:1.
- Riutilizzare l'helper TOML introdotto in 21.2 invece di aggiungere un secondo percorso di
  parsing TOML.

## Steps

1. Implementare `parseGeminiCommandToml`/`serializeGeminiCommandToml` mappando
   da/verso `CanonicalCommand`, inclusa la conversione bidirezionale percorso↔nome `/`↔`:`.
2. Implementare `parseGeminiRule`/`serializeGeminiRule` — la lettura combina
   `GEMINI.md` globale + di progetto (documentare come i due vengono combinati, es.
   ordine di concatenazione, poiché "gerarchico" non è ulteriormente specificato in
   `SPEC.md`); la scrittura agisce sullo scope specifico a cui l'operazione di installazione/sincronizzazione
   è effettivamente rivolta, non su entrambi contemporaneamente.
3. Implementare `parseGeminiMcpServer`/`writeGeminiMcpServer` sulla
   chiave `mcpServers` in `settings.json`, preservando il resto del contenuto del file
   (si tratta di un file di configurazione condiviso, con la stessa cura nel merge già applicata dagli
   adapter mcp-server esistenti di Claude/Kilo).
4. Secondo il risultato di 21.1: implementare parse/serialize per `agent`, oppure aggiungere un commento
   + ramo `unsupported` a livello di traduttore (21.4) che registri perché è assente.
5. Aggiungere unit test: mappatura bidirezionale nome↔percorso per command, lettura gerarchica di `GEMINI.md`
   che combina una fixture globale + di progetto, scrittura con merge di `mcpServers`
   che preserva le chiavi non correlate di `settings.json`.
