# 21.4 — Translator wiring & UI integration

> Part of [Codex CLI & Gemini CLI adapters](plan.md) · spec: [../specs/phase-4-spec.md](../../specs/phase-4-spec.md) §7

## Goal

Extend every existing translator (`src/translator/skill.ts`,
`agent.ts`, `command.ts`, `mcp.ts`, `rule.ts`) with `codex-cli`/`gemini-cli`
target branches, and add both assistants to every UI assistant picker
(install target, sync target from initiative 18, Sources view), closing out
Phase 4's fifth and final adapter pair.

This task must produce one commit containing only its changes.

## Grounding

- Each translator currently branches on `targetAssistant` (see
  `translateRule` in `src/translator/rule.ts` for the smallest example) and
  returns `TranslationResult` with an `overall` diagnostic
  (`lossless`/`adapted-with-warning`/`potentially-destructive`/
  `unsupported`) — per the locked-in "every conversion carries an explicit
  diagnostic" invariant (`CONTEXT.md`), never silently drop a field.
- Known-lossy fields to flag explicitly, not silently drop: Codex's
  `sandbox`/`reasoning`/`developer_instructions` (no equivalent anywhere
  else in the matrix — `adapted-with-warning` at best when translating
  *from* Codex, since the data only round-trips via `extraFields`).
- `command` must never gain a Codex install-target branch (non-goal in
  `phase-4-spec.md` §2) — only a source-side (reading Codex `command` for
  import) if 21.2 already covers that; translating *to* Codex `command`
  stays `unsupported`.

## Steps

1. Add `codex-cli`/`gemini-cli` branches to each translator, calling into
   21.2/21.3's new parse/serialize functions, with diagnostics reflecting
   real field loss (not optimistic `lossless` claims for structurally
   different fields).
2. Add both assistants to the target picker in `src/ui/availableView.ts`
   (install), the sync target picker from initiative 18
   (`src/ui/installedView.ts`/`src/ui/dashboard.ts`), and the relevant
   Sources-view flows.
3. Add `'codex-cli'`/`'gemini-cli'` to any hardcoded `AssistantId` list the
   UI/engine currently iterates over (search for existing exhaustive
   switch/array literals over `AssistantId` — e.g. wherever Copilot was
   added in initiative 12 is the precedent to follow for what needs
   touching).
4. Add integration tests: full resolve→plan→preview→apply for at least one
   kind per new assistant (e.g. `skill` end-to-end for both, since it's
   lossless and the simplest full-path check), plus a translation-diagnostic
   test confirming Codex's lossy `agent` fields produce a non-`lossless`
   diagnostic.

## Verification

- Run full test suite, lint, typecheck, build.
- Manually install a skill from an existing `git-custom` source onto both
  Codex CLI and Gemini CLI targets and confirm the files land at the paths
  `SPEC.md` §1 documents.
