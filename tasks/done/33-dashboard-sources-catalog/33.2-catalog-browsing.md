# 33.2 — Lazy catalog browsing

**Depends on:** 33.1 (merged).

## Why

`AvailableTreeDataProvider`'s catalog (`src/ui/availableView.ts`,
`buildHierarchy:108-183`, `getChildren:482-551`) is the entire "what does
this source offer" view — folders, artifacts, diagnostics. Sending the
full catalog for every source upfront doesn't scale (`specs/phase-9-spec.md`
§3.2); expand-on-demand per source, matching how the sidebar tree already
works lazily.

## Scope

- New webview message `requestCatalog` with payload `{sourceId: string,
  scope: Scope}` (not `sourceId` alone — sources can share an id across
  global/project scope, `src/ui/availableView.ts:717` already
  disambiguates the same way — this was a specific correction from both
  spec reviews).
- Extension-host handler: `await availableProvider.ensureCatalogLoaded()`
  (`:227`), then look up the matching `AvailableSourceGroupItem` from
  `getCachedSourceGroups()` by `{sourceId, scope}`, call `.getChildren()`
  on it (the real cached instance — not a reconstructed one), and reply
  with a `catalogData` message carrying the resulting
  folders/artifacts/diagnostics, **including the `diagnostics` array**
  (`DiagnosticTreeItem` entries) — the original draft spec omitted this
  and both reviews flagged it: a source with detection problems must show
  the same diagnostic in the Dashboard the sidebar already shows, not
  render silently incomplete.
- Dashboard UI: expanding a source row (from 33.1) sends `requestCatalog`
  and renders the reply as a nested list under that source — folders
  collapsible (matching the sidebar's own folder-grouping from
  `buildHierarchy`), artifacts as leaf rows, diagnostics rendered
  distinctly (e.g. a warning-styled row, matching how the sidebar
  differentiates `DiagnosticTreeItem` today).
- No install/preview actions wired yet in this task — pure browse/render,
  33.3/33.4 add the actions on top of these rows.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Manual: expand a source with mixed content (nested folders, root
  artifacts, at least one detection diagnostic if a fixture/test source
  has one) — confirm the Dashboard's rendering matches the sidebar's tree
  structure for the same source exactly (same folder grouping, same
  artifact list, same diagnostic visible).
- Manual: expand a source that exists in both global and project scope
  with the same id — confirm each expands to its own scope's catalog, not
  a mixed/wrong one (the concrete bug the `{sourceId, scope}` payload
  fix prevents).
