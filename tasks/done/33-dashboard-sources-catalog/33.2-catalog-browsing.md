# 33.2 — Navigazione lazy del catalogo

**Depends on:** 33.1 (integrato).

## Perché

Il catalogo di `AvailableTreeDataProvider` (`src/ui/availableView.ts`,
`buildHierarchy:108-183`, `getChildren:482-551`) costituisce l'intera vista "cosa
offre questa sorgente" — cartelle, artefatti, diagnostica. Inviare in anticipo
l'intero catalogo per ogni sorgente non scala (`specs/phase-9-spec.md`
§3.2); espandere su richiesta per singola sorgente, rispecchiando il funzionamento
lazy già adottato dall'albero della sidebar.

## Ambito

- Nuovo messaggio webview `requestCatalog` con payload `{sourceId: string,
  scope: Scope}` (non solo `sourceId` — le sorgenti possono condividere un id tra
  scope global e project, e `src/ui/availableView.ts:717` disambigua già
  allo stesso modo — questa è stata una correzione specifica emersa da entrambe le
  revisioni della specifica).
- Gestore nell'extension host: eseguire `await availableProvider.ensureCatalogLoaded()`
  (`:227`), quindi cercare il corrispondente `AvailableSourceGroupItem` da
  `getCachedSourceGroups()` tramite `{sourceId, scope}`, invocarvi `.getChildren()`
  (la vera istanza in cache — non una ricostruita), e rispondere
  con un messaggio `catalogData` che trasporta le cartelle, gli artefatti e la diagnostica
  risultanti, **incluso l'array `diagnostics`**
  (voci `DiagnosticTreeItem`) — la bozza originale della specifica lo ometteva
  ed entrambe le revisioni lo hanno segnalato: una sorgente con problemi di rilevamento deve mostrare
  nella Dashboard la stessa diagnostica già mostrata dalla sidebar, senza
  renderizzarsi silenziosamente incompleta.
- UI della Dashboard: l'espansione di una riga sorgente (da 33.1) invia `requestCatalog`
  e renderizza la risposta come elenco annidato sotto quella sorgente — cartelle
  comprimibili (in linea con il raggruppamento in cartelle della sidebar prodotto da
  `buildHierarchy`), artefatti come righe foglia, diagnostica renderizzata
  in modo distinto (ad es. una riga con stile di avviso, rispecchiando il modo in cui la sidebar
  differenzia oggi `DiagnosticTreeItem`).
- Nessuna azione di installazione/anteprima cablata in questo task — pura navigazione/rendering;
  33.3/33.4 aggiungeranno le azioni sopra queste righe.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- Manuale: espandere una sorgente con contenuto misto (cartelle annidate, artefatti
  alla radice, almeno una diagnostica di rilevamento se una sorgente fixture/di test
  ne possiede una) — confermare che il rendering della Dashboard corrisponda esattamente alla struttura
  dell'albero della sidebar per la stessa sorgente (stesso raggruppamento in cartelle, stesso
  elenco di artefatti, stessa diagnostica visibile).
- Manuale: espandere una sorgente che esiste sia nello scope global sia in quello project
  con lo stesso id — confermare che ciascuna si espanda nel catalogo del proprio scope e non
  in uno mescolato/errato (il bug concreto prevenuto dalla correzione del payload
  `{sourceId, scope}`).
