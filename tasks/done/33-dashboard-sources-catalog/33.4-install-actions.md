# 33.4 — Install actions

**Depends on:** 31.2 (merged, for the decoupled `do*` install methods),
33.2 (merged, for catalog rows to install from).

## Why

This is the core "discover and install something new" workflow
(`aiSwissknife.installArtifact`/`installFolder`/`installSourceGroup`,
`src/extension.ts:409-421`) — entirely absent from the Dashboard today.
Initiative 31.2 (merged) already did the groundwork: `doInstallSourceGroup`,
`doInstallFolder`, and `doInstallArtifact` all exist on
`AvailableTreeDataProvider` as plain-identifier entry points, and
`installBatch` is public — confirm their exact current signatures by
reading `src/ui/availableView.ts` directly (31.2 landed independently and
may have shaped them slightly differently than originally sketched); this
task wires them to the webview, not build them.

## Scope

- New webview messages `installArtifact`, `installFolder`,
  `installSourceGroup` carrying whatever identifying fields the real
  `doInstallArtifact`/`doInstallFolder`/`doInstallSourceGroup` signatures
  from 31.2 need (`{sourceId, scope, ...}` plus `targetAssistant`/
  `targetScope` once picked) — the target-assistant/scope picker stays a
  native `showQuickPick` per the spec's non-goal (§2), triggered from the
  extension-host handler exactly as these methods already do it today.
  **Its assistant options must come from `getEnabledAdapters()`
  (`src/adapters/registry.ts`), never `ALL_ADAPTERS`** — confirmed still
  true as of 2026-09-08 at `src/ui/availableView.ts:552,790` for the
  existing sidebar-triggered pickers; this is a locked-in project rule
  (`tasks/CONTEXT.md`, "Any `showQuickPick` that lets the user pick a
  TARGET assistant...") that does **not** travel automatically if this
  task's implementation copies the picker logic to a new call site instead
  of calling the existing methods directly — prefer calling
  `doInstallArtifact`/`doInstallFolder`/`doInstallSourceGroup` as-is (they
  already build their own correctly-filtered picker) over re-implementing
  the picker in the Dashboard's message handler.
- Preview-before-install and batch-preview (`showPreview`/
  `showBatchPreview`) stay as their existing native VS Code preview flow —
  reuse as-is, no in-webview reimplementation.
- Dashboard UI: "Install" action per artifact row, per folder group, and
  per source (from 33.1's source row) — each triggers the corresponding
  message, then (per Initiative 32.3's incremental-update pattern) the
  extension host replies with updated catalog/installed-state data rather
  than a full page reload.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Manual: install a single artifact, an entire folder, and a whole source
  from the Dashboard, for at least two different kinds (e.g. skill +
  mcp-server) — confirm identical outcomes (same manifest/state writes,
  same conflict-handling prompts) to triggering the equivalent sidebar
  command, and confirm the sidebar's `Installed` tree reflects the new
  installation without a manual reload.
- Manual: trigger a conflict (install something already installed) from
  the Dashboard — confirm the same overwrite-confirmation prompt the
  sidebar shows appears, and declining it leaves state unchanged.
- Manual: with at least one assistant disabled via
  `aiSwissknife.enabledAssistants`, trigger an install from the Dashboard
  — confirm the target-assistant picker excludes the disabled one, same
  as the sidebar's own install commands.
