# 04.2 — Resolver git-custom

> Parte di [Resolver delle sorgenti](plan.md) · specifica: [../specs/foundations.md](../../specs/foundations.md)

**Obiettivo**: risolvere una `Source` con `type: 'git-custom'` (un URL generico
di repository git HTTPS/SSH, con pin opzionale di branch/tag/commit) in
`Package[]`, effettuando clone/fetch in una directory di cache locale e
riutilizzando poi la logica `findSkillDirs`/rilevamento del task 04.1 sul
checkout — non duplicare la logica di rilevamento.

**Riferimenti nel codice**: voce `git-custom` di Source in SPEC.md §1 ("auth
delegated to Git credentials already present on the machine", "branch/tag/commit
pin configurable"). Questo stesso repository
(`/Users/Alfredo/works/ai-coding-tools/ai-swissknife`, il suo `.git`) è un
repository git reale comodo e sempre disponibile su cui testare il comportamento
di clonazione — non serve accesso di rete a un host remoto per testare i
meccanismi di `git
clone`/`fetch`; un URL `file://` o un clone da percorso
locale su questo stesso repository (o su un repository temporaneo inizializzato
con `git init` per il test) è una vera operazione git, non un mock.

Passaggi:

1. Creare `src/sources/gitCustom.ts`:

   ```ts
   import type { Source, Package } from '../domain/types';

   export interface GitCustomOptions {
     cacheDir: string; // where checkouts live, e.g. ~/.ai-toolkit/cache/sources/<sourceId>/
   }

   export async function resolveGitCustom(source: Source, opts: GitCustomOptions): Promise<Package[]>;
   ```

   - Usare `child_process.execFile('git', [...])` (promisificato), non una
     libreria git di terze parti — l'autenticazione è delegata a qualunque
     configurazione abbia già il binario `git` nel `PATH` (SSH agent, credential
     helper), il che funziona solo invocando effettivamente il vero eseguibile
     `git`, non una reimplementazione JS.
   - Se `opts.cacheDir/<derived-from-source-id>` non esiste ancora: `git
     clone <source.url> <path>` (aggiungere `--branch <source.branch>` se
     impostato). Se esiste già: `git fetch` seguito da `git checkout` del ref
     risolto (`source.commit` ha la precedenza su `source.tag`, che ha la
     precedenza su `source.branch`, che ha la precedenza sul branch predefinito
     del remote — implementare esplicitamente questo ordine di precedenza, non
     usare sempre `HEAD`).
   - Dopo il checkout, chiamare `findSkillDirs`/la logica di risoluzione per
     cartella locale del task 04.1 (`src/sources/detect.ts`,
     `src/sources/localFolder.ts`) sul percorso del checkout e impostare ciascun
     `Package.sourceId` risultante a `source.id` (il resolver per cartella
     locale di 04.1 non conosce l'id di una `Source` git, poiché accetta una
     sorgente di tipo `local-folder` `Source` — chiamare direttamente
     `findSkillDirs(checkoutPath)` qui invece di passare per
     `resolveLocalFolder`, oppure costruire una `local-folder` `Source` sintetica
     che incapsula il percorso di checkout e riutilizzare
     `resolveLocalFolder` invariato — scegliere la soluzione che mantiene il
     codice più semplice e indicare quale è stata scelta nel report finale).
   - Esporre errori chiari e distinti per: repository non trovato/errore di
     autenticazione (git termina con codice diverso da zero durante clone/fetch
     — propagare `stderr` nell'errore sollevato, non sopprimerlo) e ref non
     trovato (git termina con codice diverso da zero durante il checkout —
     idem).
2. Scrivere `src/sources/gitCustom.test.ts`:
   - Configurare un vero repository git locale in una directory temporanea come
     fixture di test (`git init`, aggiungere un paio di directory di skill reali
     copiate da una delle fixture del task 04.1, fare commit, opzionalmente
     creare un secondo branch con una skill diversa aggiunta) — un repository
     reale, non un mock di `git`.
   - Test: `resolveGitCustom` su un percorso locale in stile `file://` (o un
     semplice percorso locale — verificare cosa accetta l'invocazione di `git clone`;
     git supporta la clonazione diretta da un percorso locale senza `file://`)
     senza pin di branch/tag/commit risolve il branch predefinito e trova le
     skill attese.
   - Test: con un pin `tag` o `commit` impostato a uno stato precedente (prima
     dell'aggiunta della seconda skill, se configurata), risolve solo le skill
     presenti in quel punto — questo verifica specificamente che la logica di
     precedenza/checkout fissi effettivamente il ref corretto, non semplicemente
     "qualunque cosa ci sia su disco ora".
   - Test: clonare due volte (la seconda chiamata riutilizza la directory di
     cache tramite fetch, non un nuovo clone) restituisce comunque il risultato
     corretto e aggiornato.
   - Test: un percorso locale inesistente come `source.url` produce un chiaro
     errore sollevato (non un risultato vuoto silenzioso).

**Verifica**: il file di test passa; `npm run lint && npm run
typecheck && npm run build` terminano tutti con codice 0. Un unico commit
contenente `src/sources/gitCustom.ts` e `src/sources/gitCustom.test.ts` —
nient'altro. Dopo questo commit, aggiornare in `tasks/00-INDEX.md` la riga dell'iniziativa `04` a `✅ done`.
