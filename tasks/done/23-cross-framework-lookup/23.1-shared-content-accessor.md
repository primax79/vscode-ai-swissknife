# 23.1 — Estrarre l'accessor condiviso dei contenuti resolve+translate

> Parte di [Ricerca di identità cross-framework + accessor condiviso dei contenuti](plan.md) · spec: [../specs/phase-6-spec.md](../../specs/phase-6-spec.md) §3, §4.2

## Goal

In `src/engine/plan.ts`, la funzione `resolveContentFromSource` (`src/engine/plan.ts:52-71`)
più le chiamate di traduzione per tipo che la seguono in `planInstall` costituiscono
l'**unica** implementazione in questo codebase che risolve il contenuto di un artefatto
da tutti e 5 i tipi di sorgente e lo traduce per tutti e 6 i tipi. `drift.ts` e
`discovery.ts` hanno ciascuno la propria versione più ristretta e duplicata (3 tipi di
sorgente, 4 tipi di artefatto — senza `hook`/`rule`). Questo task estrae la versione di `plan.ts`
in una funzione autonoma e riutilizzabile **senza modificare il comportamento
osservabile di `planInstall`** — 23.2 migra su di essa gli altri due punti di chiamata.

Questo task deve produrre un singolo commit contenente solo le proprie modifiche.

## Steps

1. Leggere `src/engine/plan.ts` per intero prima di modificarlo — `resolveContentFromSource`
   (righe 52-71) risolve; i sei rami per tipo più avanti nel file
   (`rule` ~103-133, `hook` ~199-229, `mcp-server` ~295+, `command` ~401+,
   `agent` ~532+, `skill` ~662+) chiamano ciascuno la funzione `translate*` corrispondente
   (`translateRule`, `translateHook`, `translateMcpServer`, `translateCommand`,
   `translateAgent`, `translateSkill` — tutte in `src/translator/`) sul
   contenuto risolto.
2. Aggiungere una nuova funzione esportata, es. in `src/engine/plan.ts` stesso (collocata insieme
   a `resolveContentFromSource`, senza bisogno di un nuovo file) o in un nuovo
   `src/engine/content.ts` se risulta più leggibile una volta scritta:

   ```ts
   async function resolveAndTranslate(
     source: Source,
     pkg: Package,
     artifact: Artifact,
     targetAssistant: AssistantId,
     resolverOpts?: ...  // whatever resolveContentFromSource already accepts
   ): Promise<{ translated: <the per-kind canonical union>; diagnostic: ConversionDiagnostic }>
   ```

   Deve smistare in base ad `artifact.kind` esattamente come fa già `planInstall`,
   chiamando `resolveContentFromSource` e poi la funzione `translate*` corrispondente,
   restituendo il valore canonico tradotto e la sua
   `ConversionDiagnostic`. Rispettare con precisione la struttura di smistamento per tipo esistente
   di `planInstall` — non inventare una nuova forma di smistamento.
3. Rifattorizzare i sei rami per tipo di `planInstall` affinché chiamino questa nuova funzione
   invece di eseguire inline `resolveContentFromSource` + `translate*`.
   I passi successivi di `planInstall` (calcolo dell'hash, costruzione di `PreparedInstall`,
   rilevamento dei conflitti) rimangono invariati — si sposta solo il passo di risoluzione+traduzione.
4. Esportare la nuova funzione da `src/engine/index.ts` accanto alle esportazioni esistenti
   del motore.
5. **Non** toccare `drift.ts` né `discovery.ts` in questo task — quello è il task 23.2,
   mantenuto separato affinché questa estrazione possa essere verificata prima in isolamento
   rispetto alla copertura di test esistente di `planInstall`.

## Verification

- Eseguire l'intera suite di test esistente (`npm test`) — ogni test esistente in
  `plan.test.ts`/`apply.test.ts` (o equivalente) per `planInstall` deve
  continuare a passare senza modifiche, dimostrando che il refactoring non ha alterato il
  comportamento di `planInstall` per nessuno dei 6 tipi.
- `npm run typecheck && npm run lint && npm run build`.
- Aggiungere uno unit test mirato direttamente per la nuova funzione (un caso per tipo,
  riutilizzando le fixture già presenti nei test esistenti di `plan.ts`) se nessun
  test esistente la esercita a questo livello di granularità.
