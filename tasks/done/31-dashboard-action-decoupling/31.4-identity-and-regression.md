# 31.4 — Identità stabile degli elementi + verifica di non regressione

**Depends on:** 31.1, 31.2, 31.3 (integrati).

## Perché

Due aspetti conclusivi per questa iniziativa, entrambi segnalati dalla
revisione multi-engine:

1. **Sicurezza/correttezza della chiave di identità.** La chiave esistente del pannello di dettaglio di `DashboardPanel`
   è `${assistant}:${scope}:${name}`
   (`src/ui/dashboard.ts:165,213`) — manca `kind`, perciò una `skill` e un
   `agent` che condividono lo stesso nome entrano in collisione. Le azioni `Uninstall`/`Update` dell'Iniziativa 34
   (che consumano `doUninstallItem`/`doUpdateInstallation` di 31.1)
   devono risolvere nuovamente il `ManagedInstallation` di destinazione **lato server, a partire da una
   scansione aggiornata dell'inventario**, tramite una chiave `{assistant, scope, kind, name}` —
   senza mai fidarsi di un oggetto completo (specialmente `path`) inviato avanti e indietro dalla
   webview, poiché `removeManagedInstallation` (`src/ui/installedView.ts:807`)
   elimina sul filesystem in corrispondenza di `inst.path`.
2. **Dimostrare che 31.1-31.3 non hanno alterato silenziosamente il comportamento della sidebar.** Tre
   estrazioni indipendenti sono state integrate in parallelo; questo task rappresenta l'unico
   passaggio che le esercita tutte insieme end-to-end prima che le Iniziative
   33/34 vi costruiscano sopra.

## Ambito

- Definire la chiave di identità composita come un piccolo helper condiviso — ad es.
  `installationKey(inst: ManagedInstallation): string` che restituisce
  `` `${inst.assistant}:${inst.scope}:${inst.kind}:${inst.name}` ``, e una
  corrispondente funzione di ricerca `findInstallationByKey(key: string, allManaged:
  ManagedInstallation[]): ManagedInstallation | undefined`. Collocarla
  dove risiede già `getInstallKey` (`src/ui/installedView.ts:1080`,
  attualmente `${assistant}:${scope}:${projectPath}:${name}` — usata per
  le ricerche dei report di drift, una chiave **diversa** per uno scopo diverso;
  decidere se estendere quell'helper esistente con `kind` o aggiungerne uno nuovo,
  e documentarne il motivo, invece di avere due chiavi quasi identiche
  non documentate).
- Aggiornare la costruzione della chiave in `src/ui/dashboard.ts` (`:165,213,347,401`
  circa — rieseguire grep per il pattern letterale
  `` `${...assistant}:${...scope}:${...name}` ``, poiché potrebbero esserci
  più punti oltre ai due citati) affinché usi la nuova chiave composita che include
  `kind`. Questo costituisce il lavoro preparatorio circoscritto per il cablaggio di Uninstall/Update dell'Iniziativa 34,
  non una modifica comportamentale per alcunché di attualmente raggiungibile — nessuna
  azione esistente della Dashboard dipende ancora dal fatto che questa chiave distingua il tipo
  (Copy/Move/Edit passano già l'intero oggetto, non solo la chiave).

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- Aggiungere uno unit test che dimostri che `installationKey` distingue due
  installazioni che condividono `assistant`+`scope`+`name` ma differiscono per
  `kind`.
- **Passaggio completo di non regressione su 31.1-31.3**, eseguito manualmente contro il pacchetto
  `.vsix` generato (non solo tramite i test automatizzati): per ciascuno tra
  `updateInstallation`, `uninstallItem`, `installFolder`,
  `installSourceGroup`, `recommendForWorkspace`, `unrecommendForWorkspace`
  — attivarlo dalla **sidebar** esattamente come prima di questa iniziativa,
  confermando finestre di dialogo, messaggi e stati finali identici. Questo è il
  vero gate dell'iniziativa per l'avvio delle Iniziative 33/34, non il semplice superamento della
  suite di test automatizzati.
