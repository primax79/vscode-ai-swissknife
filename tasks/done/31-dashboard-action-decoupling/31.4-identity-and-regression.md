# 31.4 — Stable item identity + regression verification

**Depends on:** 31.1, 31.2, 31.3 (merged).

## Why

Two closing concerns for this initiative, both flagged by the
multi-engine review:

1. **Security/correctness of the identity key.** `DashboardPanel`'s
   existing detail-panel key is `${assistant}:${scope}:${name}`
   (`src/ui/dashboard.ts:165,213`) — missing `kind`, so a `skill` and an
   `agent` sharing a name collide. Initiative 34's `Uninstall`/`Update`
   actions (consuming 31.1's `doUninstallItem`/`doUpdateInstallation`)
   must re-resolve the target `ManagedInstallation` **server-side, from a
   fresh inventory scan**, by a `{assistant, scope, kind, name}` key —
   never trust a full object (especially `path`) round-tripped from the
   webview, since `removeManagedInstallation` (`src/ui/installedView.ts:807`)
   deletes at `inst.path`.
2. **Proving 31.1-31.3 didn't silently change sidebar behavior.** Three
   independent extractions landed in parallel; this task is the single
   pass that exercises all of them together end-to-end before Initiative
   33/34 build on top.

## Scope

- Define the composite identity key as a small shared helper — e.g.
  `installationKey(inst: ManagedInstallation): string` returning
  `` `${inst.assistant}:${inst.scope}:${inst.kind}:${inst.name}` ``, and a
  matching lookup `findInstallationByKey(key: string, allManaged:
  ManagedInstallation[]): ManagedInstallation | undefined`. Put it
  wherever `getInstallKey` already lives (`src/ui/installedView.ts:1080`,
  currently `${assistant}:${scope}:${projectPath}:${name}` — used for
  drift-report lookups, a **different** key for a different purpose;
  decide whether to extend that existing helper with `kind` or add a new
  one, and document why, rather than having two near-identical
  undocumented keys).
- Update `src/ui/dashboard.ts`'s own key construction (`:165,213,347,401`
  roughly — re-grep for the literal
  `` `${...assistant}:${...scope}:${...name}` `` pattern, there may be
  more than the two cited spots) to use the new composite key including
  `kind`. This is scoped groundwork for Initiative 34's Uninstall/Update
  wiring, not a behavior change for anything currently reachable — no
  existing Dashboard action depends on this key distinguishing kind yet
  (Copy/Move/Edit pass the full object already, not just the key).

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Add a unit test proving `installationKey` distinguishes two
  installations that share `assistant`+`scope`+`name` but differ in
  `kind`.
- **Full regression pass across 31.1-31.3**, run manually against the
  packaged `.vsix` (not just automated tests): for each of
  `updateInstallation`, `uninstallItem`, `installFolder`,
  `installSourceGroup`, `recommendForWorkspace`, `unrecommendForWorkspace`
  — trigger it from the **sidebar** exactly as before this initiative,
  confirm identical dialogs/messages/end states. This is the initiative's
  actual gate for Initiative 33/34 to start, not just the automated test
  suite passing.
