# 31.1 — `doUpdateInstallation`/`doUninstallItem`

**Depends on:** nulla oltre all'attuale `main` (Fase 8/29.3 confermata
integrata — `getAdapter()` è già in uso alle righe citate di seguito,
riverificato il 2026-09-08 su `main` dopo il merge di 29.3/29.4/30.3/30.4).

## Perché

`InstalledTreeDataProvider.updateInstallation` (`src/ui/installedView.ts:462`)
e `.uninstallItem` (`:789`) richiedono entrambi un wrapper `InstalledInstallationItem`
(`item.installation`) — un'istanza di classe adiacente a `TreeItem`, non un
semplice oggetto di dominio. Un messaggio della webview della Dashboard può consegnare solo un semplice
`ManagedInstallation` (JSON clonato strutturalmente), quindi nessuno dei due metodi è
invocabile così com'è da `DashboardPanel`. Confermato in modo indipendente da entrambe le
revisioni della specifica di Codex e Kilo/gemini-3.7-flash (`specs/phase-9-spec.md` §1.1).

## Ambito

- `src/ui/installedView.ts`:
  - Aggiungere `async doUpdateInstallation(inst: ManagedInstallation): Promise<void>`
    contenente tutto ciò che `updateInstallation` (`:462-546` circa — il
    corpo del metodo dalla riga `const inst = item.installation;` in poi)
    fa oggi, invariato, incluso `const targetAdapter = getAdapter(inst.assistant);`
    già basato sul registro a `:495`.
    `updateInstallation(item?: InstalledInstallationItem)` diventa un wrapper
    sottile: mantenere la guardia `if (!item) { warn; return; }`, quindi `return
    this.doUpdateInstallation(item.installation);`.
  - Stesso pattern per `uninstallItem` (`:789-813`) →
    `doUninstallItem(inst: ManagedInstallation)`. `removeManagedInstallation`
    (`:771-787`, privato, usa già `getAdapter(inst.assistant)` a
    `:773` per il ramo di rimozione di `mcp-server`) rimane privato e invariato
    — invocato da `doUninstallItem` esattamente come avviene oggi da
    `uninstallItem` (punto di chiamata attuale `:804`).
- Nessuna modifica comportamentale per i chiamanti esistenti della sidebar — le firme e il comportamento esterno di `updateInstallation`/
  `uninstallItem` (finestre di conferma,
  messaggi, chiamate di refresh) sono identici prima e dopo; si limitano a
  delegare ai nuovi metodi `do*` invece di incorporare la logica inline.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- `src/ui/installedView.test.ts`: i test esistenti per `updateInstallation`/
  `uninstallItem` continuano a passare senza modifiche (dimostra che la delega del wrapper
  preserva il comportamento); aggiungere un test diretto per ciascun nuovo metodo `do*` invocandolo
  con un semplice oggetto `ManagedInstallation` (senza wrapper `InstalledInstallationItem`)
  per dimostrare che il disaccoppiamento funziona effettivamente, non solo che il
  wrapper continua a compilare.
- Manuale: `grep -n "item.installation" src/ui/installedView.ts` deve mostrare
  esattamente i due punti di chiamata nei wrapper (`updateInstallation`,
  `uninstallItem`) e nessun altro — l'obiettivo riguarda solo questi due metodi, non
  una rimozione più ampia di `InstalledInstallationItem`.
