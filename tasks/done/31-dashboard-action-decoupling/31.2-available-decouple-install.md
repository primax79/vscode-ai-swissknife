# 31.2 — Disaccoppiare i metodi di installazione di `availableView.ts`

**Depends on:** nulla oltre all'attuale `main` (Fase 8/29.3/30.3 confermata
integrata, riverificata il 2026-09-08).

## Perché

Rileggendo il codice reale (post-merge) questo task si restringe a una sola
vera lacuna, non quattro:

- **`installArtifact` (`src/ui/availableView.ts:543`) e `installBatch`
  (`:698`, `private`) accettano già di fatto dati semplici.**
  `installArtifact` destruttura `const { source, pkg, artifact } = item;`
  a `:549` — semplici letture di campi, nessun metodo — e `installBatch` accetta
  `items: AvailableArtifactItem[]`, la cui classe (`:80-87`) non ha **alcun
  metodo**, ma solo i campi readonly `source`/`pkg`/`artifact`/`isRecommended`.
  Un oggetto JSON semplice strutturalmente identico funziona già oggi per
  entrambi. L'unico vero ostacolo per questi due è il fatto che `installBatch`
  sia `private`.
- **`installSourceGroup` (`:676`) risolve già tutto a partire da campi
  semplici** (`sourceItem.source.id`, `sourceItem.source.scope`, `:682-683`)
  rispetto a `this.cachedSourceGroups` (`:191`) — non invoca mai alcun metodo su
  `sourceItem` stesso. Deve cambiare solo la *forma dei suoi parametri*.
- **`installFolder` (`:667`) è l'unico caso effettivo.** Invoca
  `folderItem.getAllArtifacts()` (`:672`), un vero metodo ricorsivo
  (`AvailableFolderItem`, `:59-77`). Punto critico: le istanze di `AvailableFolderItem`
  **non** sono messe in cache da nessuna parte — `buildHierarchy()` (`:99`) viene
  invocata ex novo a ogni espansione dell'albero, da `getChildren`
  (`:502`: `buildHierarchy(element.source, element.resolution.packages, ...)`),
  usando `resolution.packages` messo in cache su `AvailableSourceGroupItem`.
  Pertanto una cartella non può essere cercata per identità in una cache — deve essere
  **ricostruita** a partire dai pacchetti del gruppo sorgente in cache, e poi attraversata fino al
  percorso corrispondente.

## Ambito

- `src/ui/availableView.ts`:
  - `installBatch`: rimuovere `private` (o aggiungere un sottile passthrough pubblico —
    rimuovere `private` è più semplice e non c'è motivo di mantenerlo
    privato una volta che diventa un secondo punto di ingresso legittimo). Nessuna modifica
    alla firma necessaria.
  - `installArtifact`: nessuna modifica necessaria — è già invocabile con un semplice
    oggetto `{source, pkg, artifact}` strutturalmente conforme ad
    `AvailableArtifactItem`. (Se il payload della webview della Dashboard arriva
    come `{sourceId, scope, packageId, artifactId}` invece che come un intero
    oggetto `{source, pkg, artifact}` — probabile, dato che inviare interi oggetti
    `Package`/`Artifact` avanti e indietro è uno spreco — aggiungere un piccolo
    risolutore `resolveArtifactByIds(sourceId, scope, packageId,
    artifactId): {source, pkg, artifact} | undefined` basato su
    `getCachedSourceGroups()` (`:205`), e far sì che il gestore dell'Iniziativa 33.4
    lo chiami prima di invocare `installArtifact`. Questo task può aggiungere
    quel risolutore poiché ne è la sede naturale; l'Iniziativa 33.4
    lo consumerà.)
  - `installSourceGroup(sourceItem?: SourceItem)` → aggiungere
    `doInstallSourceGroup(sourceId: string, scope: Scope): Promise<void>`
    con lo stesso identico corpo del metodo odierno ma leggendo direttamente `sourceId`/
    `scope` invece di `sourceItem.source.id`/`.source.scope`.
    `installSourceGroup(sourceItem)` diventa un wrapper sottile: `if
    (!sourceItem) { warn; return; } return
    this.doInstallSourceGroup(sourceItem.source.id, sourceItem.source.scope);`.
  - `installFolder(folderItem?: AvailableFolderItem)` → aggiungere
    `doInstallFolder(sourceId: string, scope: Scope, folderPath: string):
    Promise<void>`: cercare il corrispondente `AvailableSourceGroupItem` da
    `getCachedSourceGroups()` tramite `{sourceId, scope}` (stessa ricerca che
    `installSourceGroup` esegue già a `:682-683`), invocare
    `buildHierarchy(group.source, group.resolution.packages)` per ricostruire
    l'albero, attraversarlo per trovare l'`AvailableFolderItem` il cui percorso
    accumulato corrisponde a `folderPath` (confrontare con la costruzione del percorso
    propria di `buildHierarchy`, `:152-154` — riutilizzare quella logica esatta, senza
    riderivare in modo indipendente la concatenazione del percorso), invocare `.getAllArtifacts()` su
    quell'istanza (una vera istanza di classe appartenente a un albero appena costruito — il
    metodo funziona perché *è* reale, non perché era in cache), quindi
    `installBatch(artifacts, ...)`. `installFolder(folderItem)` diventa un
    wrapper sottile: `if (!folderItem) { warn; return; } return
    this.doInstallFolder(folderItem.source.id, folderItem.source.scope,
    folderItem.folderPath);` (`AvailableFolderItem.folderPath` è un vero
    campo del costruttore, `:62`).
- Nessuna modifica comportamentale per i chiamanti esistenti della sidebar.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- I test esistenti che esercitano `installFolder`/`installSourceGroup`/
  `installBatch` (`src/ui/ui.test.ts`, `src/ui/recommendations.test.ts`)
  continuano a passare senza modifiche.
- Aggiungere un test diretto per `doInstallFolder(sourceId, scope, folderPath)`
  su una sorgente fixture con una cartella annidata, verificando che installi
  lo stesso insieme di artefatti che `installFolder(folderItem)` installerebbe per il
  `folderItem` equivalente — questo è l'unico caso che merita un test di regressione
  dedicato poiché svolge un vero lavoro di riderivazione e non
  una semplice ridenominazione di parametri.
- Aggiungere un test diretto per `doInstallSourceGroup(sourceId, scope)` con argomenti
  semplici (senza istanza `SourceItem`).
