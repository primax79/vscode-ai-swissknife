# 31.2 — Decouple `availableView.ts` install methods

**Depends on:** nothing beyond current `main` (Phase 8/29.3/30.3 confirmed
merged, re-verified 2026-09-08).

## Why

Re-reading the real code (post-merge) narrows this task to exactly one
real gap, not four:

- **`installArtifact` (`src/ui/availableView.ts:543`) and `installBatch`
  (`:698`, `private`) already take effectively plain data.**
  `installArtifact` destructures `const { source, pkg, artifact } = item;`
  at `:549` — plain field reads, no methods — and `installBatch` takes
  `items: AvailableArtifactItem[]`, whose class (`:80-87`) has **no
  methods at all**, just `source`/`pkg`/`artifact`/`isRecommended`
  readonly fields. A structurally-identical plain JSON object works for
  both today. The only real blocker for these two is `installBatch`
  being `private`.
- **`installSourceGroup` (`:676`) already resolves everything from plain
  fields** (`sourceItem.source.id`, `sourceItem.source.scope`, `:682-683`)
  against `this.cachedSourceGroups` (`:191`) — it never calls a method on
  `sourceItem` itself. Only its *parameter shape* needs to change.
- **`installFolder` (`:667`) is the one genuine case.** It calls
  `folderItem.getAllArtifacts()` (`:672`), a real recursive method
  (`AvailableFolderItem`, `:59-77`). Critically, `AvailableFolderItem`
  instances are **not** cached anywhere — `buildHierarchy()` (`:99`) is
  called fresh on every tree expansion, from `getChildren`
  (`:502`: `buildHierarchy(element.source, element.resolution.packages, ...)`),
  using the cached `resolution.packages` on `AvailableSourceGroupItem`.
  So a folder can't be looked up by identity from a cache — it must be
  **rebuilt** from the cached source group's packages, then walked to the
  matching path.

## Scope

- `src/ui/availableView.ts`:
  - `installBatch`: remove `private` (or add a thin public passthrough —
    removing `private` is simpler and there's no reason to keep it
    private once it's a legitimate second entry point). No signature
    change needed.
  - `installArtifact`: no change needed — already callable with a plain
    `{source, pkg, artifact}` object structurally matching
    `AvailableArtifactItem`. (If the Dashboard's webview payload arrives
    as `{sourceId, scope, packageId, artifactId}` instead of a full
    `{source, pkg, artifact}` object — likely, since sending full
    `Package`/`Artifact` objects round-trip is wasteful — add a small
    resolver `resolveArtifactByIds(sourceId, scope, packageId,
    artifactId): {source, pkg, artifact} | undefined` against
    `getCachedSourceGroups()` (`:205`), and have Initiative 33.4's
    handler call it before calling `installArtifact`. This task can add
    that resolver since it's the natural home for it; Initiative 33.4
    consumes it.)
  - `installSourceGroup(sourceItem?: SourceItem)` → add
    `doInstallSourceGroup(sourceId: string, scope: Scope): Promise<void>`
    with the exact same body as today's method but reading `sourceId`/
    `scope` directly instead of `sourceItem.source.id`/`.source.scope`.
    `installSourceGroup(sourceItem)` becomes a thin wrapper: `if
    (!sourceItem) { warn; return; } return
    this.doInstallSourceGroup(sourceItem.source.id, sourceItem.source.scope);`.
  - `installFolder(folderItem?: AvailableFolderItem)` → add
    `doInstallFolder(sourceId: string, scope: Scope, folderPath: string):
    Promise<void>`: look up the matching `AvailableSourceGroupItem` from
    `getCachedSourceGroups()` by `{sourceId, scope}` (same lookup
    `installSourceGroup` already does at `:682-683`), call
    `buildHierarchy(group.source, group.resolution.packages)` to rebuild
    the tree, walk it to find the `AvailableFolderItem` whose accumulated
    path matches `folderPath` (compare against `buildHierarchy`'s own path
    construction, `:152-154` — reuse that exact logic, don't
    re-derive path-joining independently), call `.getAllArtifacts()` on
    that instance (a real class instance from a freshly-built tree — the
    method works because it *is* real, not because it was cached), then
    `installBatch(artifacts, ...)`. `installFolder(folderItem)` becomes a
    thin wrapper: `if (!folderItem) { warn; return; } return
    this.doInstallFolder(folderItem.source.id, folderItem.source.scope,
    folderItem.folderPath);` (`AvailableFolderItem.folderPath` is a real
    constructor field, `:62`).
- No behavior change for existing sidebar callers.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Existing tests exercising `installFolder`/`installSourceGroup`/
  `installBatch` (`src/ui/ui.test.ts`, `src/ui/recommendations.test.ts`)
  still pass unmodified.
- Add a direct test for `doInstallFolder(sourceId, scope, folderPath)`
  against a fixture source with a nested folder, asserting it installs
  the same artifact set `installFolder(folderItem)` would for the
  equivalent `folderItem` — this is the one case worth a dedicated
  regression test since it's the one doing real re-derivation work, not
  just a parameter rename.
- Add a direct test for `doInstallSourceGroup(sourceId, scope)` with plain
  arguments (no `SourceItem` instance).
