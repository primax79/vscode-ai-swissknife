# 31.3 — Identifier-based recommend/unrecommend

**Depends on:** nothing beyond current `main`.

## Why

`handleRecommendForWorkspace` (`src/extension.ts:159-233`) and
`handleUnrecommendForWorkspace` (`:235-...`) are already **exported,
standalone functions** (not private closures — better starting point than
either spec review assumed), but both take `item:
AvailableArtifactItem | InstalledInstallationItem | undefined` and branch
`if (item instanceof AvailableArtifactItem) {...} else if (item
instanceof InstalledInstallationItem) {...} else { return; }`
(`:177,193,208`). A webview `postMessage` payload fails both `instanceof`
checks and silently falls into the `return` branch — the Dashboard's
`recommendForWorkspace` message would appear to succeed while doing
nothing.

Re-reading the two branches narrows the real work:

- The `AvailableArtifactItem` branch (`:177-192`) needs `item.source.scope`,
  `item.source.id`, `item.artifact.id`, plus its own `assistantPick`
  QuickPick (the item isn't installed anywhere yet, so there's no
  assistant to infer) — this branch is genuinely "available artifact,
  not yet installed" and needs identifiers `{sourceId, scope, artifactId}`
  in place of the wrapper.
- The `InstalledInstallationItem` branch (`:193-207`) just unwraps
  `item.installation` into `inst`, then calls
  `ensureRecommendableSource(sourcesProvider, projectRoot, inst.name,
  inst.kind, inst.sourceId, inst.artifactId)` — already takes only plain
  `ManagedInstallation` fields. This branch needs no real rework, only a
  parameter that accepts `inst: ManagedInstallation` directly instead of
  unwrapping `item.installation`.

## Scope

- `src/extension.ts`: split `handleRecommendForWorkspace`'s two branches
  into two identifier-based functions (co-locate wherever makes sense —
  they can stay in `extension.ts` since they're already exported
  top-level functions there, not necessarily move to
  `recommendations.ts`; only move them if `recommendations.ts` is clearly
  the better home once you see how much of `readManifest`/
  `writeManifest`/`getWorkspaceRoot` plumbing they share with what's
  already there):
  - `recommendAvailableArtifact(sourceId: string, scope: Scope, artifactId:
    string, projectRoot: string): Promise<void>` — the current
    `AvailableArtifactItem` branch's body (scope check, assistant
    QuickPick, manifest write), taking identifiers instead of
    `item.source`/`item.artifact`.
  - `recommendInstalledArtifact(inst: ManagedInstallation,
    sourcesProvider: SourcesTreeDataProvider, projectRoot: string):
    Promise<void>` — the current `InstalledInstallationItem` branch's
    body, taking `inst` directly.
  - `handleRecommendForWorkspace(item, availableProvider,
    installedProvider, sourcesProvider)` becomes a thin
    `instanceof`-dispatching wrapper calling one of the two above with the
    extracted fields, then doing the existing `availableProvider.refresh()`/
    `installedProvider.refresh()` calls (`:225-226`) itself, same as today.
  - Mirror the same split for `handleUnrecommendForWorkspace`.
- External behavior for the sidebar's `aiSwissknife.recommendForWorkspace`/
  `unrecommendForWorkspace` commands is unchanged.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Add a test calling `recommendAvailableArtifact`/`recommendInstalledArtifact`
  (and their unrecommend counterparts) directly with plain arguments (no
  `AvailableArtifactItem`/`InstalledInstallationItem` instance) — proves
  the Dashboard's future call path (Initiative 34.1) actually works.
- Manual: confirm the sidebar's `Recommend for workspace`/`Unrecommend`
  context-menu actions still behave identically (same manifest
  read/write, same confirmation messaging, same
  global-scope-rejection for `AvailableArtifactItem` at `:178-181`) — this
  is a pure extraction, not a behavior change.
