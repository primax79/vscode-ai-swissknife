# 05.2 — Traduzione tipizzata sulla destinazione e diagnostiche per campo (hardening)

> Parte di [Modello canonico + traduttore](plan.md) · specifica: [../specs/foundations.md](../../specs/foundations.md) · decisioni di revisione accettate: decisione 4 del [round 001](../../_reviews/001-hardening-gate-SUMMARY.md) e decisioni 3 e 17 del [round 002](../../_reviews/002-hardening-gate-SUMMARY.md). Il precedente riferimento alla decisione 9 del round-001 era errato ed è stato rimosso.

## Goal

Rimuovere la provenienza non risolvibile dell'assistente sorgente, accettare il tipo reale della destinazione dell'adapter ed esporre diagnostiche con granularità di campo/percorso senza scartare l'output tradotto.

Questo task deve produrre un unico commit contenente solo le proprie modifiche.

## Riferimenti nel codice

Leggere `src/adapters/types.ts`, `src/translator/skill.ts` e ogni chiamante di `translateSkill`. `Adapter.assistant` è `AssistantId`; la firma del traduttore deve comporsi con esso senza cast di restringimento (narrowing).

## Steps

1. Modificare la firma pubblica in `translateSkill(source: CanonicalSkill, targetAssistant: AssistantId): TranslationResult<CanonicalSkill>`. Rimuovere `fromAssistant`: il contenuto di un repository personalizzato non ha un assistente sorgente affidabile. Ritirare il nome di tipo `SupportedAssistant` dopo aver migrato tutti i chiamanti. La funzione dormiente `translateRule` importa attualmente quel tipo, quindi migrarla in questo commit allo stesso confine `AssistantId` basato solo sulla destinazione (Claude/Kilo senza perdita, altre destinazioni non supportate); non lasciare un import che rompe la compilazione né un alias di compatibilità.

2. Sostituire il risultato solo aggregato con questa forma concreta (riutilizzare l'unione `ConversionDiagnostic` esistente per `overall`):

   ```ts
   export interface TranslationDiagnostic {
     code: string;
     severity: 'info' | 'warning' | 'error';
     field?: 'name' | 'description' | 'body' | 'extraFields' | 'files' | 'target';
     path?: string;
     impact: 'none' | 'adapted' | 'lost' | 'unsupported';
     message: string;
   }

   export interface TranslationResult<T> {
     value: T;
     overall: ConversionDiagnostic;
     diagnostics: TranslationDiagnostic[];
   }
   ```

   Le diagnostiche identificano il campo interessato (e il percorso del file quando applicabile). Un risultato senza perdita contiene comunque una diagnostica informativa esplicita o un elenco vuoto documentato più `overall: 'lossless'`; non mantenere mai due campi concorrenti `diagnostic`/`overall`.

3. Le destinazioni Claude Code e Kilo Code restituiscono l'intero payload canonico della directory senza perdita. Preservare `extraFields`, file ausiliari, contenuto binario e permessi (mode).

4. Qualsiasi altro `AssistantId` restituisce `overall: 'unsupported'` con una diagnostica esplicita sulla destinazione. Non deve sollevare eccezioni né fingere di essere senza perdita. Il valore restituito può preservare la sorgente per ispezione, ma i chiamanti effettuano il branch su `overall` prima di pianificare un'installazione.

5. Rendere inequivocabili i nomi di input e output nei punti di chiamata (`resolvedContent`, `translation`, `translation.value`). Il task 06.1 valida, calcola l'hash, genera l'anteprima e memorizza `translation.value`, mai l'input del traduttore.

## Verification

- Eseguire l'intera suite di test, typecheck, lint e build.
- Compilare le chiamate per skill e per le regole dormienti usando ogni `AssistantId`; non rimane alcun cast, parametro di assistente sorgente o `SupportedAssistant`.
- Verificare la traduzione senza perdita per Claude/Kilo di file annidati, contenuto binario, campi extra e permessi (mode).
- Verificare che le destinazioni non supportate restituiscano `overall: 'unsupported'` con una diagnostica sulla destinazione e nessuna eccezione.
- Utilizzare una traduzione di test che modifica un campo e dimostrare che il chiamante osserva `translation.value`, impedendo che un comportamento di sola identità nasconda regressioni.

## Non-obiettivi

- Nessuna inferenza dell'assistente sorgente.
- Nessun accesso al filesystem.
- Nessun adapter oltre alla segnalazione delle destinazioni non supportate in questa fase.
