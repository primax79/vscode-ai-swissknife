# 03.3 — Kilo Code adapter

> Part of [Claude + Kilo adapters](plan.md) · spec: [../specs/foundations.md](../../specs/foundations.md)

**Goal**: implement the `Adapter` interface (from 03.1) for Kilo Code,
covering `skill` and `rule` only — structurally almost a copy of the
Claude adapter (03.2), since both kinds are format-identical between the
two assistants (see `plan.md`'s shared decisions), but with Kilo's own
paths.

**Grounding**: SPEC.md §1 `skill`/`rule` rows for Kilo — the exact
citations are `paths.ts:21-24` (skill paths) and
`rules-migration.md:67-73` (native `AGENTS.md`/`CLAUDE.md` reading). If
`src/adapters/claude.ts` (task 03.2) is already merged when you start this
task, read it first — this adapter's `skill` logic should be structurally
identical (same frontmatter shape, same round-trip behavior), only the
paths differ.

Steps:

1. Create `src/adapters/kilo.ts` implementing `Adapter`:
   - `assistant = 'kilo-code'`.
   - `skillPath(name, loc)`: global `~/.kilo/skills/<name>/SKILL.md`,
     project `<projectRoot>/.kilo/skills/<name>/SKILL.md`. **Not**
     `~/.config/kilo/skills` — that's a different (agent) path family, not
     used for skills (SPEC.md §1, `paths.ts:21-24` is explicit about
     this).
   - `readSkill`/`writeSkill`/`listSkills`: same frontmatter shape and
     behavior as the Claude adapter (`name`/`description` required, extra
     fields preserved) — Kilo's own skill installer only checks for those
     two fields (`plugin_manager.py:319-321`), no Kilo-specific extra
     schema exists.
   - `rulePath(loc)`: **reuse the same path Claude's adapter would use**
     for the equivalent scope — `<projectRoot>/CLAUDE.md` (project) or
     `~/.claude/CLAUDE.md` (global)? **No** — re-read SPEC.md §5 "rule
     convergence" carefully: the convergence is that Kilo *also reads*
     `AGENTS.md`/`CLAUDE.md` at the project root and
     `~/.config/kilo/AGENTS.md` globally, natively, without needing its
     own `instructions` array entry. So for `writeRule` at project scope,
     write to `<projectRoot>/CLAUDE.md` (same file Claude reads — this is
     the actual point of "zero translation": one file serves both). For
     **global** scope, Kilo's own native global rule file is
     `~/.config/kilo/AGENTS.md` (not `~/.claude/CLAUDE.md` — that's
     Claude's own home, Kilo doesn't read files under `~/.claude/`
     globally). Get this right: project scope shares Claude's file
     directly; global scope does not.
   - `readRule`/`writeRule`: plain file read/write, same as Claude's
     adapter, at the paths above.
2. Same Node-builtins-only constraint as task 03.2 (reuse whatever
   frontmatter parsing approach that task settled on — don't introduce a
   second one).
3. Write `src/adapters/kilo.test.ts`, same coverage shape as
   `claude.test.ts` (03.2), plus one test specific to this adapter: at
   **project** scope, `rulePath()` returns the exact same path string
   Claude's `rulePath()` would return for the same `projectRoot` (import
   and instantiate both adapters in the test to assert this directly —
   don't just assert the literal string twice and hope they stay in
   sync).

**Verification**: the test file passes, including the cross-adapter
project-scope-rule-path assertion; `npm run lint && npm run typecheck &&
npm run build` all exit 0. One commit containing `src/adapters/kilo.ts`
and `src/adapters/kilo.test.ts` — nothing else. After this commit, update
`tasks/00-INDEX.md`'s row for initiative `03` to `✅ done`.
