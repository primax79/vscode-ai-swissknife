# 03.3 — Adapter Kilo Code

> Parte di [Adapter Claude + Kilo](plan.md) · specifica: [../specs/foundations.md](../../specs/foundations.md)

**Obiettivo**: implementare l'interfaccia `Adapter` (da 03.1) per Kilo Code,
coprendo esclusivamente `skill` e `rule` — strutturalmente quasi una copia
dell'adapter Claude (03.2), poiché entrambi i tipi hanno formato identico tra i
due assistenti (vedere le decisioni condivise in `plan.md`), ma con i percorsi
propri di Kilo.

**Riferimenti nel codice**: righe `skill`/`rule` di SPEC.md §1 per Kilo — i
riferimenti esatti sono `paths.ts:21-24` (percorsi delle skill) e
`rules-migration.md:67-73` (lettura nativa di `AGENTS.md`/`CLAUDE.md`). Se
`src/adapters/claude.ts` (task 03.2) è già stato unito quando si inizia questo
task, leggerlo prima — la logica `skill` di questo adapter deve essere
strutturalmente identica (stessa forma del frontmatter, stesso comportamento di
round-trip), cambiano solo i percorsi.

Passaggi:

1. Creare `src/adapters/kilo.ts` che implementa `Adapter`:
   - `assistant = 'kilo-code'`.
   - `skillPath(name, loc)`: globale `~/.kilo/skills/<name>/SKILL.md`,
     progetto `<projectRoot>/.kilo/skills/<name>/SKILL.md`. **Non**
     `~/.config/kilo/skills` — quella è una famiglia di percorsi diversa (per
     gli agent), non usata per le skill (SPEC.md §1, `paths.ts:21-24` è
     esplicito al riguardo).
   - `readSkill`/`writeSkill`/`listSkills`: stessa struttura del frontmatter e
     stesso comportamento dell'adapter Claude (`name`/`description` obbligatori,
     campi aggiuntivi preservati) — lo stesso installer di skill di Kilo
     controlla solo quei due campi (`plugin_manager.py:319-321`), non esiste
     alcuno schema extra specifico di Kilo.
   - `rulePath(loc)`: **riutilizzare lo stesso percorso che userebbe l'adapter
     di Claude** per lo scope equivalente — `<projectRoot>/CLAUDE.md` (progetto)
     o `~/.claude/CLAUDE.md` (globale)? **No** — rileggere attentamente SPEC.md
     §5 "rule convergence": la convergenza consiste nel fatto che Kilo *legge
     anche* `AGENTS.md`/`CLAUDE.md` nella radice del progetto e
     `~/.config/kilo/AGENTS.md` a livello globale, nativamente, senza bisogno di
     una propria voce nell'array `instructions`. Quindi per `writeRule` nello
     scope di progetto, scrivere in `<projectRoot>/CLAUDE.md` (lo stesso file
     letto da Claude — questo è il vero senso di "zero traduzione": un unico
     file serve entrambi). Per lo scope **globale**, il file di regole globale
     nativo di Kilo è `~/.config/kilo/AGENTS.md` (non `~/.claude/CLAUDE.md` —
     quella è la home propria di Claude, Kilo non legge file sotto `~/.claude/`
     a livello globale). Prestare attenzione a questo punto: lo scope di
     progetto condivide direttamente il file di Claude; lo scope globale no.
   - `readRule`/`writeRule`: semplice lettura/scrittura su file, come per
     l'adapter di Claude, ai percorsi indicati sopra.
2. Stesso vincolo di usare solo moduli built-in di Node del task 03.2
   (riutilizzare qualunque approccio di parsing del frontmatter sia stato scelto
   in quel task — non introdurne un secondo).
3. Scrivere `src/adapters/kilo.test.ts`, con la stessa copertura di
   `claude.test.ts` (03.2), più un test specifico per questo adapter: nello
   scope di **progetto**, `rulePath()` restituisce esattamente la stessa stringa
   di percorso che restituirebbe `rulePath()` di Claude per lo stesso
   `projectRoot` (importare e istanziare entrambi gli adapter nel test per
   verificarlo direttamente — non limitarsi a verificare due volte la stringa
   letterale sperando che restino allineati).

**Verifica**: il file di test passa, inclusa l'asserzione incrociata tra adapter
sul percorso delle regole nello scope di progetto; `npm run lint && npm run typecheck &&
npm run build` terminano tutti con codice 0. Un unico commit contenente
`src/adapters/kilo.ts` e `src/adapters/kilo.test.ts` — nient'altro. Dopo questo
commit, aggiornare in `tasks/00-INDEX.md` la riga dell'iniziativa `03` a
`✅ done`.
