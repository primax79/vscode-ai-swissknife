# 32.2 — Guscio di navigazione a sezioni + punto di accesso New Artifact

**Depends on:** 32.1 (integrato).

## Perché

La Dashboard ha bisogno di spazio per quattro sezioni (Overview, Installed, Sources &
Catalog, Recommendations) senza diventare un'unica pagina a scorrimento ancora più
monolitica. La revisione di Kilo/Gemini ha raccomandato specificamente di costruire questo guscio
*prima* dell'arrivo dei contenuti delle Iniziative 33/34, per evitare di costruire grandi blocchi
HTML su un layout provvisorio e doverli ristrutturare in seguito
(`specs/phase-9-spec.md` §3.3).

## Ambito

- `src/ui/dashboard.ts`: aggiungere tab di sezione di primo livello riutilizzando le classi CSS esistenti
  `.tab-btn`/`.tab-btn.active` già definite per il filtro per
  tipo (`:527-540`) — quattro tab: **Overview**, **Installed**, **Sources
  & Catalog**, **Recommendations**. Solo **Installed** ha contenuto reale in
  questo task (la tabella unificata/i filtri/il pannello di dettaglio odierni, portati così come sono —
  nessuna modifica comportamentale, solo spostati sotto il proprio tab invece di costituire
  l'intera pagina). **Overview**, **Sources & Catalog**, **Recommendations**
  renderizzano un contenitore di sezione vuoto/segnaposto (un `<div>` con un id
  a cui punteranno le Iniziative 33/34) — non costruirne il contenuto qui.
- Suddividere `getHtml()` (`:304-1049`) in funzioni template per singola sezione
  (ad es. `getOverviewHtml()`, `getInstalledSectionHtml(...)`,
  `getSourcesCatalogHtml()`, `getRecommendationsHtml()`) invocate da un'unica
  funzione di assemblaggio di primo livello — questa è la mitigazione del rischio "suddividere in funzioni
  template per sezione" di `specs/phase-9-spec.md` §6,
  applicata ora mentre la sezione Installed è l'unica con contenuto reale,
  così che il pattern sia stabilito prima di aggiungervi l'HTML di altre tre
  sezioni.
- Aggiungere un pulsante `+ New Artifact` nell'intestazione della Dashboard
  (`src/ui/dashboard.ts:676-686`) che invia un nuovo messaggio webview `createArtifact`;
  il gestore nell'extension host invoca lo stesso flusso in modalità creazione di `FormEditorPanel`
  già usato da `aiSwissknife.createArtifact`
  (`src/extension.ts:456-493`) — riutilizzare direttamente la logica di quel flusso (estrarla
  in una funzione invocabile se attualmente è solo inline nella registrazione del
  comando, invece di duplicarla dentro `dashboard.ts`).
- JS lato client: logica di cambio sezione (mostra/nascondi i contenitori di sezione,
  segna il tab attivo) — semplice show/hide sul DOM, nessun framework.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- Manuale: aprire la Dashboard, confermare che tutti e quattro i tab vengano renderizzati, che il cambio
  di tab mostri/nasconda il contenitore corretto, e che il contenuto del tab **Installed**
  e ogni azione esistente (filtri, selezione riga, pannello di
  dettaglio, Copy/Move/Edit/diff/Promote — tutto ciò che proviene dall'Iniziativa 26)
  si comporti in modo identico a prima di questo task — si tratta di un puro riposizionamento,
  verificato percorrendo con clic gli stessi flussi coperti dalla verifica manuale
  delle Iniziative 26/27.
- Manuale: `+ New Artifact` apre `FormEditorPanel` in modalità creazione
  in modo identico al comando `Create Artifact` della sidebar.
