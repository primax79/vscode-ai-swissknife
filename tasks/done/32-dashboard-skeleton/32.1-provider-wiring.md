# 32.1 — Cablaggio dei provider

**Depends on:** nulla oltre all'attuale `main` (riverificare prima che la Fase 8/29 sia
stata integrata — vedere `plan.md`).

## Perché

In `DashboardPanel`, il costruttore e `render` (`src/ui/dashboard.ts:21,114`)
accettano solo `InstalledTreeDataProvider`; entrambi i punti di chiamata in `extension.ts`
(`:550,552`) passano solo quello. Ogni nuova sezione nelle Iniziative 33/34 ha bisogno di
`SourcesTreeDataProvider`/`AvailableTreeDataProvider` nello scope, più un modo
per attivare lo stesso aggiornamento della barra di stato e dei provider della sidebar che i comandi
mutanti della sidebar stessa già eseguono (`specs/phase-9-spec.md` §4.1).

## Ambito

- `src/ui/dashboard.ts`: in `DashboardPanel` il costruttore privato e `static render`
  acquisiscono i parametri `sourcesProvider: SourcesTreeDataProvider`,
  `availableProvider: AvailableTreeDataProvider` e
  `refreshCallback: () => void` (oppure una piccola interfaccia che li raggruppa
  — scegliere la soluzione più leggibile una volta davanti alla firma del
  costruttore). Memorizzare tutti e tre come campi privati, seguendo il pattern del campo
  esistente `_provider`.
- `src/extension.ts`: entrambi i punti di chiamata `DashboardPanel.render(...)`
  (`:550,552`) passano `sourcesProvider`, `availableProvider` e una callback
  collegata alla stessa logica di refresh che `updateStatusBar()` e le chiamate
  `refresh()`/`refreshCatalog()` dei tree provider stessi usano già dentro
  `activate()` (`:335` per `updateStatusBar`, rieseguire grep per i suoi punti di chiamata
  esatti dopo i comandi mutanti — probabilmente accanto a `installedProvider.refresh()`/
  `availableProvider.refreshCatalog()` in ciascuna registrazione di comando). Non
  incorporare inline la logica di refresh una seconda volta dentro `dashboard.ts` — passare
  le closure esistenti, oppure estrarle in una piccola funzione con nome in
  `extension.ts` se non lo sono già, e passare quella.
- Nessun nuovo messaggio webview né modifiche alla UI in questo task — puramente costruttore/cablaggio.
  Il comportamento effettivo di `DashboardPanel` resta invariato; i nuovi campi rimangono
  inutilizzati fino alle Iniziative 33/34 (un campo privato non ancora letto va
  bene qui, poiché costituisce la base necessaria per ciò che segue).

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` tutti
  verdi.
- Manuale: aprire la Dashboard tramite `aiSwissknife.openDashboard` e tramite
  `aiSwissknife.openInDashboard` (il salto filtrato per sorgente, entrambi i punti di
  chiamata in `extension.ts:550,552`) — entrambi devono continuare ad aprirsi correttamente senza
  alcun errore a runtime, dimostrando che i nuovi parametri sono propagati attraverso entrambi i
  percorsi e non solo uno.
