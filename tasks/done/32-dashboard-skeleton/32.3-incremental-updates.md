# 32.3 — Incremental update model

**Depends on:** 32.2 (merged).

## Why

`DashboardPanel.update()` (`src/ui/dashboard.ts:238-302`, specifically
`:271`) reassigns `this._panel.webview.html` wholesale on every
`refresh`/`checkDrift`/filter-driven update, already resetting scroll
position today. Both spec reviews flagged that lazy catalog expansion,
collapsible groups, and per-section state (Initiative 33/34) make a
full-DOM-replace model actively lossy — open/closed state, scroll
position, in-progress search text, and any expanded catalog nodes would
all reset on every mutation (`specs/phase-9-spec.md` §3.4).

## Scope

- `src/ui/dashboard.ts`: change `update()` so it **only** calls
  `this._panel.webview.html = ...` once, the first time the panel is
  created (already effectively true via the constructor's `this.update()`
  call at `:111` — confirm whether `update()` is ever called again after
  panel creation in a way that currently *needs* a full HTML replace, e.g.
  after `addSource`/`removeSource` from Initiative 33, and change those
  call sites to send data via `postMessage` instead).
- Extend the existing `driftResult`/`scanComplete` message-handling
  pattern (`:984-1044` client-side) — which already updates specific DOM
  nodes in place rather than replacing the page — to the Installed
  table's own data refresh (today, `refresh`/`checkDrift` still trigger a
  full `getHtml()` regeneration per `:29-34`; change these to send a
  `inventoryData` message with the new managed/observed arrays, and have
  client-side JS re-render just the `<tbody id="unifiedTable">` rows from
  that data, reusing the existing `rowsHtml`-building logic ported to the
  client side, or kept server-side and sent as a pre-rendered HTML
  fragment via `postMessage` — pick whichever keeps the diff smaller,
  document the choice in the commit message since Initiative 33/34 will
  follow the same pattern for their own sections).
- This is the general pattern Initiative 33 (`catalogData`) and 34
  (`recommendationsData`) will reuse — get it right here with the one
  section that already exists (Installed) before three more sections
  adopt it.

## Verification

- `npm run typecheck && npm run lint && npm test && npm run build` all
  green.
- Manual: scroll the Installed table, expand a row's detail panel, then
  trigger `refresh` — confirm scroll position and the open detail panel
  survive (today, per `specs/phase-9-spec.md` §3.4, they do not). This is
  the concrete, testable proof the incremental model actually replaced
  the lossy one, not just that the code compiles.
- Manual: trigger `checkDrift` mid-scan, confirm the existing
  scan-in-progress → `scanComplete` flow (`:280-301`, `:1001-1005`) still
  behaves identically — this task changes *how* data reaches the DOM, not
  the drift-check behavior itself.
