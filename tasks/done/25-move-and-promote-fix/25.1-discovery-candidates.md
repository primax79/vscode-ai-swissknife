# 25.1 — Discovery: collect all match candidates

> Part of [Move action + Promote disambiguation fix](plan.md) · spec: [../specs/phase-6-spec.md](../../specs/phase-6-spec.md) §2, §3, §4.4

## Goal

Fix the real bug Codex found and confirmed against the code: discovery's
matching loop (`src/engine/discovery.ts:216-306`) keeps only one `match`,
overwritten as it scans registered sources — an `identical` hit `break`s
immediately (first found wins), a `different` hit does **not** break, so a
*later* source with the same `kind+name` silently overwrites an earlier
one with no disambiguation ever offered (confirmed: today it keeps the
**last** `different` candidate). This task makes it collect **all**
candidates instead.

This task must produce one commit containing only its changes.

## Steps

1. Change the loop in `src/engine/discovery.ts` (lines ~216-306) to build a
   `candidates: { sourceId: string; packageId: string; artifactId: string;
   sourceRevision?: ResolvedRevision; status: 'identical' | 'different' }[]`
   array instead of a single overwritten `match` variable — every source
   that resolves an artifact with matching `kind+name` contributes one
   entry, whether `identical` or `different`. Remove the early `break` on
   `identical` — it must keep checking remaining sources so multi-candidate
   cases are fully captured.
2. Also remove the "stop after first artifact hit within one source" early
   exit if present in the inner package/artifact loop — a source with
   multiple packages that each happen to contain a matching artifact should
   contribute multiple candidates too (unlikely in practice, but the loop
   must not silently stop early).
3. Extend source-type coverage to all 5 types: today only
   `local-folder`/`git-custom`/`git-marketplace` are attempted
   (`src/engine/discovery.ts:224-240`) — add `git-single-item` and
   `remote-url` resolution attempts using the same resolvers `plan.ts`
   already imports (`resolveGitSingleItem`/`resolveArtifactContent` from
   `src/sources/gitSingleItem`, `resolveRemoteUrl`/`resolveArtifactContent`
   from `src/sources/remoteUrl`). If a source type's resolution fails
   (network error, etc.), it simply contributes no candidate — same
   existing swallow-and-continue behavior, do not add new error surfacing
   here.
4. Add `candidates` as a new field on `ObservedArtifact`
   (`src/domain/types.ts` or wherever `ObservedArtifact`/`ObservedSourceMatch`
   are defined) — keep the existing `match` field too, but re-derive it
   from `candidates` as "first `identical`, else first candidate" (this is
   a small, intentional change from today's "last different wins" for the
   existing badge rendering — call this out explicitly in the commit
   message, it's not a no-op).
5. Do **not** touch `promoteObservedArtifact`, `Promote`'s UI, or
   `promoteAllIdentical` in this task — those are 25.2/25.3.

## Verification

- Add test cases proving: two sources with `identical` content for the
  same `kind+name` both appear in `candidates` (previously the loop would
  `break` after the first); two sources with `different` content both
  appear in `candidates` in scan order (previously only the last survived);
  a `git-single-item`/`remote-url` source now contributes a candidate
  (previously silently skipped); the re-derived `match` field matches the
  "first identical, else first candidate" rule against a fixture with mixed
  candidates.
- Run full test suite, lint, typecheck, build.
