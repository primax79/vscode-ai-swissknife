# 20.2 — `remote-url` resolver

> Part of [`remote-url` & `git-single-item` sources](plan.md) · spec: [../specs/phase-4-spec.md](../../specs/phase-4-spec.md) §6

## Goal

Implement the `remote-url` `SourceType` (already in the union, no resolver
yet): a single file or small manifest fetched over plain HTTP(S) — no Git
involved (e.g. a raw gist/file URL).

This task must produce one commit containing only its changes.

## Grounding

- `Source.url` field already exists (`src/domain/types.ts`) — this
  resolver is the first to actually use it for a non-git fetch.
- Caching convention to match: whatever cache-directory scheme
  `gitCustom.ts`/`gitMarketplace.ts` already use (`cacheDir` option, see
  `GitMarketplaceResolveOptions` in `src/sources/gitMarketplace.ts`) — reuse
  the same base directory convention, a different subpath.
- Resolution output shape: `SourceResolution`, `DetectionDiagnostic`
  (`src/sources/types.ts`).

## Steps

1. In `src/sources/remoteUrl.ts`, fetch `Source.url` over HTTPS (Node's
   built-in `https`/global `fetch`, no new dependency), detect content kind
   from the fetched body the same way `gitSingleItem` (20.1) does for a
   checked-out root (try `SKILL.md`-shaped frontmatter, then agent/command,
   then MCP JSON) — share the detection logic with 20.1 rather than
   duplicating it if 20.1 lands first (check `20-remote-url-and-single-item-sources`'s
   sibling task before writing a second detector).
2. Content-hash based re-fetch: store the last-seen hash (or ETag if the
   server sends one) alongside the cached file; skip re-download on refresh
   if unchanged, matching the "diff against previous cache" behavior
   `SPEC.md` §2 already requires for catalog refresh generally.
3. Reject non-HTTPS URLs by default (HTTP only if the user's `Source`
   explicitly opts in — treat plain HTTP as a trust boundary worth flagging,
   not silently allowed) and cap response size to avoid pulling down an
   unbounded file.
4. Produce exactly one `Package`/`Artifact`, same degenerate-package
   shape as 20.1.
5. Add unit tests against a local fixture server (or a stubbed fetch) — no
   live network call in the test suite, per the "portable tests" convention.
