# 19.3 — Politica di merge non distruttiva per `rule`

> Parte di [Tipo `hook` + merge attivo di `rule`](plan.md) · spec: [../specs/phase-4-spec.md](../../specs/phase-4-spec.md) §5

## Goal

Trasformare `rule` da "adapter esistente, dormiente" (voce di `CONTEXT.md` "`rule` is
deferred to Phase 2") in una destinazione effettiva di installazione/sincronizzazione, usando una
politica di merge non distruttiva invece di sovrascrivere integralmente
`CLAUDE.md`/`AGENTS.md`/`copilot-instructions.md`, secondo la politica
in `phase-4-spec.md` §5: blocco gestito delimitato
(`<!-- ai-swissknife:managed:<sourceId> -->` … `<!-- /ai-swissknife:managed -->`),
accodato se assente, sostituito sul posto se già presente, senza mai toccare
il contenuto circostante.

Questo task deve produrre un singolo commit contenente solo le proprie modifiche.

## Riferimenti nel codice

- Adapter dormiente esistente: `src/translator/rule.ts` (`translateRule`,
  attualmente senza perdita per `claude-code`/`kilo-code`, `unsupported` altrimenti
  — mantenere quella logica di traduzione; questo task aggiunge lo strato di merge attorno
  all'installazione/applicazione, non una nuova traduzione).
- Perché era bloccato in precedenza: voce di `CONTEXT.md` "`rule` is deferred to Phase
  2" — installare una regola in modo sicuro richiede esattamente questa politica
  di merge/composizione, che finora non esisteva.
- Pattern di apply/verify da estendere: `src/engine/apply.ts` — `rule` richiede una
  strategia di scrittura distinta (merge in un file esistente) invece della
  strategia di creazione/sovrascrittura del file usata da ogni altro tipo; lasciare intatto
  il percorso di apply degli altri tipi.

## Steps

1. Implementare la funzione di merge (es. `mergeRuleContent(existing: string,
   sourceId: string, newContent: string): string` in `src/translator/rule.ts`
   o in un nuovo `src/engine/ruleMerge.ts`): trovare il blocco gestito esistente per
   `sourceId` se presente e sostituire solo quel blocco; altrimenti accodare un nuovo
   blocco alla fine del file (creando il file se non esiste ancora).
2. Collegare `rule` in `planInstall`/`applyInstall` (`src/engine/plan.ts`,
   `src/engine/apply.ts`): il piano produce un diff del *risultato del merge*, non
   solo del nuovo blocco, in modo che l'anteprima mostri esattamente cosa cambia nel file
   di destinazione; apply chiama la funzione di merge invece di una semplice scrittura, passando comunque
   per la stessa transazione di scrittura atomica/rollback usata da ogni altro tipo
   (gli invarianti del gate di consolidamento in `CONTEXT.md` si applicano invariati).
3. Aggiornare in `src/engine/types.ts` l'unione `PreparedInstall` se il ramo `rule`
   non restituisce già contenuto utilizzabile (il tipo precede questo task poiché
   `rule` era dormiente — verificare prima di dare per scontato che non richieda modifiche).
4. Aggiungere unit test: installazione in un file che non esiste ancora (lo crea),
   in un file con contenuto preesistente non correlato (accoda, lasciando intatto il contenuto
   esistente) e aggiornamento sul posto (sostituisce solo il proprio blocco gestito
   precedente, lasciando intatti il blocco di un secondo sourceId e tutto il contenuto
   circostante).

## Verification

- Eseguire l'intera suite di test, lint, typecheck, build.
- Installare manualmente una `rule` in un progetto che ha già un `CLAUDE.md` scritto
  a mano e verificare che il contenuto scritto a mano rimanga identico byte per byte dopo
  l'installazione, con il solo nuovo blocco gestito accodato.
