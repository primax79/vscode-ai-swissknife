# 22.3 — "Install Recommended" command + Available-view "Recommended" filter

> Part of [Project-scoped recommended installations](plan.md) · spec: [../specs/project-recommendations.md](../../specs/project-recommendations.md) §4.4

## Goal

Give curators and teammates an always-available way to see and install
whatever the project recommends, independent of any workspace-open
notification — mirrors VS Code's own always-available "Show Recommended
Extensions" command. This is also where actual source resolution (network
access) for recommendations happens for the first time — deliberately never
triggered automatically on workspace open (see 22.4 and the spec's
local-only-on-open locked-in decision).

Depends on 22.2. Must land before 22.4, which reuses this task's Recommended
filter (`Review` action) and install-runner (`Install All` action) — the
original plan had this backwards; do not resurrect that ordering.

This task must produce one commit containing only its changes.

## Steps

1. Add command `aiSwissknife.installRecommended` to `package.json` and
   `src/extension.ts`, exposed on the Sources view toolbar (`"view/title"`
   contribution, same mechanism as existing toolbar buttons) and command
   palette.
2. Handler:
   - `readManifest('project', root)`, `readState('project', root)`.
   - For each distinct `sourceId` referenced in `desiredInstallations`,
     resolve it (reuse whichever per-type resolver
     `src/ui/availableView.ts` already calls — `resolveGitCustom`,
     `resolveLocalFolder`, etc., per `src/sources/*`), building the
     `Map<string, SourceResolutionAttempt>` shape 22.2 expects: a
     successful resolution → `{ status: 'resolved', source, packages }`; a
     thrown/rejected resolution → `{ status: 'failed', source, error:
     String(err) }` (never let one failed source abort resolving the
     others).
   - Call `resolveRecommendations` (22.2).
   - Show a preview listing `pending` (installable, grouped by target
     assistant) and `broken` (informational rows, each showing its specific
     `BrokenReason`) — do not attempt to install `broken` entries.
3. On confirm — **not before** — re-read `readState('project', root)` and
   re-filter `pending` against it, dropping anything that became satisfied
   in the interim (e.g. the user manually installed it from the Available
   view while the preview from step 2 was still on screen). This handler is
   reused as-is by 22.4's `Install All` action, where the gap between the
   open-time check and the user clicking "Install All" can be arbitrarily
   long — a stale `pending` list must not be installed unchecked.
4. Install the (freshly re-filtered) `pending` list via a small new shared
   function, e.g.
   `installResolvedArtifacts(items: { artifact: Artifact; pkg: Package;
   source: Source; targetAssistant: AssistantId; targetScope: Scope }[])`,
   calling `planInstall`/`applyInstall` directly (`src/engine/index.ts`) per
   item's own `targetAssistant`/`targetScope: 'project'` — **do not** route
   through `installBatch` (`src/ui/availableView.ts:470-548`), which is
   `private` and prompts once for a single assistant/scope for the whole
   batch; recommendations already carry a specific assistant per entry.
   Keep the existing plan→preview→apply→verify sequence intact per item —
   this new function is a thinner caller of the same engine functions
   `installBatch` also calls, not a bypass of them.
5. Add a "Recommended" top-level grouping to the Available view: a new
   root-level tree node (sibling to the existing per-source
   `AvailableSourceGroupItem` groups from `buildHierarchy`,
   `src/ui/availableView.ts:73`) populated from the same `pending`/`broken`
   data computed in step 2 — do not modify `buildHierarchy`'s per-source
   logic itself.

## Verification

- Unit test the handler's resolve step using 22.2's fixtures plus fake
  resolvers (some resolving, one throwing) to confirm the resulting
  `SourceResolutionAttempt` map is built correctly and a single failing
  source doesn't prevent others from resolving.
- Unit test `installResolvedArtifacts`: given a mixed list of
  `targetAssistant`/`targetScope`, assert `planInstall`/`applyInstall` are
  invoked once per item with that item's own target, not a single shared
  target for the whole list.
- Extend `src/ui/ui.test.ts`-style tests for the new "Recommended" grouping:
  given a hierarchy and a `desiredInstallations` list, assert only matching
  artifacts appear under the grouping, and `broken` entries render as
  non-actionable rows with their specific reason text.
- Run full test suite, lint, typecheck, build.
- Manually in the Extension Development Host: run "Install Recommended"
  from the Sources view toolbar with a mix of installed, pending, and
  intentionally-broken (e.g. a recommendation pointing at a removed
  artifact) recommendations; confirm the preview separates them correctly
  and only `pending` items get installed, each onto its own recommended
  assistant.
