# 26.2 — Per-item detail panel + value-based action handlers

> Part of [Dashboard rebuild](plan.md) · spec: [../specs/phase-6-spec.md](../../specs/phase-6-spec.md) §3, §4.5

## Goal

Selecting a row opens a detail section showing origin, diff availability,
cross-framework presence, and the relevant actions — the integration point
where initiatives 23, 24, and 25 land in the UI. Depends on 26.1, 23.3
(cross-framework lookup), 24.1 (diff availability), and 25.2/25.5
(Promote/Move actions) all having landed and merged.

This task must produce one commit containing only its changes.

## Steps

1. Add a new request/response webview message protocol: clicking a row
   posts `{command: 'requestDetail', key}` (same key format as the existing
   `data-drift-key`); the extension host responds with `{command:
   'itemDetail', key, origin, diffAvailable, crossFramework, candidates}`
   computed on demand by calling into 23.3's `findRelatedInstallations` and
   checking 24.1's diff-applicability conditions. The existing
   `driftResult`/`scanComplete` messages are insufficient for this (they
   only carry a key and a status string) — this is a genuinely new
   protocol addition, not an extension of those.
2. Render the detail section (same webview, a panel that appears below or
   beside the table) showing: **origin** (source id + commit when tracked,
   from `sourceRevision`; "local, no known origin" when absent), a **"Diff
   vs. original"** button when `diffAvailable` (invokes 24.1's command),
   the **cross-framework "installed also in"** list (each entry showing
   assistant + scope, with a dashed-border/`?` visual treatment for
   `name-fallback` matches per the spec's "probable, not certain"
   requirement — never rendered identically to a `provenance` match), and
   action buttons: `Promote` (only if the item is unmanaged and has
   candidates — reuse 25.2's bucket logic), `Copy to...`, `Move to...`
   (only for managed items, only for `skill`/`agent`/`command`/
   `mcp-server` per 25.5's scoping), `Edit` (already exists).
3. `syncItem`/`promoteItem`/`editItem`/the new `moveItem` (25.5) currently
   take real class instances (`InstalledInstallationItem`/
   `ObservedArtifactItem`) and branch on `instanceof`
   (`src/ui/installedView.ts`) — a webview message only ever carries a
   plain serialized object. Add value-based variants of each (accepting a
   plain `ManagedInstallation`/`ObservedArtifact` object directly, doing
   the same work the class-based versions do) shared between the sidebar's
   commands and the Dashboard's message handlers — do not duplicate the
   underlying logic, factor out a shared implementation both the
   class-based and value-based entry points call.
4. Wire the Dashboard's new action buttons to post the corresponding
   message (`copyItem`/`moveItem`/`promoteItem`/`editItem`) with the plain
   item payload; the extension host's `onDidReceiveMessage` handler
   (`src/ui/dashboard.ts`) dispatches to the value-based implementations
   from step 3.

## Verification

- Manual verification: select a managed item with a known cross-framework
  match — confirm the detail panel shows it correctly with the right
  match-strategy visual treatment; select an unmanaged item with candidates
  — confirm Promote works from the detail panel and produces the same
  result as the sidebar's equivalent action; perform a Copy and a Move from
  the detail panel, confirming both work identically to their sidebar
  counterparts.
- Run full test suite, lint, typecheck, build.
