# 26.1 — Unified table + filter bar + breadcrumb

> Part of [Dashboard rebuild](plan.md) · spec: [../specs/phase-6-spec.md](../../specs/phase-6-spec.md) §3, §4.5

## Goal

Replace the Dashboard's two structurally different tables (managed vs.
unmanaged, different columns — `src/ui/dashboard.ts:189-245`) with one
unified row model and a real filter bar, since "riepilogo globale" and
"vista per framework" must be the same filtered state, not two views.
Depends only on initiative 16 (already merged) — dispatch independently of
23-25.

This task must produce one commit containing only its changes.

## Steps

1. In `src/ui/dashboard.ts`'s `getHtml`, merge the `managedRows`/
   `observedRows` generation (lines 189-245) into one row-generation
   function over a combined list of managed + unmanaged items. Each row
   carries one status badge encoding **both** membership and drift/match
   state, e.g.: "● Managed · up to date" (`badge-success`), "● Managed ·
   update available" (`badge-info`), "● Managed · modified locally"
   (`badge-warning`), "◌ Unmanaged · identical to X" (`badge-success`
   variant), "◌ Unmanaged · differs from X" (`badge-warning` variant),
   "◌ Unmanaged · local only" (`badge-unmanaged`). Keep the existing
   `data-drift-key`/`data-kind`/`data-name` row attributes (needed by the
   existing progressive-scan `driftResult` message handling and the
   existing search/kind-tab filtering) — extend them with whatever new
   data attributes the new filters below need (e.g. `data-assistant`,
   `data-scope`, `data-membership`).
2. Add a filter bar above the table with: **Environment** (`All` plus one
   pill per assistant actually present in the current data — reuse
   `getAssistantIconPath`, `src/ui/assistantIcons.ts`, which returns
   filesystem `Uri`s meant for `TreeItem.iconPath` — the webview needs
   `webview.asWebviewUri(...)` instead, so give `DashboardPanel` access to
   `extensionUri` (pass it into the constructor/`render()`, mirroring how
   `AvailableTreeDataProvider`/`InstalledTreeDataProvider` already take it)
   and set `localResourceRoots` on the webview options so
   `asWebviewUri` resolves correctly for the icon files under
   `resources/`), **Scope** (All/Global/Project), **Membership**
   (All/Managed/Unmanaged), **Kind** (already exists as tabs — keep), plus
   the existing free-text search.
3. Add a breadcrumb line above the table showing the active filters as
   removable chips (e.g. "Claude Code ✕ · Project ✕ · Managed ✕") — clicking
   a chip's ✕ clears that one filter; the default (all filters at `All`) is
   the "global summary" state.
4. Stats ribbon (`updatesAvailable`/`modifiedLocally`/etc.) recomputes from
   the currently filtered subset client-side (matching how `filterTable()`
   already toggles row visibility, `src/ui/dashboard.ts`'s existing script)
   — do not require a round-trip to the extension host just to update
   counts on a filter change.
5. **Escape all interpolated dynamic strings** (names, paths, match
   details) before inserting them into HTML — do not carry forward the
   current unescaped-interpolation pattern into the larger unified table.
   Do not embed raw `JSON.stringify` output directly inside a `<script>`
   tag unescaped (current pattern at `src/ui/dashboard.ts:541`) — escape
   `<` in the JSON output, or pass data via a `data-*` attribute parsed
   with `JSON.parse` client-side instead.
6. Update `src/ui/ui.test.ts`'s existing Dashboard tests (around lines
   462-531) that assert the old two-table structure/attributes (e.g.
   `data-drift-key="claude-code:project:demo-skill"`, `#scan-indicator`) to
   match the new unified structure — do not leave them asserting a
   structure this task removes.

## Verification

- Manual verification: open the Dashboard with a mix of managed and
  unmanaged items across at least two assistants and both scopes; confirm
  the unified table renders correctly, each filter narrows the row set as
  expected, the breadcrumb reflects active filters and each chip's ✕
  actually clears that filter, and the stats ribbon updates accordingly.
- Confirm the existing progressive-scan behavior (fast initial render,
  `driftResult`/`scanComplete` messages patching the unified table's
  status badges) still works against the new row structure.
- Run full test suite (including the updated Dashboard tests), lint,
  typecheck, build.
