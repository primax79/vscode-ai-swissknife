# 02.1 — Tipi di dominio fondamentali

> Parte di [Tipi di dominio + store del registro](plan.md) · specifica: [../specs/foundations.md](../../specs/foundations.md)

**Obiettivo**: definire ogni entità fondamentale della specifica come
interfacce/tipi TypeScript in `src/domain/types.ts` — solo interfacce, nessuna
funzione, nessun I/O, nessuna logica.

**Riferimenti nel codice**: `SPEC.md` §1 "Domain model" (radice del repository,
un livello sopra `tasks/`) è la fonte autorevole per ogni campo sottostante —
leggerlo per intero prima di scrivere qualsiasi tipo; non inventare campi che
non menziona e non omettere campi che menziona solo perché non sono ancora usati
dagli adapter della Fase 1 (ad es. `Package.nativeFormat` serve al modello di
dominio anche se gli adapter di questa Fase lo toccano appena).

Passaggi:

1. Creare `src/domain/types.ts` con:
   - `type AssistantId = 'claude-code' | 'kilo-code' | 'github-copilot' |
     'codex-cli' | 'gemini-cli';` — un'unione di stringhe, non un enum (coerente
     con la nota sull'estensibilità di SPEC.md §1; nuovi assistenti si
     aggiungono estendendo l'unione, non tramite un registro a runtime in questo
     task).
   - `type Scope = 'global' | 'project';`
   - `type ItemKind = 'skill' | 'agent' | 'command' | 'mcp-server' |
     'rule' | 'hook';` — tutti e 6, secondo la decisione condivisa di questa
     iniziativa (vedere `plan.md`), anche se solo `skill`/`rule` sono
     implementati in questa Fase.
   - `type SourceType = 'git-custom' | 'git-marketplace' | 'local-folder'
     | 'remote-url' | 'git-single-item';`
   - `interface Source { id: string; type: SourceType; scope: Scope;
     projectPath?: string; url?: string; localPath?: string; branch?:
     string; tag?: string; commit?: string; name?: string; }` — `url`/
     `localPath` sono mutuamente esclusivi a seconda di `type`; `branch`/
     `tag`/`commit` costituiscono il pin `git-custom` (SPEC.md §1). `projectPath`
     è impostato solo quando `scope === 'project'` ("a project-level
     Source must never leak into other workspaces" in SPEC.md).
   - `interface Package { id: string; sourceId: string; version?: string;
     nativeFormat: string; artifacts: Artifact[]; }` — `nativeFormat` è un tag
     stringa a formato libero come `"claude-plugin"`/`"kilo-skill-dir"`, non
     ancora un enum (non vincolarlo eccessivamente in questo task; un'iniziativa
     successiva potrà restringerlo una volta implementati più formati).
   - `interface Artifact { id: string; packageId: string; kind: ItemKind;
     name: string; description?: string; nativeFormat: string; }`.
   - `interface ObservedArtifact { assistant: AssistantId; scope: Scope;
     projectPath?: string; kind: ItemKind; name: string; path: string;
     discoveredAt: string; }` — `discoveredAt` è una stringa timestamp ISO.
   - `interface ManagedInstallation { assistant: AssistantId; scope:
     Scope; projectPath?: string; kind: ItemKind; name: string; path:
     string; sourceId?: string; packageId?: string; artifactId?: string;
     installedVersion?: string; installedAt: string; contentHash?:
     string; }` — `contentHash` è ciò che SPEC.md §3.6 chiama "a hash/snapshot
     saved at apply time" per il successivo rilevamento del drift; predisporre
     il campo ora anche se nulla calcola ancora il drift (Fase 3).
   - `type ConversionDiagnostic = 'lossless' | 'adapted-with-warning' |
     'potentially-destructive' | 'unsupported';` (SPEC.md §2/§4).
   - **Non** definire `DesiredManifest` o `LocalState` in questo task —
     SPEC.md §1 li definisce concettualmente ma nulla nella Fase 1 li legge o
     scrive ancora (rappresentano la separazione condivisibile-vs-locale di
     `.ai-toolkit/registry.json`, rilevante quando arriveranno i flussi di
     sync/team in una fase successiva). Aggiungere tipi inutilizzati ora sarebbe
     solo peso morto; un'iniziativa successiva li introdurrà insieme al loro
     primo vero consumatore.
2. Esportare ogni tipo/interfaccia sopra da `src/domain/types.ts` (nessun
   default export; solo named export).
3. Eseguire `npm run typecheck` — deve passare con zero errori (nulla importa
   ancora questo file, quindi questo conferma semplicemente che il file stesso è
   TypeScript sintatticamente e strutturalmente valido).

**Verifica**: `npm run typecheck` e `npm run lint` terminano entrambi con
codice 0. Revisione del diff: ogni campo nel file è riconducibile a una frase
specifica in `SPEC.md` §1 — se è stato aggiunto un campo che non è lì,
rimuoverlo o giustificarlo nel messaggio di commit. Un unico commit contenente
solo `src/domain/types.ts`.
