# 24.1 — Comando di diff rispetto all'originale

> Parte di [Diff rispetto all'originale + anteprima prima dell'installazione](plan.md) · spec: [../specs/phase-6-spec.md](../../specs/phase-6-spec.md) §3, §4.2

## Goal

Un nuovo comando che mostra un diff reale tra un elemento installato/rilevato e
il suo originale risolto, usando l'accessor condiviso resolve+translate
dell'iniziativa 23 (23.1/23.2) invece di qualsiasi risoluzione ad hoc. Dipende dal
completamento e dall'unione di 23.2.

Questo task deve produrre un singolo commit contenente solo le proprie modifiche.

## Steps

1. Aggiungere un nuovo comando (es. `aiSwissknife.diffAgainstOriginal`) disponibile:
   - Da `InstalledInstallationItem` quando lo stato del suo report di drift è
     `modified-locally` o `modified-and-update-available`
     (`src/ui/installedView.ts`, tipo `DriftReport` in
     `src/engine/types.ts`).
   - Da `ObservedArtifactItem` quando `observed.match?.status === 'different'`
     (`src/engine/discovery.ts`).
2. Il gestore risolve l'"originale" tramite l'accessor condiviso di 23 (chiamato ex novo —
   non esiste alcun contenuto in cache da riutilizzare, secondo la correzione esplicita della specifica):
   per un elemento gestito, risolvere+tradurre dalla sorgente registrata corrispondente al suo `sourceId`/`artifactId`
   nel formato nativo dell'assistente; per un elemento non gestito,
   risolvere+tradurre usando i campi `sourceId`/`packageId`/
   `artifactId` corrispondenti da `observed.match`.
3. Per `skill` (una directory, non un singolo file): eseguire il diff solo del contenuto del file
   principale `SKILL.md`; se differiscono anche eventuali file di risorse, mostrare un
   semplice messaggio informativo che li elenca (non un diff a livello di cartella).
4. Per `rule`: eseguire il diff del blocco delimitato estratto
   (`<!-- ai-swissknife:managed:${sourceId} -->` … `<!-- /ai-swissknife:managed -->`,
   vedere i marcatori già usati nel percorso di apply delle rule in `src/engine/apply.ts`)
   rispetto al contenuto tradotto della regola canonica — non dell'intero file
   condiviso.
5. Per `mcp-server`: eseguire il diff della voce JSON specifica per l'`id` di questo server
   rispetto all'originale tradotto — non dell'intero file di configurazione condiviso.
6. Per ogni altro tipo (`agent`, `command`), eseguire il diff dell'intero file — è
   già un'unità autonoma.
7. Usare `vscode.diff(leftUri, rightUri, title)`. Il lato "originale" non ha alcun
   file reale su disco — scriverlo in un `TextDocumentContentProvider` sotto uno
   schema personalizzato (es. `ai-swissknife-diff:`) invece che in un file temporaneo su
   disco, in modo che non rimanga alcun residuo dopo la chiusura dell'editor di diff.
8. Secondo la decisione fissata per cui "originale significa l'upstream corrente": non
   tentare di risolvere l'esatto `sourceRevision.commit` che era stato installato
   — risolvere ciò che la sorgente restituisce attualmente. Nessuna gestione speciale per
   `modified-and-update-available` oltre a ciò che il diff mostra naturalmente
   (il delta combinato locale+upstream è previsto e accettabile per questo
   passaggio).

## Verification

- Verifica manuale: installare una skill, modificare a mano il suo `SKILL.md` su disco,
  eseguire il controllo di drift, confermare che il nuovo comando di diff appaia e mostri un
  diff corretto. Ripetere per un `agent` o `command`. Se una fixture `rule`/`mcp-server`
  è facile da costruire, verificare specificamente il diff dell'unità estratta
  (non il diff dell'intero file condiviso).
- Testare con unit test tutta la logica pura isolabile (es. l'estrazione del blocco
  delimitato per `rule`, l'estrazione della voce JSON per `mcp-server`) senza
  richiedere l'editor di diff di VS Code stesso.
- Eseguire l'intera suite di test, lint, typecheck, build.
