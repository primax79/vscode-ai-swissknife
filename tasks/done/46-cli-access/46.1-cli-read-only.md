# 46.1 — Scheletro della CLI e comandi in sola lettura

Un task, un commit. Nessuna modifica ai file in `src/ui/`.

**Read first:** `../CONTEXT.md`, `plan.md` (il contratto), `esbuild.config.js`, `package.json` (`main`, `files`/`.vscodeignore`, `scripts`), `src/domain/registry.ts` (`readManifest`, `readState`, radici), `src/engine/{discovery,drift,plan,installMatrix}.ts`, `src/sources/registry.ts`, `src/adapters/registry.ts` (`getEnabledAdapters` ripiega su tutti gli adapter quando `vscode` è assente), e per il pattern `../vscode-mcp-dap-debugger/src/cli/` (uso di commander, stdout di solo JSON) senza copiarne le parti MCP.

## Cosa fare

1. **Build**: un secondo punto di ingresso esbuild `src/cli/main.ts` -> `dist/cli.js` (node, cjs, shebang), voce `bin` `ai-swissknife` in `package.json`, inclusa nel vsix. Aggiungere `commander` come unica nuova dipendenza (indicarlo nel messaggio di commit). Un controllo in fase di build fallisce se `dist/cli.js` contiene `require('vscode')` o `from 'vscode'` in qualsiasi punto.
2. **Opzioni globali** secondo il contratto del piano (`--workspace`, `--home`, `--assistants`), un unico helper `emit(json)` / `fail(code, message)` così che stdout resti puro JSON, e codici di errore tipizzati (`INVALID_ARGUMENT`, `NOT_FOUND`, `SOURCE_RESOLUTION_FAILED`, `INTERNAL`).
3. **Comandi** (ciascuno restituisce JSON, documentato con un breve esempio in `--help`):
   - `sources` : sorgenti globali + del workspace con `{id, type, scope, url|localPath, branch|tag}`.
   - `catalog [--source <id>] [--kind <k>]` : risolve le sorgenti (usando i resolver irrobustiti) ed elenca gli artefatti `{sourceId, scope, packageId, artifactId, kind, name, description, version}`; i fallimenti delle singole sorgenti sono riportati dentro il risultato (`diagnostics`), non come fallimento globale.
   - `installed [--scope global|project] [--assistant <id>] [--kind <k>]` : elementi gestiti + osservati con `{key, kind, name, assistant, scope, membership, path, sourceId?, match?: identical|different}` (`scanInstalledInventory`).
   - `updates` : report di drift per ogni elemento gestito (`up-to-date | update-available | modified-locally | modified-and-update-available | missing-on-disk`).
   - `item <key>` : dettaglio: origine, posizioni in cui è installato, disponibilità del diff (nessun corpo del diff; aggiungere `--diff` per includere un diff unificato, con limite di dimensione).
   - `plan-install --source <id> --artifact <id> --assistants a,b --scopes global,project [--overwrite-check]` : il riepilogo di `planInstallMatrix` (new / conflict / unsupported con motivazioni per assistant x scope), **non applica mai nulla**.
4. I comandi non scrivono mai alcun file (verificarlo nei test facendo uno snapshot dell'albero temporaneo prima e dopo).

## Verification

`src/cli/cli.test.ts` che avvia `node dist/cli.js` (o importa le funzioni dei comandi) su fixture temporanee `--home` / `--workspace` costruite con gli helper di test esistenti: forma JSON di ciascun comando su una fixture con una sorgente local-folder ed elementi installati; il percorso di errore stampa l'errore JSON ed esce con codice diverso da zero; stdout contiene esattamente un documento JSON (eseguirne il parsing) e nient'altro anche quando una sorgente fallisce la risoluzione; il controllo su `dist/cli.js` di assenza di `vscode`; gli alberi temporanei sono identici byte per byte prima e dopo ogni comando di lettura. `npm test` verde, `npm run build` pulito (entrambi i bundle). Manuale: `node dist/cli.js installed --assistants claude-code` sulla home reale del proprietario stampa i suoi elementi reali (in sola lettura).
