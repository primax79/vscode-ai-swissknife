## Cosa fare

Tutti i comandi: solo pianificazione senza `--write` (stampano cosa accadrebbe, non modificano nulla), applicati con `--write`; tipi `hook` / `mcp-server` rifiutati a meno che non sia passato `--allow-code-kinds`; JSON su stdout secondo il contratto; ogni modifica ai file eseguita dentro `withStateLock`; ogni output di applicazione elenca i file modificati e, quando ha sovrascritto o rimosso qualcosa, dove è stata salvata la versione precedente.

1. **Estrarre nel motore** (senza `vscode`; i metodi della UI chiamano poi le funzioni estratte mantenendo comportamento e test invariati): `uninstallInstallation(inst, { mode: 'soft' | 'hard' })` (rimozione del record di stato + `softDeletePath` per soft, `fs.rm` per hard) e le mutazioni del manifest delle sorgenti `addSourceToManifest` / `removeSourceFromManifest` (validate con i validatori di 44.1/36.1, regola sull'id duplicato: `DUPLICATE_ID` a meno che non sia passato `--replace`).
2. `apply-install` con gli stessi argomenti di `plan-install` più `--overwrite`: ripianifica internamente con `planInstallMatrix`, applica solo le nuove destinazioni, risolve i conflitti solo con `--overwrite` (versione precedente nel cestino), restituisce gli esiti per destinazione.
3. `uninstall <key> [--hard]` (soft = sposta nel cestino è il comportamento predefinito; `--hard` è permanente e deve essere esplicito).
4. `source add <type> <location> [--id <id>] [--name <name>] [--scope global|project] [--replace]` (id/nome derivati con `deriveSourceDefaults` quando omessi) e `source remove <id> --scope ...`.
5. `update [<key>] [--all] [--scope] [--assistant] [--source] [--kind] [--include-modified]` costruito su `planUpdateAll` / `applyUpdateAll` (47.1): un singolo elemento per chiave oppure tutti; le copie modificate localmente vengono saltate a meno che non sia passato `--include-modified` (la loro versione precedente finisce nel cestino, come in 47.1); l'output per elemento aggiunge `oldRevision` / `newRevision` (il commit o la versione della sorgente registrati prima e dopo) e `changedFiles: { added, changed, removed }` (riusare l'helper di confronto dell'albero dei file scritto per `redistribute`; estrarlo in un modulo condiviso se lì è privato).
6. `trash list` (in sola lettura, entrambi gli scope, dal più recente), `trash restore <id> [--to <path>]` e `trash empty [--scope]` (gli ultimi due richiedono `--write`; il ripristino non sovrascrive mai e segnala un conflitto come errore tipizzato).

## Verification

Test su fixture temporanee: ogni comando viene rifiutato o eseguito in sola pianificazione senza `--write` e lascia l'albero temporaneo identico byte per byte; `hook`/`mcp-server` rifiutati senza `--allow-code-kinds`; `apply-install` applica le nuove destinazioni e salta i conflitti a meno che non sia passato `--overwrite`; `uninstall` soft sposta in `_deleted/` e `--hard` rimuove, e in entrambi i casi il record di stato scompare; `source add` rifiuta un URL non valido (casi negativi da 44.1) e un id duplicato; `update <key>` e `update --all` riportano `oldRevision`/`newRevision`/`changedFiles`; il ciclo completo `trash list` / `restore` restituisce i file identici byte per byte; due scrittori CLI concorrenti non perdono aggiornamenti; i test di disinstallazione / aggiunta / rimozione della UI continuano a passare senza modifiche (ora esercitano il motore estratto); `describe` elenca ogni nuovo comando. `npm test` verde (compila prima i bundle), `npm run build` pulito.
