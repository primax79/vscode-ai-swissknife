# 46.3 — Lock inter-processo per lettura-modifica-scrittura di manifest/stato

Un task, un commit. A livello di motore, nessuna UI. Prerequisito per qualsiasi scrittura da CLI (l'estensione e la CLI possono essere in esecuzione contemporaneamente).

**Read first:** `plan.md`, `src/domain/registry.ts` (`atomicWriteJson`, `readManifest`/`writeManifest`, `readState`/`writeState`), ogni pattern chiamante che legge e poi scrive (`grep -rn "writeManifest(\|writeState(" src`), `src/sources/gitCustom.ts` (il `gitCustomMutex` in-process come riferimento di stile).

## Cosa fare

`withStateLock(scope, projectRoot?, homeRoot?, fn)` in `src/domain/` usando un file di lock esclusivo accanto al manifest/stato (creazione `wx` con pid + timestamp, nuovi tentativi con backoff fino a un timeout, acquisizione dei lock obsoleti quando il pid è terminato o il lock è più vecchio di N secondi, sempre rilasciato in `finally`). Applicarlo alle sequenze di lettura-modifica-scrittura (i chiamanti che eseguono `readManifest`/`readState`, modificano, `write...`) avvolgendole, **senza cambiarne il comportamento**; le semplici letture restano prive di lock (le scritture sono già rinominazioni atomiche).

## Verification

Test con concorrenza reale in un singolo processo e con due processi node avviati che martellano lo stesso manifest temporaneo: N incrementi di un campo contatore da parte di due scrittori terminano con la somma esatta (fallisce senza il lock); un lock obsoleto (pid terminato) viene acquisito; un crash dentro `fn` rilascia il lock; l'errore di timeout è tipizzato. Test esistenti intatti e verdi. `npm test` verde, `npm run build` pulito.
