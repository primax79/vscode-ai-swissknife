# 46.3 — Cross-process lock for manifest/state read-modify-write

One task, one commit. Engine-level, no UI. Prerequisite of any CLI write (the extension and the CLI may run at the same time).

**Read first:** `plan.md`, `src/domain/registry.ts` (`atomicWriteJson`, `readManifest`/`writeManifest`, `readState`/`writeState`), every caller pattern that reads then writes (`grep -rn "writeManifest(\|writeState(" src`), `src/sources/gitCustom.ts` (the in-process `gitCustomMutex` for style).

## Do

`withStateLock(scope, projectRoot?, homeRoot?, fn)` in `src/domain/` using an exclusive lock file next to the manifest/state (`wx` create with pid + timestamp, retry with backoff up to a timeout, stale-lock takeover when the pid is dead or the lock is older than N seconds, always released in `finally`). Apply it to the read-modify-write sequences (the callers that `readManifest`/`readState`, change, `write...`) by wrapping them, **without changing their behaviour**; plain reads stay lock-free (writes are already atomic renames).

## Verification

Tests with real concurrency in one process and with two spawned node processes hammering the same temp manifest: N increments of a counter field from two writers end with the exact sum (fails without the lock); stale lock (dead pid) is taken over; a crash inside `fn` releases the lock; timeout error is typed. Existing tests untouched and green. `npm test` green, `npm run build` clean.
