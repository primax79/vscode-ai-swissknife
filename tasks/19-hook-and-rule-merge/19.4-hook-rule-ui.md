# 19.4 — UI integration for hook & rule

> Part of [`hook` kind + active `rule` merge](plan.md) · spec: [../specs/phase-4-spec.md](../specs/phase-4-spec.md) §5

## Goal

Expose both `hook` and `rule` as installable/browsable kinds across the
existing views, and verify the whole chain end-to-end — this is the task
that actually makes 19.2/19.3 reachable by a user, matching how initiatives
08-10 each closed with a UI-integration task.

This task must produce one commit containing only its changes.

## Steps

1. Extend the kind filters in `src/ui/availableView.ts`,
   `src/ui/installedView.ts`, and `src/ui/dashboard.ts`'s webview filter
   tabs to include `hook` and `rule` (currently limited to
   skill/agent/command/mcp per initiative 16's filter tabs).
2. Confirm source detection (`src/sources/detect.ts`) can surface `hook` and
   `rule` artifacts from `git-custom`/`local-folder` sources — add detection
   helpers analogous to `findAgentFiles`/`findCommandFiles` if missing.
3. Confirm the Form Editor (initiative 17) picks up `rule`'s single-body-field
   schema once 19.3 makes it a real install target (17 explicitly deferred
   `hook` and left `rule` schema defined but potentially untested end-to-end
   — close that gap here, don't silently leave it half-wired).
4. Add unit/integration tests exercising the full resolve→plan→preview→apply
   path for `hook` and for `rule` (merge case included), plus discovery
   (`ObservedArtifact`) recognizing both kinds.

## Verification

- Run full test suite, lint, typecheck, build.
- Manually: install a `hook` from a `git-custom` source onto Claude Code,
  confirm it lands at the path 19.1/19.2 confirmed; install a `rule` twice
  from the same source and confirm the second install updates the same
  managed block instead of duplicating it.
