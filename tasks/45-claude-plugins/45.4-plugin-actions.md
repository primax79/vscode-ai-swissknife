# 45.4 — Plugin actions: enable/disable, update, uninstall

One task, one commit. Depends on 45.3 and 42.3 (fixed inline trio and context menu rules).

**Read first:** `plan.md` (safety and uninstall decisions), `notes/45.1-findings.md` (scope semantics, non-interactive behaviour, side effects), `src/engine/claudeCli.ts`, 42.3 for where actions go.

## Do

1. `ClaudeCli` write functions: `enablePlugin(id, scope, projectPath?)`, `disablePlugin(...)`, `updatePlugin(id, ...)`, `uninstallPlugin(id, scope, projectPath?)`, each returning a typed result (`ok` | `failed(reason)`), run with the correct scope/cwd per the findings, never with `-y`.
2. UI actions on plugin places (sidebar and Dashboard, per 42.3 placement): **Enable/Disable** as one toggle (icon-only on rows, label in the detail panel), **Update** (enabled only when an update is available; "update available" comes from the CLI per the findings, otherwise from comparing with `list --available`), **Uninstall** (modal: "Uninstall plugin X from Claude (<scope>)? Claude removes it from its plugin cache."; no trash, no hard/soft choice).
3. After any action refresh the plugin list, show one result message, and tell the user that a running Claude session may need a restart/reload if the findings say so.
4. Failures show the CLI's stderr in the detail ("Show details" output channel), not just "failed".

## Verification

Mock `ClaudeCli`: each action calls the right function with the right scope/projectPath; Update disabled when none available; Uninstall requires the modal; a failing action surfaces stderr and leaves the list unchanged; no call ever includes `-y` or `--accept-command` (assert on the args). `npm test` green, `npm run build` clean. Manual with the real CLI on a throwaway plugin or isolated config dir (per 45.1): toggle, update, uninstall round trip.
