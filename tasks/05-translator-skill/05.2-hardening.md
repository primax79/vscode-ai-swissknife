# 05.2 — Drop unresolvable source-assistant provenance; per-field diagnostics (hardening)

> Part of [Canonical model + translator](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md) · hardening context: [../../SPEC.md](../../SPEC.md) §2, §7, [../_inbox/analyzed/codex-analysis-2.md](../_inbox/analyzed/codex-analysis-2.md) finding I9 · **revised after multi-engine review round 001** ([../_reviews/001-hardening-gate-SUMMARY.md](../_reviews/001-hardening-gate-SUMMARY.md), decisions 4, 9 — two independent engines flagged that `translateSkill`'s `fromAssistant` parameter has no source of truth for a manifest-less custom-repo artifact, and one found it's also literally the wrong type)

**This is a revision of already-merged code** — `src/translator/skill.ts`
and `src/translator/rule.ts` exist (task 05.1). Read both in full first.

**Goal, part 1 — drop `fromAssistant`/`sourceAssistant` entirely.**
`translateSkill`'s current signature takes `fromAssistant: 'claude-code'
| 'kilo-code'` — but a `git-custom`/`local-folder` source's content is
always resolved as neutral `skill-md` (per `02.3`'s `nativeFormat`
change), with **no real originating assistant to translate from**. Round
001's review found this parameter is unresolvable in practice (no caller
in the planned pipeline actually has an assistant to pass), and
additionally, in a later task's planned usage, would have been passed a
value typed `AssistantId` (which includes `github-copilot`/`codex-cli`/
`gemini-cli`) where the narrower `'claude-code' | 'kilo-code'` union is
required — a `tsc` failure waiting to happen once that caller was
written. Fix by elimination, not by widening the type: this project has
no real source-assistant provenance to translate from in Phase 1, so
stop asking for one.

Steps:

1. Change `translateSkill`'s signature in `src/translator/skill.ts` from

   ```ts
   translateSkill(source: CanonicalSkill, fromAssistant: SupportedAssistant, toAssistant: SupportedAssistant): TranslationResult<CanonicalSkill>
   ```

   to

   ```ts
   translateSkill(source: CanonicalSkill, toAssistant: SupportedAssistant): TranslationResult<CanonicalSkill>
   ```

   Update `translateRule` in `src/translator/rule.ts` the same way. Any
   internal logic that branched on `fromAssistant` (there shouldn't be
   much, since this Phase's only real case was always `lossless`
   regardless) collapses to checking only `toAssistant`'s known
   constraints — for Claude/Kilo specifically, still none, so the result
   is still always `lossless` for this Phase; the point of this change
   is removing an unresolvable parameter, not changing observed
   behavior for the pair that exists today.
2. Update every call site and every test that currently passes a
   `fromAssistant`/`sourceAssistant` argument (`skill.test.ts`,
   `rule.test.ts`, and any other file that calls `translateSkill`/
   `translateRule`) to the new two-argument form.

**Goal, part 2 — per-field diagnostics.** `SPEC.md` §2 promises a
diagnostic **per field**; the current `TranslationResult` only returns
one aggregate `diagnostic` for the whole artifact.

1. In `src/adapters/types.ts`, add:

   ```ts
   export interface FieldDiagnostic {
     path: string; // e.g. "name", "extraFields.customTag", "files[2].mode"
     severity: ConversionDiagnostic;
     message?: string; // required when severity !== 'lossless'
   }
   ```

2. Change `TranslationResult<T>` to:

   ```ts
   export interface TranslationResult<T> {
     value: T;
     overall: ConversionDiagnostic; // renamed from `diagnostic` — update every caller
     diagnostics: FieldDiagnostic[]; // one entry per inspected field, always non-empty
     notes: string[]; // kept for backward-compat human-readable summary; may be derived from diagnostics
   }
   ```

   Update every call site (including any code written for task 06 that
   may already exist by the time this lands — grep for `.diagnostic`
   specifically, not just `TranslationResult`, since the field rename is
   easy to miss). `overall` is the worst (most severe) severity across
   `diagnostics`, computed via an explicit ordering (`lossless <
   adapted-with-warning < potentially-destructive < unsupported`), not
   independently set.
3. For `translateSkill`, diagnose every field the hardened
   `CanonicalSkill` (from 03.4) actually has: `name`, `description`,
   `body`, each key of `extraFields`, and — **once 03.4 has landed** —
   the `files` collection itself plus each file's `relativePath` and
   `mode`. If 03.4 hasn't landed yet when you start this task, diagnose
   only the fields that exist without it and say so explicitly in your
   report; don't block on 03.4, but don't skip `files` silently either
   once it's available — make 03.4 a real dependency check, not an
   afterthought. **Identity translation must preserve the exact
   `Buffer` content and `mode` of every file**, not just the
   frontmatter/body fields — round 001's review flagged that a
   translator which silently drops or rebuilds the `files` payload
   during an otherwise-identity translation would defeat the whole
   point of 03.4's directory-payload work.
4. For `translateRule`, diagnose the field `CanonicalRule` actually has
   (`content` only — it has no `name`/`description`/`files`). Don't
   reuse `translateSkill`'s field list for rules; write a distinct,
   correct one.

5. Update `src/translator/skill.test.ts`/`rule.test.ts` for both the
   signature change (step 1) and the renamed/expanded result shape
   (steps 3-4): assert `diagnostics` is non-empty and every entry has
   `severity: 'lossless'` for the existing identity-translation cases,
   plus one new test asserting `overall` is computed correctly from a
   hand-constructed `FieldDiagnostic[]` with mixed severities (test the
   worst-of computation directly, since nothing in this Phase naturally
   produces a non-lossless real result to test against).

**Verification**: `npm run typecheck && npm run lint && npm test` all
pass, including every pre-existing test updated for both the signature
change and the rename. One commit containing all changed files —
nothing else. After this commit, update `tasks/00-INDEX.md` to mark
initiative 05 fully done (including this hardening task).
