# 05.1 — Translator + conversion diagnostics

> Part of [Canonical model + translator](plan.md) · spec: [../specs/foundations.md](../specs/foundations.md)

**Goal**: a translator module that converts `CanonicalSkill`/
`CanonicalRule` between assistants, returning a `ConversionDiagnostic`
alongside the result — even though for this Phase's only pair
(Claude↔Kilo) the answer is always `lossless`, the mechanism must exist
and be tested, because Phase 2 plugs a genuinely lossy case (`agent`) into
the same shape.

**Grounding**: SPEC.md §2 "diagnostic for each field" and §4 "canonical
model... preserves unrecognized fields." `src/adapters/types.ts`
(initiative 03) for `CanonicalSkill`/`CanonicalRule`/`ConversionDiagnostic`
— import them, don't redefine.

Steps:

1. Create `src/translator/skill.ts`:
   ```ts
   import type { CanonicalSkill, ConversionDiagnostic } from '../adapters/types';

   export interface TranslationResult<T> {
     value: T;
     diagnostic: ConversionDiagnostic;
     notes: string[]; // human-readable, empty when diagnostic is 'lossless'
   }

   export function translateSkill(
     source: CanonicalSkill,
     fromAssistant: 'claude-code' | 'kilo-code',
     toAssistant: 'claude-code' | 'kilo-code',
   ): TranslationResult<CanonicalSkill>;
   ```
   For this Phase's only pair, both directions are the identity function
   on `value` (name/description/body/extraFields unchanged) with
   `diagnostic: 'lossless'` and `notes: []` — **but don't hardcode
   "always lossless" as a shortcut that skips real inspection**. Actually
   check: if `source.name` or `source.description` would violate the
   target's known constraints (Claude Code has none documented beyond
   "required"; note in SPEC.md §1 that VSCode's Copilot skill format caps
   `name` at 64 chars / lowercase-hyphen and `description` at 1024 — Kilo
   and Claude Code CLI themselves impose no such cap per the files read
   for this spec) — if `toAssistant` is `'kilo-code'` or `'claude-code'`
   specifically (both uncapped), the check is a no-op and the result is
   `lossless`; write the function so that a future target with real
   constraints (Copilot, Phase 2) has an obvious place to add a real
   check, not a comment saying "not implemented."
   - Same-assistant translation (`fromAssistant === toAssistant`) is
     always `lossless`, trivially — include this as an explicit case,
     don't rely on it falling through the identity logic by accident.
2. Create `src/translator/rule.ts`, same shape, for `CanonicalRule`
   (which only has a `content` field — translation is pure identity for
   any pair in this Phase, `diagnostic: 'lossless'` always, since SPEC.md
   §5 establishes both assistants read the exact same file format/content
   with zero adaptation).
3. Write `src/translator/skill.test.ts` and `src/translator/rule.test.ts`:
   - Claude→Kilo and Kilo→Claude both produce `lossless` with an
     unchanged `value` for a representative `CanonicalSkill`/
     `CanonicalRule` (build the input from a real fixture already used in
     initiative 04's tests, e.g. read
     `agentic-coding-kit/plugins/common-tools/skills/gitignore/SKILL.md`
     and construct a `CanonicalSkill` from it, rather than a hand-typed
     literal with no real provenance).
   - A `CanonicalSkill` with a non-empty `extraFields` map still comes out
     `lossless` with `extraFields` unchanged (proves the "preserve
     unrecognized fields" decision holds through the translator layer,
     not just the adapter layer).
   - Same-assistant translation short-circuits to `lossless` (assert this
     explicitly as its own test case, not just as a side effect of the
     cross-assistant test).

**Verification**: both test files pass; `npm run lint && npm run
typecheck && npm run build` all exit 0. One commit containing
`src/translator/skill.ts`, `src/translator/rule.ts`, and their two test
files — nothing else. After this commit, update `tasks/00-INDEX.md`'s row
for initiative `05` to `✅ done`.
